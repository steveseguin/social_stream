เอกสารอ้างอิงอีเวนต์สด

หน้านี้อธิบายข้อมูลอีเวนต์มาตรฐานที่ Social Stream Ninja ส่งสำหรับแพลตฟอร์มหลัก ใช้เป็นแหล่งอ้างอิงร่วมเมื่อเชื่อมแหล่งใหม่ แก้ปัญหาการเชื่อมต่อ หรือจัดป้าย UI ให้ตรงกัน สำหรับตารางสรุปสั้นที่เน้นผู้ใช้ข้อมูล ดู ความเข้ากันได้ของอีเวนต์และการแจ้งเตือน.

สำคัญ: อีเวนต์ที่ใช้ได้ขึ้นอยู่กับแหล่งข้อมูล สิทธิ์ และการตั้งค่าจับข้อมูล หากต้องการซ่อนแถวที่ระบุอีเวนต์ในแผงด็อกหรือโอเวอร์เลย์ Featured ให้เพิ่ม &hideevents หรือ &hideallevents หากต้องการซ่อนอีเวนต์ที่เลือก ใช้ &filterevents=subscription_gift,new_follower,gifted ตัวกรองเหล่านี้ซ่อนแถวที่มีการชำระเงินซึ่งมีค่าได้ด้วย event; แถวบริจาคปกติที่ไม่มีตัวระบุอีเวนต์จะไม่ตรงกับตัวกรองอีเวนต์ ตัวกรองข้อความอื่นยังมีผล
เลือกวิธีจับข้อมูล: สำหรับ YouTube, Twitch และ Kick, โหมด WebSocket โดยทั่วไปครอบคลุมอีเวนต์มากกว่า การจับ DOM มาตรฐานอ่านแถวและการ์ดที่แสดงจริงในหน้า YouTube Super Chats, Super Stickers และของขวัญ Jewel มีเส้นทางจับข้อมูลทั้งสองโหมด อีเวนต์ของขวัญ ทิป และสมาชิกอื่นแตกต่างตามแหล่ง ดูตารางแพลตฟอร์มสำหรับเส้นทางที่รองรับและการตั้งค่าที่จำเป็น
กำลังสร้างระบบอัตโนมัติหรือไม่? ดู คู่มือ Event Flow เพื่อเรียนรู้การใช้ข้อมูลอีเวนต์เหล่านี้ในตัวเรียก การแจ้งเตือน และขั้นตอนงานกำหนดเอง คู่มือมี เอกสารอ้างอิงตัวแปรเทมเพลต สำหรับรูปแบบข้อความ ส่วนยอดของขวัญ การนับชุด และเกมที่แก้ไขได้ ดู สร้างเกมและรางวัล.
รูปแบบข้อมูล: แถวแชตแบบบริจาคควรใช้ hasDonation และตัวเลือกเพิ่มเติม donoValue อย่าตั้ง event: "donation" เพียงเพราะแถวแชต/ทิปปกติมีมูลค่า ใช้ชื่ออีเวนต์เฉพาะสำหรับการกระทำแพลตฟอร์มจริงหรือประเภทสินค้าแบบชำระเงินเท่านั้น เช่น superchat, supersticker, gift, หรือ jeweldonation ใช้ meta เฉพาะข้อมูลมีโครงสร้างเพิ่มเติมที่ผู้รับต้องใช้จริง และไม่มีช่องเดิมรองรับอยู่แล้ว

ฟีเจอร์ที่ใช้ได้โดยย่อ

ใช้ตารางนี้ดูประเภทแจ้งเตือนที่แต่ละวิธีจับข้อมูลส่งได้ในปัจจุบัน หมายเหตุข้อมูลแบบละเอียดอยู่ด้านล่าง

Multi-Stream Alert Box โดยเฉพาะจัดกลุ่มอีเวนต์สดเป็นหมวดแจ้งเตือนหลักหกหมวด: Follow, Subscription/Member, Donation, Bits/Cheers, Raid/Host, และ Purchase, พร้อมสองหมวดหมู่ที่เลือกเปิดใช้ได้ (Auction และ Hype Train) ที่เปิดผ่านพารามิเตอร์ URL โดยสร้างหมวดหมู่เหล่านั้นจากค่าที่มีอยู่ event, membership, subtitle, hasDonation, และ meta ช่องข้อมูลที่อธิบายที่นี่ ไม่ต้องมีรูปแบบข้อมูลแยก

ภาพรวมช่องข้อมูล

data ในที่นี้หมายถึงออบเจ็กต์ข้อความ ไม่ใช่ชั้นหุ้มเพิ่มเติมที่ต้องใส่ แถวแชตและอีเวนต์ที่มีเฉพาะเมทาดาทามีรูปแบบต่างกัน ตัวนับและภาพข้อมูลสถานะอาจไม่ใส่ chatname/chatmessage ในตารางแพลตฟอร์ม ข้อความ อธิบายแถวแชตปกติ ไม่ใช่ค่าตามตัวอักษร event: "message".

ช่องข้อมูล รูปแบบ การใช้งาน
data.type สตริง ตัวระบุแหล่งข้อมูลที่โอเวอร์เลย์ ตัวกรอง และ Event Flow ใช้ Instagram คงแชตสดเป็น instagramlive และความคิดเห็นที่ไม่ใช่แชตสดเป็น instagram ดู คู่มือประเภทแหล่งข้อมูล สำหรับรูปแบบย่อย แหล่งทั่วไป และการกำหนดเส้นทางขาออก
data.chatname สตริง ชื่อแสดงที่แหล่งข้อมูลให้มา ใช้ในการประมวลผลข้อความและเอาต์พุตที่ไม่ใช่โอเวอร์เลย์ นามแฝงชื่อแสดงผู้ใช้ที่ตั้งไว้อาจแทนค่านี้เฉพาะในสำเนาข้อมูลส่งไปแผงด็อกและโอเวอร์เลย์
data.username สตริง ชื่อผู้ใช้ต้นทางเมื่อมี ข้อมูลแผงด็อกหรือโอเวอร์เลย์ที่ใช้นามแฝงอาจเพิ่มช่องนี้เพื่อคงค่าต้นฉบับ chatname สำหรับการกระทำกับผู้ใช้ ข้อความมาตรฐานยังคงเดิม
data.userid สตริง รหัสผู้ใช้เฉพาะแพลตฟอร์ม การกระทำกับผู้ใช้ใช้ค่านี้ก่อน username และ chatname.
data.platformสตริง (ไม่บังคับ)การเชื่อมต่อบางตัวรวมค่านี้ร่วมกับ type อะแดปเตอร์แหล่งข้อมูลหลายตัวไม่ใส่ค่านี้ ใช้ type สำหรับกำหนดเส้นทางแหล่งข้อมูล
data.idสตริง | ตัวเลข (ไม่บังคับ)รหัสข้อความหรืออีเวนต์ ความหมายขึ้นอยู่กับแหล่งข้อมูลและช่องทางรับส่ง อย่าถือว่าเป็นรหัสดูแลแชตดั้งเดิมของแพลตฟอร์มเสมอ ใช้ meta.messageId เมื่ออะแดปเตอร์ให้สำหรับซิงก์การลบ
data.donoValueตัวเลข (ไม่บังคับ)ค่าเทียบเท่า USD แบบตัวเลขที่แหล่งข้อมูลให้มา รวมค่าประมาณ ค่าที่ถูกต้อง (รวมศูนย์) ใช้แทนการแปลง currency.js หากไม่มี ผู้ใช้ข้อมูลประเมิน USD จาก hasDonation และบริบทแหล่งข้อมูล ยอดและหน่วยต้นฉบับคงอยู่ใน hasDonation และเมทาดาทาผู้ให้บริการเดิม
data.chatbadgesอาร์เรย์ | สตริง (ไม่บังคับ)URL ภาพตราหรือออบเจ็กต์ตรา (type: "img" พร้อม src, type: "svg" พร้อม html, หรือ type: "text" พร้อม text) รีเลย์เก็บข้อความบนตราไว้ตามเดิมในช่องเพิ่มเติม rawText และสร้างค่าที่ escape แล้ว text สำหรับโอเวอร์เลย์เก่า ในการส่งต่อรอบหลังให้สร้างใหม่สำหรับ text จาก rawText; อย่า escape text อีกครั้ง ตัวแสดงผลปัจจุบันแสดง rawText ตามตัวอักษรเมื่อมี และคงการจัดการข้อความเข้ารหัสแบบเดิมเมื่อไม่มี นี่คือช่องรูปแบบการแทนค่า ไม่ใช่สิทธิ์แสดง HTML แหล่งเก่าอาจส่งสตริง HTML เดียวแทนอาร์เรย์ โอเวอร์เลย์แสดงตรารับทั้งสองรูปแบบและทำ HTML ตรากับ URL ให้ปลอดภัยในเครื่อง รวมกรณีผู้ส่งเป็นส่วนขยายเก่า ตราที่ไม่ถูกต้องต้องไม่ขัดขวางการแสดงข้อความแชตหรือสมาชิก
data.event สตริง | บูลีน ตัวระบุกิจกรรมระบบ (เช่น viewer_update, subscription_gift, giftpurchase) แชตปกติควรเว้นว่าง/false เพื่อให้โอเวอร์เลย์แยกประกาศระบบจากข้อความสนทนาได้
data.chatmessage สตริง เนื้อหาข้อความ มี HTML ที่ปลอดภัย/แสดงผลได้เฉพาะเมื่อ data.textonly เป็น false
data.textonly บูลีน มีผลเฉพาะ data.chatmessage. true หมายถึงแสดง chatmessage เป็นข้อความธรรมดา โดยคงแท็กตามตัวอักษรและข้อความที่ดูเหมือน entity อย่าถอดรหัส ทำ HTML sanitization หรือเพิ่มแท็กจัดรูปแบบในเนื้อหานั้น ให้ตกแต่งอีเวนต์บนองค์ประกอบที่แสดง false หมายถึง chatmessage อาจมี HTML ที่ปลอดภัย/แสดงผลได้ ข้อความเก่าที่ไม่มีแฟล็กยังคงพฤติกรรม HTML นั้น ช่องปกติอื่นเป็นข้อความธรรมดา ยกเว้นช่องสื่อ เช่น chatimg และ contentimg แสดงช่องข้อความธรรมดาด้วย textContent, หรือ escape หนึ่งครั้งเมื่อสร้างเทมเพลต HTML อย่าลบเนื้อหาหรือถอดรหัสซ้ำ ๆ
data.contentimg สตริง (ไม่บังคับ) ภาพเนื้อหาหรือ URL สื่อที่รองรับ ในส่วนขยายและแอปเดสก์ท็อป ตัวเลือกที่เปิดใช้ได้ allowExternalGifs การตั้งค่าเติมช่องว่างด้วยลิงก์ GIF โดยตรงแบบ HTTP(S) แรกในข้อความหรือในลิงก์ HTML เส้นทาง URL ต้องลงท้ายด้วย .gif (ไม่แยกตัวพิมพ์ใหญ่เล็ก); คงพารามิเตอร์คำค้นและแฟรกเมนต์ไว้ ไม่ต้องใช้คีย์ API และคง chatmessage และไฟล์แนบเดิม และเคารพ removeContentImage ตัวเลือกเพิ่มเติม hideExternalGifUrl การตั้งค่าเพิ่ม meta.hideExternalGifUrl: true; แผงด็อกและโอเวอร์เลย์ Featured จะซ่อนลิงก์ GIF ที่ตรงกันหลังภาพโหลดสำเร็จเท่านั้น โดยคงข้อความรอบข้างและข้อมูลต้นฉบับไว้ ภาพที่โหลดไม่สำเร็จหรือหมดเวลาจะยุบพื้นที่ไฟล์แนบและคงลิงก์ให้เห็น โอเวอร์เลย์เฉพาะ GIF ลองแสดงภาพโดยตรงหากดึงข้อมูลไบต์ภาพไม่ได้ และใช้เวลาแสดงที่ตั้งไว้เมื่อหาเวลาภาพเคลื่อนไหวไม่ได้ หากโหลดล้มเหลวหรือค้างจะเลื่อนคิวต่อ ไม่เพิ่ม event หรือเปลี่ยนแหล่งข้อมูล type ภาพภายนอกไม่ผ่านการกรองเนื้อหาและอาจโหลดไม่ได้หากโฮสต์บล็อกการฝัง
data.membership สตริง สถานะสมาชิกที่อ่านได้ เช่น MEMBERSHIP, new_sponsor, gift_recipient หน้าต่าง ๆ ใช้ค่านี้สำหรับตรา ตัวกรอง และประกาศ
data.subtitle สตริง คำอธิบายเสริม (ระยะเวลาสมาชิก การอัปเกรดระดับ ผู้มอบของขวัญ...) ให้สั้นและเป็นข้อความอย่างเดียว เพื่อให้โอเวอร์เลย์วางใต้ชื่อแสดงได้
data.hasDonation สตริง ยอดเงินหรือของขวัญเสมือน ($5.00, 500 bits, 300 coins) เติมค่าแม้เมื่อ data.event ว่างเพื่อให้โอเวอร์เลย์บริจาคตรวจพบ
data.meta ตัวเลข | ออบเจ็กต์ | สตริง (แบบเดิม) ใช้จำนวนเต็มสำหรับตัวนับเดี่ยว (ผู้ชม ผู้ติดตาม สมาชิก) และออบเจ็กต์สำหรับบริบทที่ละเอียดกว่า อีเวนต์เก่าบางตัว เช่น Twitch DOM community_highlight, มีค่าสตริง ตรวจรูปแบบของอีเวนต์นั้นก่อนอ่านคุณสมบัติออบเจ็กต์ รายละเอียดแบบมีโครงสร้างใหม่ควรอยู่ในออบเจ็กต์
data.firsttime บูลีน ตั้งเป็น true เมื่อเปิดการตรวจผู้แชตครั้งแรก เปิดฐานข้อมูลในเครื่อง และนี่เป็นข้อความแชตแรกที่บันทึกสำหรับผู้ใช้/แหล่งนั้น แผงด็อกใช้เพื่อไฮไลต์ครั้งแรกและตัวกรองเสียงเตือนครั้งแรก การตั้งค่าตราครั้งแรกที่เลือกใช้ได้จะเติมตราใบไม้หน้าค่า chatbadges.
data.lastactivity ตัวเลข เวลา Unix หน่วยวินาทีของกิจกรรมแชตก่อนหน้าที่บันทึกไว้สำหรับผู้ใช้นั้น เมื่อเปิดการตรวจผู้แชตครั้งแรกและฐานข้อมูลในเครื่อง ไม่ใส่สำหรับผู้ใช้ใหม่เอี่ยม

ช่องทางรับส่งการควบคุมโอเวอร์เลย์แยกจากแชต/อีเวนต์ที่จับ ตัวรับที่อัปเดตใช้ ssnControl ซองข้อมูลที่มีค่าการส่ง id, ฟีเจอร์ target, ช่องตอบกลับและรหัสไคลเอนต์ภาพข้อมูลหากระบุ เนื้อหาฟีเจอร์เดิมยังคงครบถ้วน การควบคุมฟีเจอร์สาธารณะใช้ช่อง 7 ส่วน Actions คงใช้ช่อง 6 สถานะ Poll และ Map มีค่าผู้ดำเนินรายการ epoch, revision และ reset ตัวระบุ; Timer, Ticker และ Spotify ใช้ ssnState พร้อม epoch และ revision ตัวระบุเหล่านี้อธิบายสถานะผู้ดำเนินรายการ ไม่ใช่ประวัติโหวต/แชตที่กู้คืน แหล่งข้อมูลต้องไม่เพิ่มช่องซองควบคุมในข้อความที่จับ การตอบรับไม่ได้ยืนยันการกระทำเสร็จหรือการมองเห็นใน OBS ดู สถานะการย้ายระบบ สำหรับฟีเจอร์ที่รองรับ การตกลงรูปแบบตอบกลับ และขีดจำกัดเชื่อมต่อใหม่

Phrase Guess ใช้ค่าดั้งเดิม {response: text} คำขอสำหรับคำตอบแชต server2 และ {action: "phraseGuessResponse", value: {type: "bot", chatname: name, chatmessage: text}} สำหรับประกาศเฉพาะแผงด็อก ผู้ดำเนินรายการต้องเปิดข้อความ server3 ขาเข้า การปิดควบคุมผู้ดำเนินรายการยังบล็อกคำขอเหล่านี้ ประกาศแผงด็อกส่งต่อเป็นแถวแชตบอตปกติพร้อม textonly: true, โดยไม่ส่งไปยังช่องป้อนแชตของแหล่งจับข้อมูล โหมด API เดิมคงรูปแบบคำสั่งเดิม

แนวทางใช้ Meta

เพื่อให้แดชบอร์ดและระบบอัตโนมัติสอดคล้องกัน ให้ทำตามแนวทางเหล่านี้เมื่อขยาย data.meta:

  • viewer_update, follower_update, subscriber_update, และ likes_update ใช้จำนวนเต็มธรรมดา meta ค่า likes_update เป็นยอดรวมแพลตฟอร์มจากแหล่งที่เชื่อถือได้ ผู้ใช้ข้อมูลต้องตั้งค่าที่แสดงแทนการบวกเพิ่ม สคริปต์เบื้องหลังรวมจำนวนผู้ชมไว้ใน viewer_updates พร้อมออบเจ็กต์ที่มีคีย์ตาม data.type.
  • giveaway_state เป็นภาพข้อมูลที่มีเฉพาะเมทาดาทาซึ่งผู้ดำเนินรายการสร้างสำหรับหน้าที่จัดการ meta.giveaway เวอร์ชัน 2 รวม giveawayId, ค่าที่เก็บถาวร roundId/epoch, เพิ่มค่า generation ข้ามรอบใหม่, revision ภายในรอบ, status, open, draw, keyword, count, ticketCount, ค่าที่ตรึงไว้ config, ตัวอย่างสูงสุด 120 รายการของ entrants, และ 20 รายการล่าสุดของ winners รายการให้ค่า id, name, platform และ tickets; ผู้ชนะเพิ่ม drawnAt และค่าที่มอบให้ points Coin Flip Pot เพิ่ม outcome; Number Hunt เพิ่ม number พร้อมค่าสาธารณะ low, high และค่าล่าสุด guesses, ไม่ส่งข้อมูลลับ ผู้ใช้ข้อมูลกรองตามรหัสแจกของรางวัลและทิ้งรุ่น/ฉบับแก้ไขเก่ากว่า สิ่งเหล่านี้เป็นตัวอย่างสำหรับแสดงผล ไม่ใช่รายการตั๋วทั้งหมดหรือคำสั่งจ่ายเงิน คีย์กระเป๋าเงิน ยอดคงเหลือ และรายการจองไม่อยู่ในภาพข้อมูลผู้ชม ผู้ดำเนินรายการเผยแพร่ไปยัง giveaway ป้ายกำกับ P2P และฟีด WebSocket โอเวอร์เลย์ที่เปิดไว้ ไม่ได้บอกว่า OBS มองเห็นอยู่ คู่มือ.
  • meta.giveawayControlResult มีผลของการกระทำแจกของรางวัล Event Flow (ok, ตัวเลือกเพิ่มเติม error, giveaway หรือ simulated). meta.giveawayHandled แสดงรหัสแจกของรางวัลที่การกระทำโฟลว์เข้าร่วม/ซื้อจัดการแล้ว เพื่อไม่ให้คำสั่งแชตอัตโนมัติเรียกเก็บซ้ำ ตัวแก้ไขเพิ่ม meta.economyTest สำหรับการกระทำแจกของรางวัลจำลอง ไม่ใช่อีเวนต์แพลตฟอร์มต้นทางหรือข้อมูลรับรองการอนุญาต
  • video_stats ใช้ค่าแบบมีโครงสร้าง meta ออบเจ็กต์สำหรับสถานะความพร้อมของตัวเข้ารหัส/เซิร์ฟเวอร์ภายนอก รวม provider, label, online, bitrateKbps, rttMs, bufferMs, ตัวนับแพ็กเก็ตสูญหาย/ถูกทิ้ง และรายละเอียด codec หากมี
  • อีเวนต์แบบบริจาคอาจมีออบเจ็กต์อธิบาย เช่น { amount, currency, supporter } สำหรับ Kick, { bits } สำหรับ Twitch cheers อีเวนต์สมาชิกมีเมทาดาทาเฉพาะแหล่งของตัวเอง ไม่ถือเป็นการบริจาคเงินโดยอัตโนมัติ
  • ข้อความ webhook ของ Stripe, Ko-fi, Buy Me a Coffee และ Fourthwall ที่ปรับรูปแบบแล้วมีค่าที่จำกัดขอบเขตตามผู้ให้บริการ meta.webhookId, คัดลอกจากรหัสอีเวนต์ที่คงที่ของผู้ให้บริการ เพื่อให้หน้าปลายทางตัดรายการซ้ำจากการลองใหม่และการรับส่งหลายช่องทางได้
  • เรด Twitch ส่ง { fromId, fromLogin, viewers } แหล่งอื่นต่างกัน: Whatnot ใช้ meta.numRaiders, ส่วน SharePlay ใช้ช่องเพิ่มเติม meta.fromLogin/meta.viewers ตรวจแถวเฉพาะแหล่งข้อมูลก่อนอ่านเมทาดาทาเรด
  • การแลกรางวัล Twitch EventSub ให้ค่า meta.rewardId, cost, rewardTitle, redemptionId, และรูปแบบเดิม alias ควบคู่กับข้อความที่เตรียมไว้ การ์ดรางวัล DOM และแหล่งอื่นอาจให้ช่องน้อยกว่าหรือต่างกัน
  • user_banned มีเฉพาะเมทาดาทาสำหรับวิดเจ็ตดูแลแชต โดยตั้งใจไม่รวม chatname และ chatmessage; ใช้ meta.username, meta.displayName, meta.avatarUrl, และ meta.profileUrl.
  • ช่องทางรับส่งแชตที่รองรับการซิงก์ลบผ่านการควบคุมแหล่งข้อมูลควรให้รหัสแชตดั้งเดิมของแพลตฟอร์มเป็น meta.messageId แทนการพึ่งค่าภายในแผงด็อก data-mid ค่า

  • รางวัลสติกเกอร์ SSN ที่เลือกเปิดใช้: event: "sticker" ส่งเฉพาะไปยัง stickers ป้ายกำกับโอเวอร์เลย์หลังหักแต้มสะสม โดยตั้ง platform และ type ไปยังค่าของข้อความต้นทาง type, และคง chatname, โดยเว้นว่าง chatmessage, textonly: true, และ contentimg ที่มีเส้นทางภาพสัมพัทธ์ในแพ็กเกจ หรือ URL สื่อ HTTPS ที่ผู้ดำเนินรายการอนุมัติ meta.sticker มี id, pack, name, cost, duration (วินาที), motion, redemptionId, และ expiresAt (มิลลิวินาที Unix) นี่คือรางวัล SSN ไม่ใช่การบริจาคของแพลตฟอร์มหรืออีเวนต์แต้มช่องดั้งเดิม ดู แกลเลอรีและคู่มือตั้งค่า.

  • โอเวอร์เลย์การค้าควรใช้ออบเจ็กต์ภาพข้อมูลใน meta (ตัวอย่างเช่น auction_update และ commerce_update) และหลีกเลี่ยงช่องข้อมูลระดับบนสุดที่เพิ่มเองโดยไม่มีมาตรฐาน

การแจ้งเตือนผู้ติดตาม YouTube (new_follower)

ขณะนี้ Social Stream ตรวจพบผู้ติดตาม YouTube ใหม่ได้ด้วย myRecentSubscribers endpoint ของ API ทำงานคล้ายการแจ้งเตือนสมาชิก Streamlabs

วิธีทำงาน:

  • ตรวจ YouTube API ทุก 5 นาทีเพื่อหาผู้ติดตามล่าสุด
  • ติดตามผู้ติดตามที่เห็นใน localStorage เพื่อตรวจหาคนใหม่
  • ส่ง new_follower อีเวนต์พร้อมชื่อ อวาตาร์ และรหัสช่องของสมาชิก
  • ปิดข้อความแจ้งเตือนผู้ติดตามเป็นค่าเริ่มต้น เมื่อเปิดจะใช้ข้อความแปลปัจจุบันสำหรับ alert-just-subscribed
  • ค่าเริ่มต้นรวมกลุ่มเมื่อมีสมาชิกใหม่มากกว่าสามคนเข้ามารัว ๆ เพื่อไม่ให้การเชื่อมต่อใหม่ทำให้โอเวอร์เลย์หรือ Event Flow เต็มไปด้วยรายการ
  • ต้องเปิดโหมด WebSocket ในการตั้งค่าส่วนขยาย

ข้อจำกัด (เป็นข้อจำกัดของ YouTube API ไม่ใช่ Social Stream):

  • ไม่รับประกันระยะเวลาส่ง – SSN ตรวจทุกห้านาที แต่ API อาจคืนผลล่าช้าหรือไม่ครบ อย่าพึ่งกรอบเวลาสี่ชั่วโมงตายตัว
  • เฉพาะการติดตามสาธารณะ – ผู้ติดตามที่ตั้งรายชื่อการติดตามเป็นส่วนตัวจะไม่เรียกการแจ้งเตือน YouTube ตั้งการติดตามเป็นส่วนตัวตามค่าเริ่มต้น
  • เฉพาะเจ้าของช่อง – คุณรับการแจ้งเตือนผู้ติดตามได้เฉพาะช่องที่เป็นเจ้าของและยืนยันตัวตนแล้ว
  • การใช้โควตา API – การตรวจแต่ละครั้งใช้ API 1 หน่วย หากตรวจทุก 5 นาที จะใช้ประมาณ 288 หน่วยต่อวัน (จากโควตาเริ่มต้น 10,000 ต่อวัน)

ตัวเรียกในตัวแก้ไข Event Flow: ใช้ data.event === "new_follower" และ data.type === "youtube"

OBS Flow Actions

การใช้งานในโค้ด: actions.html ผ่านอีเวนต์ OBS WebSocket v5 พร้อม dock.html อีเวนต์แหล่งเบราว์เซอร์ OBS เป็นทางสำรอง

  • เปิดโอเวอร์เลย์ Flow Actions ด้วยเซสชัน Social Stream เดียวกับตัวแก้ไข Event Flow/ระบบเบื้องหลัง หรือโหลดแผงด็อกไว้ใน OBS
  • ตั้งค่า OBS WebSocket v5 บน OBS 28+ โดย URL เริ่มต้นคือ ws://127.0.0.1:4455.
  • เป็นอีเวนต์ระบบ Event Flow ไม่รวม chatname หรือ chatmessage, และรายละเอียด OBS เพิ่มเติมอยู่ภายใน meta.

กล่องแจ้งเตือน Streamlabs

การใช้งานในโค้ด: sources/streamlabs.js (DOM กล่องแจ้งเตือน); สะพานเชื่อมซ็อกเก็ตเพิ่มเติมที่ sources/websocket/streamlabs.html

  • เปิดกล่องแจ้งเตือน Streamlabs ไว้ในแท็บหรือแหล่งเบราว์เซอร์ให้การแจ้งเตือนแสดง สคริปต์เนื้อหาอ่าน DOM แจ้งเตือนเพื่อรับข้อความ/ภาพ/โทเค็น
  • การแจ้งเตือนแบบบริจาคตั้งค่า hasDonation (เช่น “$10 USD” หรือ “100 bits”) และตัวเลือกเพิ่มเติม donoValue เป็น USD
  • ประเภทอีเวนต์ที่อนุมาน: follow, subscription, gift, cheer, donation, superchat, raid, redeem, merch, sponsor.
  • สำหรับสะพานเชื่อมซ็อกเก็ต ให้วางโทเค็น Streamlabs Socket API แล้วเชื่อมต่อ การแจ้งเตือนส่งต่อได้โดยไม่ต้องเปิดหน้ากล่องแจ้งเตือน

TikTok Live – การจับ DOM และฟีด TikFinity

การใช้งานในโค้ด: sources/tiktok.js สำหรับหน้า TikTok ดั้งเดิมและ sources/tikfinity.js สำหรับวิดเจ็ต/iframe ฟีดกิจกรรมของ TikFinity ส่วน SSApp ยังมีการเชื่อมต่อ TikTok ดั้งเดิมที่รองรับอีเวนต์ครอบคลุมที่สุด (ดูเอกสาร SSApp)

  • ทำงานบนหน้าถ่ายทอดสดของเจ้าของช่อง แบนเนอร์ของขวัญ/ไลก์/ติดตามแสดงข้อมูลเฉพาะเมื่อเซสชันยืนยันตัวตนแล้ว
  • TikTok ให้อีเวนต์จำนวนมากผ่านการตรวจ DOM โดยไม่ต้องใช้โหมด WebSocket – จับของขวัญ การติดตาม ไลก์ และการเข้าร่วมที่เลือกเปิดจากแถวที่แสดง
  • หน้าวิดเจ็ต TikFinity ที่ tikfinity.zerody.one/widget/activity-feed* ก็ทำงานได้เช่นกัน iframe ฟีดกิจกรรมที่ฝังส่งช่องข้อมูล TikTok มาตรฐานเดียวกันสำหรับแชต ติดตาม แชร์ ของขวัญ สมัครสมาชิก การเข้าร่วมที่เลือกเปิด และหีบสมบัติ
  • ไม่ต้องยืนยันตัวตน API เพิ่มเติม
  • โหมดดั้งเดิมของ SSApp ยังเพิ่มอีเวนต์นอกเหนือจากเส้นทางจับหน้า/วิดเจ็ต: question_new, emote, viewer_update, และค่าสรุปรวมที่เลือกเปิดใช้ likes_update.

For explicitly streakable gifts with a repeatEnd flag, TikFinity sends only the completed streak and its final quantity; intermediate count updates are not forwarded. Non-streak gifts and older payloads without that flag continue through immediately. Native DOM gift streak updates and TikFinity gift rows include meta.tiktokGiftStreakId, meta.tiktokGiftCount, และ meta.tiktokGiftQuietMs เพื่อให้โอเวอร์เลย์รวมอัปเดตซ้ำได้ รหัสคอมโบแบบเดิมไม่ซ้ำภายในอินสแตนซ์หน้า เมทาดาทาของขวัญอาจรวม tiktokGiftMessageId (รหัสข้อความ TikTok ต้นฉบับ), tiktokGiftSenderId, groupId, giftId, giftName, streakable, และ repeatEnd รหัสดั้งเดิมระบุของขวัญเดียวกันข้ามหน้าต่างจับข้อมูล รหัสกลุ่มที่ไม่เป็นศูนย์ร่วมกับรหัสผู้ส่งและของขวัญใช้ระบุการอัปเดตคอมโบสะสม การจับ SSApp WebSocket ให้ช่องเดียวกันหลังคอมโบจบ พร้อม count คงไว้เพื่อความเข้ากันได้ ตรวจสวิตช์บริจาคเมื่อส่งต่อของขวัญแต่ละรายการ การปิดบริจาค TikTok นำออก hasDonation และ donoValue โดยคงอีเวนต์ของขวัญและเมทาดาทา TTS ใช้ตัวตนเหล่านี้รวมอัปเดตและระงับรายการสำเร็จซ้ำนานสูงสุดสิบนาที (แคชจำกัดขนาด) และอ่านของขวัญ TikTok เป็นผู้ส่ง จำนวน และชื่อของขวัญ ข้อมูลเก่าใช้รหัสคอมโบและข้อความเดิมเป็นทางสำรอง ไม่อนุมานตัวตนจากข้อความของขวัญอย่างเดียว เสียงพูดของขวัญ TikTok ใช้ภาษา TTS/เสียงที่เลือกแยกจากภาษา UI กริยาประกาศมีคำแปลภาษาอังกฤษ สเปน โปรตุเกส ฝรั่งเศส เยอรมัน อิตาลี และดัตช์ ภาษาอื่นใช้ผู้ส่ง จำนวน และชื่อของขวัญโดยไม่ใส่กริยาภาษาอังกฤษ TTS แบบเรียบง่ายคงรูปแบบกลางนี้ ชื่อของขวัญคงตามที่แพลตฟอร์มให้มา ไม่ได้แปลแค็ตตาล็อกของขวัญหรือข้อความแชตอัตโนมัติ และไม่อนุมานภาษาสตรีม

สำหรับการอัปเดตคอมโบเหล่านี้ จำนวนและป้ายบริจาคเป็นค่าสะสม: 1, 2, 3 หมายถึงสามของขวัญ ไม่ใช่หก ระบบรวมยอดควรบวกเฉพาะส่วนที่เพิ่มจากค่าสูงสุดที่เห็นแล้วสำหรับรหัสคอมโบนั้น การจับมาตรฐานรองรับทั้งคลาสของขวัญเดิมและแถวภาพ/จำนวนปัจจุบัน ทั้งคู่คง event: "gift" และ hasDonation ราคาที่ไม่ทราบจะคงจำนวน/ชื่อของขวัญไว้แสดง และประเมิน USD โดยใช้หนึ่งเหรียญต่อของขวัญหนึ่งชิ้น ค่าที่แหล่งข้อมูลให้มา donoValue มีลำดับความสำคัญก่อน เมทาดาทาของขวัญที่แสดงอาจให้ coinsPerGift หรือ diamondsPerGift ก่อนต้องใช้ตารางของขวัญหรือค่าเริ่มต้น การประเมินเหรียญแบบ Standard/TikFinity และการประเมินเพชรแบบดั้งเดิมของ SSApp ใช้การแปลงแยกตามเดิม ทั้งคู่ไม่ใช่ยอดเงินสดรับที่รับประกัน

Whatnot

การใช้งานในโค้ด: sources/whatnot.js

  • เปิดหน้ารายการ Whatnot สดโดยให้แชตมองเห็น การจับ websocket ที่มีอยู่ให้แชต การแจ้งเตือนประมูล/ขาย การชำระเงินล้มเหลว เรด การบริจาค และอัปเดตผู้ชมอย่างรวดเร็ว ภาพข้อมูลสินค้า/แจกของรางวัลยังพึ่งส่วน DOM ที่แสดงในหน้ารายการ
  • จับอีเวนต์สตรีม (Capture Stream Events) ควบคุมอีเวนต์ระบบ Whatnot และอัปเดตเมทาดาทาประมูล/แค็ตตาล็อก แถวเข้าร่วมยังต้องใช้ จับอีเวนต์สตรีม "joined"; จำนวนผู้ชมยังทำตามสวิตช์ viewer/hype
อีเวนต์ เมื่อใดที่ทำงาน หมายเหตุข้อมูลที่รับส่ง
viewer_update จำนวนผู้ชมเปลี่ยนจากอัปเดตสตรีมสด websocket โดยใช้การตรวจ DOM เป็นทางสำรอง meta เป็นจำนวนเต็มผู้ชม
donation อีเวนต์ทิปและการร่วมสมทบบูสต์ชุมชน Whatnot websocket hasDonation มียอดที่จัดรูปแบบ บริบทเฉพาะ websocket อยู่ใน meta.
raid อีเวนต์เรด Whatnot websocket รวมคำตอบกิจกรรมย้อนหลัง meta.numRaiders รวมเมื่อ Whatnot ให้มา
joined แถวแชตที่เนื้อหาหลังปรับรูปแบบขึ้นต้นด้วย joined, เมื่อ จับอีเวนต์สตรีม "joined" เปิดอยู่ ใช้ป้ายอีเวนต์สตริงสำหรับประกาศเข้าร่วม (ไม่ใช่บูลีน true).
auction_update เมื่อสถานะประมูลสดส่วนท้ายเปลี่ยน (ข้อความผู้ชนะ/กำลังนำ ชื่อ ราคาเสนอ ราคา เวลา สถานะขายแล้ว) มักเร็วขึ้นด้วยแพ็กเก็ตวงจรประมูลผ่าน websocket อีเวนต์ที่มีเฉพาะเมทาดาทา ไม่มี chatname/chatmessage; ข้อมูลอยู่ใน meta (ตัวอย่างเช่น meta.title, meta.bids, meta.price, meta.timer, meta.status).
commerce_update เมื่อส่วนแค็ตตาล็อกเปลี่ยน (สินค้า surprise sets การแจกของรางวัลที่จะมาถึง) มักเร็วขึ้นด้วยแพ็กเก็ตวงจรแจกของรางวัล/สินค้าผ่าน websocket ภาพข้อมูลที่มีเฉพาะเมทาดาทา พร้อมจำนวนแต่ละส่วนและอาร์เรย์รายการใน meta.products, meta.surpriseSets, และ meta.upcomingGiveaways.
auction_started, new_bid, auction_ended, product_sold ได้รับการแจ้งเตือน websocket สดที่ตรงกัน เป็นอีเวนต์รายตัว แยกจากภาพข้อมูลแสดงผลเดิม platform/type: "whatnot", ข้อความธรรมดา chatname, userid เมื่อให้มา ชื่อสินค้าใน subtitle, และข้อความธรรมดา chatmessage พร้อม textonly: true รหัสและรายละเอียดประมูลที่มีอยู่ใน meta: productId, auctionId, orderId, transactionId, livestreamId, bidId, bids, auctionEndTime, และ status ตัวเลือกเพิ่มเติม price เป็นหน่วยหลักของสกุลเงิน พร้อม priceText และ currency เมื่อให้มา
payment_failed ได้รับการแจ้งเตือน websocket สดว่าชำระเงินไม่สำเร็จ ช่องผู้ซื้อ สินค้า และรหัสที่มีอยู่ชุดเดียวกัน พร้อม meta.paymentStatus: "failed" เมื่อมีเพียง product.purchaserUserId ระบุผู้ซื้อ จะเติมค่าใน userid ในอีเวนต์ขาย/ชำระเงิน และชื่อผู้ซื้อคงว่าง ไม่อนุมานผู้ซื้อจากการประมูลอื่นหรือก่อนหน้า
payment_succeeded ได้รับการแจ้งเตือน websocket สดว่าชำระเงินสำเร็จ meta.paymentStatus: "succeeded", พร้อมผู้ซื้อ สินค้า รหัสคำสั่งซื้อ และช่องข้อมูลอื่นที่อนุญาตซึ่งการแจ้งเตือนนั้นให้มา ยังคงเป็นอีเวนต์ชำระเงินแยก ไม่ส่งอีกหนึ่งอีเวนต์ purchase หรือการบริจาค ช่องที่ขาดคงว่างหรือไม่ใส่ แม้การขายก่อนหน้าเคยให้มา

การอัปเดตแสดงประมูล/การค้ายังคงเป็นภาพข้อมูลจาก DOM หากต้องการจับคู่อีเวนต์ websocket รายตัวใน Event Flow ให้ใช้ ประเภทอีเวนต์ (ขั้นสูง), เลือก อีเวนต์กำหนดเอง, แล้วป้อนชื่อให้ตรงทุกตัว ป้ายกำกับใช้ **{username}**\n{subtitle} พร้อมน้ำหนักข้อความที่เลือก เงื่อนไขเปรียบเทียบได้กับ meta.paymentStatus พร้อม failed ส่วน ตัวอย่างป้าย Whatnot ที่นำเข้าได้ พร้อมใช้ การตั้งค่าจับอีเวนต์สตรีมเดิมยังมีผล

ช่องเพิ่มเติมที่เลือกใช้ได้ ได้แก่ meta.catalogProductId (ค่าของแพ็กเก็ต product.productId), meta.parentProductId (product.parentId), meta.transactionType (ประเภทการขายของ Whatnot โดยไม่เปลี่ยนแปลง) และ meta.placeOrderErrorReason (รหัสข้อผิดพลาดคำสั่งซื้อ/การชำระเงินที่ Whatnot ส่งมา) การอ้างอิงสินค้าเหล่านี้อธิบายแค็ตตาล็อกหรือประกาศขายหลัก ไม่ได้แทนรหัสคำสั่งซื้อ จำนวนสต็อกไม่ถือเป็นจำนวนที่ซื้อ

สำหรับระบบอัตโนมัติเมื่อชำระเงินสำเร็จ ให้ตั้ง ประเภทอีเวนต์ (ขั้นสูง) ตัวเรียกเป็น อีเวนต์กำหนดเอง: payment_succeeded, และกรองแหล่งข้อมูลเป็น Whatnot เงื่อนไขและเทมเพลตเดิมใช้ช่องของอีเวนต์นั้นได้คือ userid, chatname, subtitle และ meta.orderId โดยตรง ไม่ต้องจำรายการซื้อไว้หากการแจ้งเตือนมีรายละเอียดที่จำเป็น

การประมูลจบหรือสินค้าถูกทำเครื่องหมายว่าขายแล้วไม่ได้ยืนยันว่าชำระเงินสำเร็จ การแจ้งเตือนเหล่านี้จึงไม่ส่งเป็นรายการชำระแล้ว purchase อีเวนต์และไม่ตั้งยอดบริจาค อีเวนต์สำเร็จส่งเฉพาะเมื่อได้รับ payment_succeeded การแจ้งเตือน การจับข้อมูลไม่ตรวจการชำระเงินสำเร็จเป็นระยะหรืออนุมานจากการขาย ส่วนอื่น paymentStatus ค่าส่งต่อเฉพาะเมื่อมีอย่างชัดเจนในแพ็กเก็ตที่จับได้ ไม่ใส่รหัสที่ขาด รหัสสินค้าอย่างเดียวอาจครอบคลุมหลายการขาย จึงใช้รหัสคำสั่งซื้อ/ประมูลที่ให้มาเพื่อเชื่อมการแจ้งเตือน การจับข้อมูลไม่จำการซื้อหรือจับคู่อัปเดตชำระเงิน ขั้นตอนนั้นต้องตั้งอย่างชัดเจนใน Event Flow แพ็กเก็ตซ้ำช่วงสั้นจากสะพานจับข้อมูลเดิมสองตัวจะถูกระงับ ไม่ส่งต่อออบเจ็กต์คำสั่งซื้อ/ชำระเงินดิบ

eBay Live

การเชื่อมต่อผู้ขาย eBay ใน Monetization ต้องตั้งค่าบริการ SSN eBay และได้รับความยินยอม OAuth จากผู้ขาย การจับ eBay Live ด้านล่างทำงานแยกกัน โหมด Sandbox ใช้ URL ประกาศขาย sandbox ระบุผู้ซื้อว่า "eBay Sandbox buyer" และขึ้นต้นข้อความด้วย "Sandbox test purchase:" การซื้อ Sandbox คงรูปแบบการซื้อเดียวกันและเรียกการแจ้งเตือน/การกระทำแชตที่เปิดไว้ขณะทดสอบได้ ข้อกำหนดการชำระเงินที่ใช้จริงส่ง event: "purchase", พร้อม type และ platform ตั้งเป็น ebay ต้องเป็นคำสั่งซื้อที่ชำระแล้วและตรงกับสินค้าที่เลือก id เป็นตัวระบุบรรทัดคำสั่งซื้อแบบทึบที่คงที่; chatname เป็น "eBay buyer", chatmessage เป็นข้อความธรรมดา (textonly: true), subtitle เป็นชื่อสินค้าและตัวเลือกเพิ่มเติม contentimg เป็นภาพของรายการนั้น meta.ebayPurchase มี itemId, itemName, quantity, และค่าสาธารณะ url ไม่มีตัวตนผู้ซื้อ ข้อมูลจัดส่ง hasDonation หรือ donoValue รวมไว้ ต่างจากการอัปเดตประมูลหรือสต็อกที่ดึงจากหน้า ซึ่งไม่ยืนยันการชำระเงิน

viewer_update เมื่อจำนวนผู้ชมอีเวนต์ปัจจุบันเปลี่ยน (จำนวนส่วนหัวหรือค่าสำรองจากป้ายอีเวนต์สด) meta เป็นจำนวนเต็มผู้ชม

  • การแลกโทเค็น OAuth เพิ่มเติมใช้สำหรับ endpoint ตัวช่วย เช่น https://api.joystick.tv/api/users/stream-settings.

ตัวรับ Shopify ที่ลงลายเซ็นซึ่งเลือกเปิดใช้ได้ส่ง platform/type: "shopify" และ event: "purchase" เฉพาะสำหรับ orders/paid พร้อม financial_status: "paid", ยอดรวมบวก, test: false, ไม่มีการยกเลิก และมีเวลาการอัปเดตล่าสุดจากเนื้อหาที่ลงลายเซ็น การแจ้งเตือนทดสอบ ยังไม่ชำระ เก่า ยกเลิก และคืนเงินไม่ส่งการกระทำซื้อ ไม่มีการอนุมานเจตนาให้ของขวัญ

chatname เป็น Anonymous ไม่รวมช่องลูกค้า หมายเหตุส่วนตัว และ URL คำสั่งซื้อ chatmessage เป็นข้อความธรรมดาพร้อม textonly: true; subtitle เก็บชื่อสินค้าสาธารณะสูงสุดสามชื่อ meta.commerce มี orderTotal และ currency ในสกุลเงินร้านค้า พร้อม quantity เมื่อทราบจำนวนที่ถูกต้องครบถ้วน ผู้รับและจุดประสงค์สินค้าจริง/ดิจิทัลยังไม่ตั้ง ไม่มี hasDonation หรือ donoValue ถูกตั้งค่า id เป็นแฮชคงที่แบบทึบ จำกัดขอบเขตตามร้าน/คำสั่งซื้อพร้อมคำนำหน้า Shopify ไม่ใช่รหัสคำสั่งซื้อดิบ

การซื้อใช้เส้นทางกิจกรรม หมวด Purchase ใน multi-alerts และ Event Flow ที่มีอยู่ การโปรโมตสินค้าใช้ตัวเดิม meta.monetization.commerce แค็ตตาล็อก การนำเข้าสินค้าหรือตั้งป้ายโปรโมตเป็น Gift ไม่สร้างอีเวนต์ซื้อหรือของขวัญ การตั้งค่า Shopify และข้อจำกัดการส่ง.

ของขวัญและการค้า

ใช้ event: "gift" สำหรับของขวัญ, giftcontribution สำหรับการจ่ายเงินสมทบของขวัญ, giftfunded สำหรับการระดมทุนสำเร็จ และ purchase สำหรับการขายสินค้า ชื่อเหล่านี้ไม่ขึ้นกับผู้ให้บริการหรือเป็นสินค้าจริง/ดิจิทัล สงวนชื่อเดิม giftpurchase อีเวนต์สำหรับสมาชิกแบบของขวัญ Throne เคยใช้ชื่อนั้นผิดและขณะนี้ส่ง gift แหล่งสร้างอีเวนต์สมาชิกเดิมไม่เปลี่ยน ตัวกรองชื่ออีเวนต์ Throne กำหนดเองควรเปลี่ยนเป็น gift; ไม่ต้องเปลี่ยนตัวกรองการบริจาค

hasDonation ยังเป็นสัญญาณเพื่อความเข้ากันได้สำหรับการสนับสนุนที่ชำระเงิน พร้อม donoValue ที่เก็บมูลค่า USD ที่ให้มาหรือประเมิน ของขวัญและการร่วมสมทบคงช่องเหล่านั้นไว้ การระดมทุนสำเร็จไม่ใส่ทั้งคู่เพื่อไม่ให้นับเงินสมทบซ้ำ การขายสินค้าปกติไม่ใส่เป็นค่าเริ่มต้น โดยคงข้อกำหนด eBay อย่าอนุมานเจตนาให้ของขวัญจากร้านค้า URL รายการอยากได้ หรือสินค้าจริง การซื้อให้ผู้ซื้อเองหรือผู้รับอื่นยังเป็นการขาย เว้นแต่แหล่งระบุชัดว่าให้ของขวัญครีเอเตอร์

ค่าร่วมเพิ่มเติม meta.commerce ช่องข้อมูลคือ recipient (creator, buyer, other), itemType (physical, digital, service), quantity (จำนวนสินค้าบวก), currency (สกุลเงิน ISO), goalAmount (เป้าหมายระดมทุนในหน่วยหลัก ไม่ใช่รายได้ใหม่) และ orderTotal (ยอดรวมคำสั่งซื้อที่ชำระแล้วซึ่งทราบค่า ในหน่วยหลักของสกุลเงิน; เป็นการค้า ไม่ใช่รายได้บริจาค) ละรายละเอียดที่ไม่ทราบ เก็บชื่อสินค้าไว้ใน subtitle, ภาพใน contentimg, และข้อความผู้สนับสนุนใน chatmessage เมทาดาทาผู้ให้บริการเดิมยังใช้ได้ Throne ให้ผู้รับและสกุลเงิน พร้อม goalAmount เมื่อสำเร็จ ส่วน eBay ให้จำนวน ทั้งคู่ไม่เดาประเภทสินค้าหรือเปิดเผยข้อมูลส่วนตัวผู้รับ

ฟีดกิจกรรมแสดงอีเวนต์เหล่านี้แม้ไม่มีข้อความผู้สนับสนุน Multi-alerts ใช้รูปแบบบริจาคสำหรับของขวัญและการร่วมสมทบ รวมการแจ้งเตือน Gift Fully Funded แยกที่ไม่มีมูลค่าเงิน การซื้อมีหมวด Purchase แยก เปิดเป็นค่าเริ่มต้น พร้อม purchasestyle, purchasesound, purchaseaccent, และ disablepurchases ตัวควบคุม URL การแจ้งเตือนซื้อไม่เปลี่ยนยอดบริจาค

Event Flow มีชื่ออีเวนต์เหล่านี้ในตัวเรียก Event Type และ Other Event ตัวเรียก Donation ยังคงตรวจ hasDonation; ตัวเรียก Gift Sub คงความหมายสมาชิก Compare Property รับเส้นทางซ้อน เช่น meta.commerce.recipient เทมเพลตการกระทำรับ {meta.commerce.quantity} และ {meta.commerce.currency}, ควบคู่กับค่าที่มีอยู่ {donation}, {subtitle}, และ {meta} เส้นทางซ้อนแยกตัวพิมพ์ใหญ่เล็ก ค่าที่ขาดแสดงว่าง และห้ามไล่ผ่าน prototype

Webhook ร้านค้าครีเอเตอร์และโอเวอร์เลย์โปรโมต

การชำระ Donation สาธารณะของ Ko-fi คง hasDonation และได้รับค่า USD donoValue การชำระค่าสมัครสมาชิกใช้ new_subscriber หรือ resub, โดยระบุระดับใน membership Shop Order และ Commission ใช้ purchase โดยไม่มีค่าบริจาค ยังคงไม่รวมอีเวนต์ Ko-fi ส่วนตัว JSON ที่เข้ารหัสฟอร์มถอดรหัสหนึ่งครั้ง ชื่อและข้อความเป็นข้อความธรรมดา

Buy Me a Coffee donation.created คงการสนับสนุนทางเงิน; extra_purchase.created และ commission_order.created กลายเป็น purchase. wishlist_payment.created กลายเป็น giftcontribution โดยใช้เฉพาะยอดชำระนั้น; meta.commerce.completed บันทึกแฟล็กสำเร็จของผู้ให้บริการโดยไม่ส่งแถวเงินอีกครั้ง membership.started กลายเป็น new_subscriber พร้อมระดับใน membership, เลิกใช้ผิดวัตถุประสงค์สำหรับ hasDonation สำหรับชื่อระดับ ยอดตอนเริ่มสมัครสมาชิกไม่ถือเป็นการเรียกเก็บที่ชำระแล้วแยกอีกครั้ง อีเวนต์ทดสอบ คืนเงิน ล้มเหลว และการอัปเดต/วงจรสถานะที่ไม่รองรับไม่สร้างการแจ้งเตือนชำระเงิน ไม่รวมหมายเหตุผู้สนับสนุนที่ซ่อนไว้

Fourthwall รองรับ ORDER_PLACED (purchase), GIFT_PURCHASE (gift, recipient other), DONATION (แถวบริจาคปกติ) และ SUBSCRIPTION_PURCHASED (new_subscriber) ยอดคำสั่งซื้อเดิมยังคง hasDonation เพื่อความเข้ากันได้ย้อนหลัง โดยระบุว่า meta.commerce.legacyDonationValue: true; เป็นข้อยกเว้นชัดเจนจากค่าเริ่มต้นใหม่สำหรับการขายสินค้า คำสั่งซื้อที่ใช้บัตรของขวัญส่งการแจ้งเตือนซื้อโดยไม่มีค่าบริจาค เพราะอนุมานยอดเรียกเก็บใหม่จากยอดคำสั่งซื้อไม่ได้อย่างน่าเชื่อถือ และนับการซื้อของขวัญไปแล้ว ไม่ใช้ชื่อเรียกเก็บเงินและอีเมลเป็นตัวตนสาธารณะ อีเวนต์ทดสอบจากแดชบอร์ดและการอัปเดตคำสั่งซื้อไม่สร้างการแจ้งเตือนชำระเงิน

อะแดปเตอร์เหล่านี้คงการส่งต่อ การกระทำบอต Event Flow และการเลือกเส้นทางปลายทางเดิม พร้อม meta.webhookId การตัดรายการซ้ำ โดยให้ชื่อสาธารณะ ข้อความธรรมดา และชื่อสินค้าที่ทราบใน subtitle, และค่า ISO meta.commerce.currency ควบคู่กับค่าบริจาคแบบตัวเลขเมื่อเกี่ยวข้อง ไม่เพิ่มระบบบัญชีคืนเงินหรือการยืนยันตัวตนตัวรับใหม่ ให้ใช้เส้นทาง webhook เดิมที่ตั้งค่าของผู้ให้บริการ

meta.monetization.commerce ใน monetization_update มี enabled, qr, position, display (first/cycle), seconds และอาร์เรย์ items สาธารณะ แต่ละรายการมี name, url, image, amount หากทราบ (null เมื่อไม่ทราบ), currency และ purpose (shop/gift/support/membership) เป็นรายละเอียดโปรโมตที่ผู้ดำเนินรายการป้อน ไม่ใช่หลักฐานชำระเงิน การเพิ่มหรือแก้ไขรายการไม่ส่งอีเวนต์บริจาคหรือซื้อ โอเวอร์เลย์ทั่วไปใช้ mode=commerce; view=both|showcase|card|alerts แยกการโปรโมตจากกิจกรรม พารามิเตอร์ URL เพิ่มเติม style, scale, cardevery, cardfor และ onlytype ควบคุมการแสดงผล โหมดผู้ให้บริการเดิมยังรับตัวควบคุม view และกำหนดเวลา ดู คู่มือตั้งค่า.

อีเวนต์ของขวัญ Throne

การเชื่อมต่อ Monetization ที่เลือกเปิดใช้ส่งต่ออีเวนต์ Throne ที่ลงลายเซ็นพร้อม platform และ type ตั้งเป็น throne ทั้งสามใช้ค่าการส่งที่คงที่ id, ข้อความธรรมดา chatname, chatmessage พร้อม textonly: true, ชื่อสินค้าใน subtitle, และภาพย่อ HTTPS เพิ่มเติมใน contentimg.

อีเวนต์ความหมายยอดบริจาค / อันดับ
giftของขวัญที่ซื้อแล้วhasDonation และค่า USD donoValue; อันดับของขวัญ +1
giftcontributionการร่วมสมทบสำหรับของขวัญเฉพาะยอดร่วมสนับสนุน ไม่เพิ่มอันดับ
giftfundedของขวัญระดมทุนสำเร็จไม่มี hasDonation หรือ donoValue, ป้องกันการนับการสนับสนุนก่อนหน้าซ้ำ; อันดับของขวัญ +1

meta.throne มี itemName, creator (ชื่อผู้ใช้สาธารณะ), completed, currency และค่าในหน่วยหลัก amount สำหรับ giftfunded, ยอดเงินอธิบายเป้าหมาย ไม่ใช่รายได้ใหม่ ผู้ให้ของขวัญนิรนามยังคงเป็น Anonymous; ของขวัญชุมชนที่สำเร็จใช้ Community ไม่ส่งต่อช่องข้อมูลชำระเงินและจัดส่งส่วนตัว

monetization_update ภาพข้อมูลมีเพิ่มด้วย meta.monetization.throne: enabled, username, url, qr, position, rank, และ gifts ภาพข้อมูลเหล่านี้ไม่มี URL ของ webhook หรือข้อมูลรับรองการรับฟัง

คำสั่งเสียงผู้ดำเนินรายการ (พรีวิวเดสก์ท็อป)

ส่วน Event Flow เมื่อฉันพูดว่า... ตัวเรียกรับคำสั่งไมโครโฟนในเครื่องที่เชื่อถือได้จาก SSApp บริบทการกระทำภายในใช้ chatname: "Host", type: "hostvoice", วลีที่รู้จำได้ใน chatmessage, และ textonly: true ไม่ใช่อีเวนต์แพลตฟอร์มขาเข้าหรือช่องทางรับส่งแชตใหม่ การส่งช่องเหล่านี้ผ่านแชตไม่เรียกตัวเรียกเสียง

ต้องใช้แอปเดสก์ท็อปที่อัปเดต เริ่มไมโครโฟนอย่างชัดเจน และเปิดการกระทำหลังโหมด Test ดู การตั้งค่าพรีวิวและสถานะตรวจยืนยัน.

การควบคุมการแสดงสินค้า

ที่มีอยู่ monetization_update ภาพข้อมูลอาจรวม meta.monetization.commerce.live: null เพื่อใช้กำหนดการที่บันทึกไว้ หรือ {mode: "show" | "hide", url?: "https://...", until: 0 | epochMilliseconds} Show จับคู่ URL สินค้าที่บันทึกไว้แบบตรงตัว หากไม่มีสินค้าจะไม่แสดงการ์ด ค่า until ที่เป็นบวกจะหมดอายุและกลับสู่กำหนดการที่บันทึกไว้ ค่าเป็นศูนย์คงอยู่จนเปลี่ยนหรือ SSN เริ่มใหม่ Hide ระงับการโปรโมต ไม่ใช่การแจ้งเตือนกิจกรรมที่ชำระเงิน

commerce.viewerURL เป็น URL ร้านค้าแบบอ่านอย่างเดียวที่เผยแพร่ หรือสตริงว่าง เมื่อมี QR โปรโมตจะลิงก์ไปที่นั่น ไม่มีเซสชัน SSN หรือคีย์เผยแพร่ สินค้ายังคงอยู่ใน commerce.items ส่วนควบคุมแสดงผล การนำเข้า หรือการเผยแพร่ไม่ส่งอีเวนต์บริจาค/ซื้อ ดู การควบคุมสินค้า สำหรับใช้กับ Event Flow และ API ระยะไกล

ส่วน Event Flow commerceControl การกระทำรอคำตอบโดยตรง/Chrome (สูงสุดแปดวินาที) สำหรับข้อมูลอีเวนต์ทั่วไป จะคงอีเวนต์และเพิ่ม meta.commerceControlResult: {success: true, commerce: controlState} หรือ {success: false, error: "..."} สำหรับค่าตัวเลข อาร์เรย์ หรือค่าอื่นที่ไม่ใช่ออบเจ็กต์ที่มีอยู่ใน meta, เมทาดาทาไม่เปลี่ยน และส่งข้อมูลวินิจฉัยกลับเป็น commerceControlResult ในผลการกระทำแทน การควบคุมที่ล้มเหลวหยุดการกระทำถัดไปในสายเดียวกันโดยไม่ระงับอีเวนต์ชำระเงินต้นฉบับ การหมดเวลาไม่ได้ยืนยันว่าการควบคุมไม่มีผล ตรวจสถานะก่อนลองคำสั่งแบบอ้างอิงค่าปัจจุบัน เช่น Next ซ้ำ ความสำเร็จยืนยันสถานะเลือก/ซ่อน/กำหนดเวลาในเครื่อง ไม่เคยยืนยันการมองเห็นใน OBS หรือการซิงก์หน้าสาธารณะ

ขั้นตอนงาน Stream Deck / API แบบมีชื่อ

ส่วน ตัวเรียกขั้นตอนงานแบบมีชื่อ สร้างข้อความ Event Flow ภายในพร้อม type: "api", event: "workflow_trigger", chatname: "Stream Deck / API", ค่าว่างของ chatmessage, และ textonly: true ส่วนค่าของมัน meta.workflow ออบเจ็กต์มีชื่อตัวเรียกและ JSON ที่ผู้เรียกให้มา data ออบเจ็กต์ อ่านค่าผ่านเทมเพลต เช่น {meta.workflow.data.minutes} ประเมินเฉพาะโฟลว์ที่บันทึกและเปิดใช้ซึ่งตรงกับตัวเรียกนั้นอย่างชัดเจน ไม่ใช่อีเวนต์ผู้ชม/แชตขาเข้าและไม่เผยแพร่เป็นแชต การคัดลอกช่องเหล่านี้เข้าแชตไม่ทำให้ตัวเรียกที่ระบุชื่อทำงาน

รุ่นนำร่องผู้ชม NinjaChatter

ตัวเชื่อมต่อส่วนขยายแบบจับคู่รุ่นทดลองส่งแถวสำหรับแสดงผลเท่านั้นพร้อม type: socialstreamchat, platform: ninjachatter, และ textonly: true. meta.ninjachatter มีค่า origin: audience, ข้อมูลเชิงบรรยาย provider, และค่าสาธารณะ room ID แถวเหล่านี้ข้ามการตอบแพลตฟอร์ม บอต ตัวเรียก Event Flow และแต้ม ผู้ให้บริการที่แสดงไม่ได้หมายถึงการอนุญาต การจับแหล่ง NinjaChatter แบบเดิมรวม meta.ninjachatter.room สำหรับตัดรายการซ้ำเฉพาะห้อง

Cheer ใช้เส้นทางรับสิทธิ์และผลลัพธ์แยกที่ยืนยันตัวตน ไม่ใช้คำสั่งแชตพิเศษ ค่าที่ตั้งไว้แบบคงที่ส่งอีเวนต์โอเวอร์เลย์ Actions เดิม show_text ข้อความนานสามวินาที การรับหมายถึงช่องทางยอมรับ ไม่ได้ยืนยันการแสดงใน OBS ข้อมูลผู้ชมไม่สามารถเลือกการกระทำตามอำเภอใจ รุ่นนำร่องปิดอยู่ตามค่าเริ่มต้นใน NinjaChatter ส่วน Electron คงรีเลย์เดิมจนกว่าจะยืนยันความพร้อมของขอบเขตจับคู่ส่วนตัวใหม่

กระดานช่องการค้าและการขายล่าสุด

ตัวเดิม monetization_update อีเวนต์ (type/platform: socialstream) ยังรวม meta.monetization.boards ส่วนค่าของมัน board มี title, style (spots/teams), columns (1–20), visible, และสูงสุด 120 รายการของ spots แต่ละช่องมีค่าสตริง id, ข้อความธรรมดา label, status (available/claimed/revealed) และ result (ข้อความธรรมดา ว่างจนกว่าจะเปิดเผย) การจองและเปิดเผยเป็นสถานะแสดงผลที่ผู้ดำเนินรายการป้อน ไม่ใช่หลักฐานซื้อหรือการจัดสรรแบบสุ่ม

boards.sales เก็บระเบียนล่าสุดสูงสุด 100 รายการ: id, title, ตัวเลือกเพิ่มเติม amount (null เมื่อไม่ทราบ), currency, quantity, source, และ at (มิลลิวินาที Unix เมื่อบันทึก) automatic เลือกเปิดการรวบรวม, salesVisible ควบคุมการแสดงและ revision เพิ่มเมื่อเปลี่ยน การรวบรวมอัตโนมัติรับเฉพาะ purchase อีเวนต์จาก Shopify, ผู้ขาย eBay, Fourthwall, Ko-fi และ Buy Me a Coffee ไม่รวมอีเวนต์ส่วนตัว/ทดสอบ ไม่ถือเมทาดาทาประมูล ทิป ของขวัญ หรือการจองช่องเป็นการซื้อ ระเบียนอัตโนมัติไม่ใช้ยอดคำสั่งซื้อ ราคาประกาศขาย หรือยอดบริจาคแทนราคาสินค้า ระเบียนที่ป้อนเองใช้ source: "Host confirmed".

สถานะคงอยู่ในพื้นที่เก็บข้อมูลสร้างรายได้ส่วนตัวของการติดตั้งนี้ ภาพข้อมูลสาธารณะไม่รวมรหัสตัดการส่งซ้ำ ตัวตนผู้ซื้อ และข้อมูลลับ การขายที่แสดงอย่างชัดเจนเก็บรหัสอีเวนต์ไว้เพื่อนำออก การคืนเงินต้องให้ผู้ดำเนินรายการนำออก รหัสซื้อซ้ำถูกจำแยกไว้ (สูงสุด 2,000) แม้ล้างประวัติที่แสดงแล้ว ส่วนเดิม getCommerceState คำตอบรวม commerce.boards; commerceControl รับคำสั่งกระดาน/การขายที่อธิบายไว้ใน คู่มือกระดาน การแก้ไขด้วยตนเองเผยแพร่สถานะที่อัปเดต แต่ไม่สร้างอีเวนต์ซื้อ ยอดบริจาค หรือรางวัลแบบเสียเงิน โอเวอร์เลย์ซ่อนเมื่อไม่มีภาพข้อมูลจากผู้ดำเนินรายการนาน 35 วินาที

ส่วนเพิ่มของขั้นตอนผู้ขาย: commerce.boards.board.id ระบุรุ่นของกระดาน การสั่งด้วยตนเอง saleAdd อาจให้ค่า boardId และ spotId เพื่อบันทึกการขายและจองช่องนั้นเป็นการทำงานเดียวกัน การขายเชื่อมโยงซ้ำที่ยังอยู่ในประวัติล่าสุดจะถูกปฏิเสธ saleRemove พร้อม reopenSpot: true คืนช่องนั้นให้ว่างเฉพาะเมื่อรุ่นกระดานยังตรงกัน รายการขายสาธารณะไม่ใส่ช่องเชื่อมโยงสำหรับผู้ดำเนินการเหล่านี้ ตัวเลือกเพิ่มเติม platform ในการขายที่ป้อนเองคงแหล่งข้อมูลไว้สำหรับกรอง ส่วน source: "Host confirmed" ระบุวิธียืนยัน amount เป็นยอดรวมของรายการ รวมค่า quantity ค่าของอะแดปเตอร์คำสั่งซื้อที่ชำระแล้วของ eBay meta.ebayPurchase.quantity คงไว้

salesSettings.auctionSource เลือกเปิดตัวช่วยสินค้า Whatnot หรือ eBay Live ค่าของคำตอบควบคุม commerce.auction มีเพียง source, title, priceText, status และ at จากข้อมูลล่าสุดที่จับได้ auction_update, หรือ null หมดอายุหลังห้านาที และล้างเมื่อเปลี่ยนแหล่งข้อมูล ได้รับภาพข้อมูลว่าง หรือเริ่มใหม่ ตัวช่วยมีให้เฉพาะผู้ดำเนินการ ไม่บันทึกถาวรและไม่รวมในการเผยแพร่ให้ผู้ชม โดยทิ้งตัวตนผู้เสนอราคา/ผู้ชนะ สคริปต์แหล่งข้อมูลและข้อมูลอีเวนต์ประมูลไม่เปลี่ยน การคัดลอกร่างไม่ได้ยืนยันการชำระเงินหรือสร้างรายการขาย
