Importante: La disponibilidad de eventos depende de la fuente, los permisos y los ajustes de captura. Para ocultar filas marcadas como eventos en el Dock o superposiciones de destacados, añade &hideevents o &hideallevents. Para ocultar eventos seleccionados, usa &filterevents=subscription_gift,new_follower,gifted. Estos filtros también pueden ocultar filas de pago que tengan un event; los filtros de eventos no coinciden con filas normales de donación sin marcador de evento. Los demás filtros de mensajes siguen aplicándose.
Elige el método de captura: Para YouTube, Twitch y Kick, Modo WebSocket suele proporcionar una cobertura más amplia de eventos. La captura Standard del DOM lee las filas y tarjetas realmente renderizadas en la página. Los Super Chats, Super Stickers y regalos Jewel de YouTube tienen rutas de captura en ambos modos; otros eventos de regalos, propinas y membresías varían según la fuente. Consulta las tablas de plataformas para ver las rutas compatibles y los ajustes necesarios.
¿Creas automatizaciones? Consulta la Guía de Event Flow para aprender a usar estos datos de eventos en disparadores, alertas y flujos personalizados. La guía incluye una Referencia de variables de plantilla para dar formato al texto. Para importes de regalos, recuento de rachas y ejemplos de juegos editables, consulta Crear juegos y recompensas.
Estructura de datos: Las filas de chat con donaciones deben usar hasDonation y el opcional donoValue. No establezcas event: "donation" solo porque una fila normal de chat/propina tenga valor; usa nombres específicos de eventos solo para acciones reales de plataforma o tipos de artículos pagados, como superchat, supersticker, gift, o jeweldonation. Usa meta solo para datos estructurados adicionales que los consumidores necesiten y que los campos existentes no cubran.

Resumen de campos

data aquí significa el objeto del mensaje, no una envoltura adicional que haya que añadir. Las filas de chat y los eventos solo de metadatos tienen estructuras distintas: los contadores e instantáneas de estado pueden omitir chatname/chatmessage. En las tablas de plataformas, mensaje describe una fila normal de chat, no un valor literal event: "message".

Campo Estructura Uso
data.type cadena Identificador de fuente usado por superposiciones, filtros y Event Flow. Instagram mantiene el chat en vivo como instagramlive y los comentarios fuera de directo como instagram. Consulta la Guía de tipos de fuentes para variantes, fuentes genéricas y enrutamiento saliente.
data.chatname cadena Nombre visible proporcionado por la fuente y usado por el procesamiento de mensajes y las salidas ajenas a las superposiciones. Un alias de nombre visible configurado solo puede sustituir este valor en copias de datos de transporte del Dock y superposiciones.
data.username cadena Nombre de usuario de origen cuando está disponible. Los datos de Dock o superposición con alias pueden añadir este campo para conservar el original chatname para acciones de usuario; el mensaje canónico no cambia.
data.userid cadena Identificador de usuario específico de la plataforma. Las acciones de usuario prefieren este valor a username y chatname.
data.platformcadena (opcional)Algunas integraciones lo incluyen junto con type. Muchos adaptadores de fuentes lo omiten; usa type para el enrutamiento de fuentes.
data.idcadena | número (opcional)Identificador del mensaje o evento. Su significado depende de la fuente y el transporte; no supongas que siempre es un ID nativo de moderación de la plataforma. Usa meta.messageId cuando el adaptador lo expone para sincronizar eliminaciones.
data.donoValuenúmero (opcional)Equivalente numérico en USD proporcionado por la fuente, incluidas estimaciones. Un valor válido (incluido cero) tiene prioridad sobre la conversión de currency.js. Sin él, los consumidores estiman USD a partir de hasDonation y el contexto de la fuente. Los importes y unidades originales permanecen en hasDonation y en los metadatos existentes del proveedor.
data.chatbadgesmatriz | cadena (opcional)URL de imágenes de insignias u objetos de insignia (type: "img" con src, type: "svg" con html, o type: "text" con text). El relé conserva la etiqueta literal de una insignia de texto en el campo opcional rawText y produce contenido escapado en text para superposiciones antiguas. En pasadas posteriores de reenvío, regenera text desde rawText; no escapes text de nuevo. Los renderizadores actuales muestran rawText literalmente cuando esté presente y conserva el manejo heredado de texto codificado en caso contrario. Es un campo de representación, no permiso para renderizar HTML. Las fuentes antiguas pueden enviar una sola cadena HTML en lugar de una matriz. Las superposiciones que renderizan insignias aceptan ambos formatos y sanean localmente el HTML y las URL de insignias, incluso si el emisor es una extensión antigua. Las insignias inválidas no deben impedir que aparezca el mensaje de chat o membresía.
data.event cadena | booleano Identificador de actividad del sistema (por ejemplo viewer_update, subscription_gift, giftpurchase). El chat normal debe dejarlo vacío/false para que las superposiciones distingan los avisos del sistema del texto de conversación.
data.chatmessage cadena Cuerpo del mensaje. Puede contener HTML saneado/renderizable solo cuando data.textonly es false.
data.textonly booleano Solo se aplica a data.chatmessage. true significa renderizar chatmessage como texto sin formato, conservando etiquetas literales y texto que parezca entidades; no decodifiques, sanees como HTML ni añadas etiquetas de formato a ese cuerpo. Aplica el estilo del evento al elemento mostrado. false significa chatmessage puede contener HTML saneado/renderizable; los mensajes antiguos sin el indicador conservan ese comportamiento HTML. Los demás campos normales son texto sin formato, excepto campos multimedia como chatimg y contentimg. Muestra los campos de texto sin formato con textContent, o escápalos una vez al construir una plantilla HTML; no elimines ni decodifiques repetidamente su contenido.
data.contentimg cadena (opcional) Imagen de contenido o URL multimedia compatible. En la extensión y la aplicación de escritorio, la opción allowExternalGifs el ajuste rellena un campo vacío con el primer enlace GIF HTTP(S) directo del texto del mensaje o de un enlace HTML. La ruta de la URL debe terminar en .gif (sin distinguir mayúsculas y minúsculas); se conservan los parámetros de consulta y fragmentos. No requiere clave API, conserva chatmessage y los adjuntos existentes, y respeta removeContentImage. El opcional hideExternalGifUrl el ajuste añade meta.hideExternalGifUrl: true; el Dock y la superposición de destacados ocultan después el enlace del GIF correspondiente solo cuando carga su imagen, conservando el texto circundante y los datos originales. Las imágenes fallidas o agotadas ocultan su contenedor de adjuntos y dejan visible el enlace. La superposición solo de GIF intenta mostrar directamente la imagen si falla la obtención de sus bytes y usa el tiempo de visualización configurado si no conoce la duración de la animación; las cargas fallidas o bloqueadas hacen avanzar la cola. No añade un event o cambia la fuente type. Las imágenes externas no pasan filtros de contenido y pueden no cargar si el alojamiento bloquea la inserción.
data.membership cadena Estado legible de membresía, como MEMBERSHIP, new_sponsor, gift_recipient. Las interfaces lo usan para insignias, filtros y anuncios.
data.subtitle cadena Descripción complementaria (antigüedad de membresía, mejoras de nivel, regalado por…). Mantenla breve y como texto sin formato para que las superposiciones puedan colocarla debajo del nombre visible.
data.hasDonation cadena Importe monetario o de regalo virtual ($5.00, 500 bits, 300 coins). Rellénalo incluso cuando data.event está vacío para que las superposiciones de donaciones lo detecten.
data.meta número | objeto | cadena (heredado) Usa enteros simples para contadores individuales (espectadores, seguidores, suscriptores) y objetos para contexto más completo. Algunos eventos antiguos, como el del DOM de Twitch community_highlight, contienen una cadena. Comprueba la estructura específica del evento antes de leer propiedades de objeto; los nuevos detalles estructurados pertenecen a un objeto.
data.firsttime booleano Establecer en true cuando la detección de primera intervención y la base de datos local están habilitadas, y este es el primer mensaje guardado de ese usuario/fuente. El Dock lo usa para destacar primeras intervenciones y filtrar sus pitidos; el ajuste opcional de insignia de primera intervención antepone una hoja a chatbadges.
data.lastactivity número Marca de tiempo Unix en segundos de la actividad de chat anterior guardada de ese usuario, cuando están habilitadas la detección de primera intervención y la base de datos local. Se omite para usuarios nuevos.

El transporte de control de superposiciones es independiente del chat/eventos capturados. Los receptores actualizados usan un ssnControl envoltura que contiene un identificador de entrega id, función target, canal de respuesta opcional e ID de cliente de instantánea. Los cuerpos de funciones existentes se mantienen. Los controles públicos de funciones usan el canal 7; Actions conserva el canal 6. El estado de Encuesta y Mapa incluye un valor del anfitrión epoch, revision y reset marcador; Timer, Ticker y Spotify usan ssnState con una época y una revisión. Estos marcadores describen el estado del anfitrión, no un historial restaurado de votos/chat. Las fuentes no deben añadir campos de la envoltura de control a mensajes capturados. Un acuse de recibo no establece que la acción se haya completado ni que sea visible en OBS. Consulta la estado de migración para funciones compatibles, negociación de respuestas y límites de reconexión.

Phrase Guess usa el nativo {response: text} solicitud para respuestas de chat por server2 y {action: "phraseGuessResponse", value: {type: "bot", chatname: name, chatmessage: text}} para anuncios solo en el Dock. El anfitrión debe habilitar mensajes entrantes de server3; desactivar el control del anfitrión sigue bloqueando estas solicitudes. Los anuncios del Dock se reenvían como filas normales de chat de bot con textonly: true, sin enviarlos a las entradas de chat de las fuentes de captura. El modo API heredado conserva su formato de comandos existente.

Convenciones de meta

Para mantener coherentes los paneles y automatizaciones, sigue estas convenciones al ampliar data.meta:

  • viewer_update, follower_update, subscriber_update, y likes_update usa un entero simple meta valor. likes_update es un total oficial de la plataforma: los consumidores deben establecer el valor mostrado en lugar de sumarlo. El script en segundo plano agrega los recuentos de espectadores en viewer_updates con un objeto cuyas claves son data.type.
  • giveaway_state es una instantánea solo de metadatos generada por el anfitrión para visualizaciones gestionadas. meta.giveaway la versión 2 incluye giveawayId, persistente roundId/epoch, aumentando generation entre rondas nuevas, revision dentro de una ronda, status, open, draw, keyword, count, ticketCount, congelado config, hasta 120 elementos de vista previa entrants, y los últimos 20 winners. Las entradas exponen id, name, platform y tickets; los ganadores añaden drawnAt y el valor concedido points. Coin Flip Pot añade outcome; Number Hunt añade number con el público low, high y los recientes guesses, nunca el secreto. Los consumidores filtran por ID del sorteo y descartan generaciones/revisiones anteriores. Son muestras para visualización, no un registro completo de boletos ni una instrucción de pago. Las claves de monedero, saldos y reservas no aparecen en las instantáneas para el público. El anfitrión publica en el giveaway etiqueta P2P y flujos WebSocket de superposiciones habilitados; esto no implica visibilidad en OBS. Guía.
  • meta.giveawayControlResult contiene el resultado de una acción de sorteo de Event Flow (ok, opcional error, giveaway o simulated). meta.giveawayHandled enumera los ID de sorteos ya procesados por una acción de entrada/compra del flujo para que el comando automático de chat no pueda cobrarlos de nuevo. El editor añade meta.economyTest para acciones de sorteo simuladas; no es un evento de plataforma ni una credencial de autorización.
  • video_stats usa un objeto estructurado meta objeto para el estado del codificador/servidor externo, incluido provider, label, online, bitrateKbps, rttMs, bufferMs, contadores de pérdida/descarte de paquetes y detalles opcionales del códec.
  • Los eventos de tipo donación pueden incluir un objeto descriptivo: por ejemplo { amount, currency, supporter } para Kick, { bits } para Cheers de Twitch. Los eventos de membresía tienen sus propios metadatos específicos de fuente; no son automáticamente donaciones monetarias.
  • Los mensajes normalizados de webhooks de Stripe, Ko-fi, Buy Me a Coffee y Fourthwall incluyen un valor por proveedor meta.webhookId, copiado del identificador estable de evento del proveedor, para que las páginas receptoras puedan eliminar duplicados de reintentos y transportes mixtos.
  • Las raids de Twitch transmiten { fromId, fromLogin, viewers }. Otras fuentes difieren: Whatnot usa meta.numRaiders, mientras SharePlay usa el opcional meta.fromLogin/meta.viewers. Revisa la fila específica de la fuente antes de leer los metadatos de raids.
  • Los canjes de recompensas de EventSub de Twitch exponen meta.rewardId, cost, rewardTitle, redemptionId, y un campo heredado alias junto con el mensaje preparado. Las tarjetas de recompensas del DOM y otras fuentes pueden proporcionar menos campos o campos distintos.
  • user_banned contiene solo metadatos para widgets de moderación. Omite deliberadamente chatname y chatmessage; usa meta.username, meta.displayName, meta.avatarUrl, y meta.profileUrl.
  • Los transportes de chat que admitan sincronización de eliminaciones desde el control de fuentes deben exponer el identificador nativo de chat como meta.messageId en lugar de depender del campo interno del Dock data-mid valor.
  • Las eliminaciones de origen usan {delete: {type, id}} para un ID conocido de mensaje del Dock, o {delete: {type, meta: {messageId}}} para un ID nativo de mensaje de plataforma. Un ID conocido elimina solo los mensajes coincidentes. Cuando solo se conoce el usuario objetivo, envía {delete: {type, userid}} o {delete: {type, chatname}} para eliminar los mensajes de ese usuario de esa plataforma. Nunca sustituyas la identidad del usuario objetivo por la del moderador. Las eliminaciones entrantes no requieren el ajuste opcional de sincronización de moderación del Dock a la plataforma.
  • Los metadatos de identidad de fuente de SSApp pueden añadir meta.ssnAccountRole, meta.ssnSourceId, y meta.ssnSession cuando una fuente tiene asignado un rol de cuenta distinto del normal.
  • Event Flow puede solicitar un destacado estableciendo meta.featured = true en los datos de chat, lo que destaca automáticamente el mensaje en el Dock/superposiciones de destacados.
  • AI Event Overlay: la acción showAiEventOverlay envía una copia del mensaje que la activó a la etiqueta aievent-CONFIGURATION_ID, añadiendo meta.aiEventOverlay: {profile: "CONFIGURATION_ID"}. Se conservan los campos existentes del mensaje y los metadatos que sean objetos; los metadatos escalares se conservan como meta.value. Se trata de una entrega a un destino específico, no de un nuevo evento de la plataforma. El mensaje original no se modifica. Consulta la guía de configuración.
  • Opcional meta.aiEventOverlay.variation selecciona una frase exacta aprobada en la configuración guardada del overlay. El texto del espectador y los metadatos rellenan los campos de la plantilla después de generarla.
  • Las solicitudes de visualización de AI Event Overlay requieren un perfil y su token privado de visualización. La configuración y las claves API se gestionan únicamente desde la ventana emergente local de SSN. Las respuestas usan {aiEventResponse: {target, value}} o {aiEventResponse: {target, error}}. Los resultados generados contienen template, duration, warnings, y URL de datos multimedia opcionales en image/audio.
  • Las recompensas de overlays de IA pagadas con puntos usan aiEventPresentation (id, profile, expiresAt, result, message) y confirman la recepción con aiEventDelivered (ID de entrega). Los registros de cargos y los importes de reembolso permanecen en el anfitrión.
  • Event Flow puede solicitar fijar en el Dock estableciendo meta.pinned = true; opcional meta.pinnedTarget limita ese mensaje fijado a un Dock con el correspondiente label.
  • La impresión térmica de Event Flow registra su resultado bajo meta.thermalPrintResult (success y el opcional code/error), conservando el evento de chat y los demás metadatos. Para eventos con metadatos numéricos o de otro tipo no objeto, el diagnóstico queda en el resultado de la acción y el evento no cambia.
  • Recompensas opcionales de pegatinas de SSN: event: "sticker" se envía solo al stickers etiqueta de superposición tras descontar puntos de fidelidad. Establece platform y type al campo del mensaje de origen type, y conserva chatname, con vacío chatmessage, textonly: true, y contentimg que contiene una ruta relativa de imagen incluida o una URL multimedia HTTPS aprobada por el anfitrión. meta.sticker contiene id, pack, name, cost, duration (segundos), motion, redemptionId, y expiresAt (milisegundos Unix). Es una recompensa de SSN, no una donación de plataforma ni un evento nativo de puntos del canal. Consulta la galería y guía de configuración.
  • El reproductor de pegatinas devuelve un paquete de control {action: "stickerReceipt", meta: {sticker: {redemptionId, success}}} a su remitente cuando carga la imagen o falla. Solo los acuses de recibo de un stickers par resuelven un canje pendiente. Una entrega fallida o sin confirmar provoca un reembolso; este paquete de control no es un evento de chat. Se recomienda una sola visualización activa de pegatinas por sesión.
  • Los comandos de superposición de escenario de IA usan { action: "aiOverlay", target, meta } o la reproducción del copresentador controlada desde el Dock usa { action: "cohostOverlay", target, meta }; conserva todos los detalles del comando, como command, text, emotion, avatar, y tts dentro de meta.
  • Si una plataforma expone varios contadores juntos, prefiere un objeto estructurado con claves explícitas (meta.viewer_count, meta.follower_count) en lugar de sobrecargar cadenas de texto.
  • Las superposiciones de comercio deben usar objetos de instantánea bajo meta (por ejemplo auction_update y commerce_update) y evita campos improvisados de nivel superior.

Cobertura de plataformas

YouTube – Captura Standard del DOM

Implementación: sources/youtube.js

  • Mantén abierta la pestaña de chat en vivo. La captura lee las tarjetas de membresía y regalo renderizadas en esa sesión; no requiere que el espectador sea el propietario o moderador del canal. El acceso de cuenta y la vista de chat seleccionada pueden afectar a las filas visibles.
  • Al abrir la superposición de número de espectadores y actividad del chat con los espectadores visibles, se solicitan automáticamente los recuentos de espectadores. Las opciones Mostrar recuento de espectadores y Seguir a los participantes activos del chat también activan la recopilación de datos.

Alertas de suscriptores de YouTube (new_follower)

Social Stream ahora puede detectar nuevos suscriptores de YouTube usando el myRecentSubscribers punto de acceso de API. Funciona de forma similar a las alertas de suscriptores de Streamlabs.

Cómo funciona:

  • Consulta la API de YouTube cada 5 minutos para obtener suscriptores recientes
  • Registra los suscriptores vistos en localStorage para detectar los nuevos
  • Emite new_follower eventos con el nombre del suscriptor, avatar e ID del canal
  • Mantiene desactivados por defecto los mensajes de alertas de suscriptores; al activarlos usa la cadena de traducción actual de alert-just-subscribed
  • Agrupa por defecto ráfagas de más de tres nuevos suscriptores para que las reconexiones no saturen las superposiciones o Event Flow
  • Requiere activar el modo WebSocket en los ajustes de la extensión

Limitaciones (son restricciones de la API de YouTube, no de Social Stream):

  • Sin demora de entrega garantizada – SSN consulta cada cinco minutos, pero la API puede devolver resultados retrasados o incompletos. No dependas de una ventana fija de cuatro horas.
  • Solo suscripciones públicas – Los suscriptores que hayan configurado su lista de suscripciones como privada no activarán alertas. En YouTube las suscripciones son privadas por defecto.
  • Solo el propietario del canal – Solo puedes recibir alertas de suscriptores de canales que te pertenezcan y en los que estés autenticado.
  • Uso de cuota de API – Cada consulta cuesta 1 unidad de API. A intervalos de 5 minutos, se usan aproximadamente 288 unidades al día (de la cuota predeterminada de 10 000).

Las propinas de NinjaBacker usan platform: "ninjabacker", type: "ninjabacker", chatname, texto sin formato chatmessage, textonly: true, un campo con prefijo de fuente id, formateado hasDonation, y el campo numérico donoValue. chatname es Anonymous; se excluyen campos del cliente, notas privadas y URL de pedidos. chatmessage es texto sin formato con textonly: true; subtitle contiene hasta tres títulos públicos de productos. meta.commerce contiene orderTotal y currency en la moneda de la tienda, más quantity cuando se conoce un recuento completo válido. No se establecen el destinatario ni la finalidad física/digital. Sin hasDonation o donoValue está establecido. id es un hash opaco estable asociado a tienda/pedido con prefijo de Shopify; no es un identificador de pedido original.

Las compras usan las rutas existentes de actividad, la categoría Compra de multi-alerts y Event Flow. La promoción de productos usa el existente meta.monetization.commerce catálogo. Importar un producto o establecer su etiqueta promocional en Regalo no genera un evento de compra o regalo. Configuración y límites de entrega de Shopify.

Regalos y comercio

Usa event: "gift" para un regalo, giftcontribution para apoyo pagado destinado a un regalo, giftfunded para completar la financiación, y purchase para una venta de producto. Estos nombres son independientes del proveedor y de si el artículo es físico o digital. Reserva el heredado giftpurchase evento para membresías regaladas; Throne usaba antes ese nombre incorrectamente y ahora emite gift. Los productores de membresías existentes no cambian. Los filtros personalizados de nombres de eventos de Throne deben cambiar a gift; los filtros de donaciones no necesitan cambios.

hasDonation sigue siendo la señal de compatibilidad para apoyo pagado, con donoValue que contiene su valor en USD proporcionado o estimado. Los regalos y aportaciones conservan esos campos. La financiación completada omite ambos para evitar contar aportaciones dos veces. Las ventas normales de productos los omiten por defecto, conservando el contrato de eBay. No deduzcas intención de regalo de una tienda, URL de lista de deseos o artículo físico: una compra para el comprador u otro destinatario sigue siendo una venta salvo que la fuente identifique explícitamente un regalo para el creador.

Campo compartido opcional meta.commerce los campos son recipient (creador, comprador, otro), itemType (físico, digital, servicio), quantity (recuento positivo de artículos), currency (moneda ISO), goalAmount (objetivo de financiación en unidades monetarias principales, nunca ingresos nuevos), y orderTotal (total conocido del pedido pagado en unidades monetarias principales; comercio, no ingresos por donaciones). Omite los detalles desconocidos. Mantén los nombres de artículos en subtitle, imágenes en contentimg, y texto del colaborador en chatmessage. Los metadatos existentes del proveedor siguen disponibles. Throne proporciona destinatario y moneda, además de goalAmount al completarse; eBay proporciona cantidad. Ninguno deduce el tipo de artículo ni expone datos privados del destinatario.

El feed de actividad muestra estos eventos incluso sin texto del colaborador. Multi-alerts usa la presentación de donaciones para regalos y aportaciones, incluido un aviso distinto de Regalo totalmente financiado sin valor monetario. Las compras tienen una categoría Compra independiente, habilitada por defecto, con purchasestyle, purchasesound, purchaseaccent, y disablepurchases controles de URL. Las alertas de compra no cambian los totales de donaciones.

Event Flow ofrece estos nombres en los disparadores Tipo de evento y Otro evento. Los disparadores de Donación siguen inspeccionando hasDonation; los disparadores de Gift Sub conservan la semántica de membresía. Compare Property acepta rutas anidadas como meta.commerce.recipient. Las plantillas de acciones aceptan {meta.commerce.quantity} y {meta.commerce.currency}, junto con los existentes {donation}, {subtitle}, y {meta}. Las rutas anidadas distinguen mayúsculas y minúsculas, los valores ausentes se muestran vacíos y está prohibido recorrer prototipos.

Webhooks de comercio para creadores y superposiciones promocionales

Los pagos públicos Donation de Ko-fi conservan hasDonation y obtienen el valor en USD donoValue. Los pagos de suscripción usan new_subscriber o resub, con el nivel en membership. Shop Order y Commission usan purchase sin valores de donación. Los eventos privados de Ko-fi siguen excluidos. El JSON codificado como formulario se decodifica una vez; los nombres y mensajes son texto sin formato.

Buy Me a Coffee donation.created conserva el apoyo monetario; extra_purchase.created y commission_order.created se convierten en purchase. wishlist_payment.created se convierte en giftcontribution usando solo ese importe de pago; meta.commerce.completed registra el indicador de finalización del proveedor sin emitir otra fila monetaria. membership.started se convierte en new_subscriber con el nivel en membership, sin seguir usando incorrectamente hasDonation para un nombre de nivel. Un importe de inicio de suscripción no se trata por sí solo como un cobro pagado. Los eventos de prueba, reembolso, fallo y actualización/ciclo de vida no compatibles no generan alertas de pago. Se omiten las notas ocultas del colaborador.

Fourthwall admite ORDER_PLACED (purchase), GIFT_PURCHASE (gift, destinatario otro), DONATION (fila normal de donación) y SUBSCRIPTION_PURCHASED (new_subscriber). Los totales de pedidos existentes conservan hasDonation por compatibilidad con versiones anteriores, marcado meta.commerce.legacyDonationValue: true; esta es una excepción explícita a los valores predeterminados de nuevas ventas de productos. Los pedidos con tarjetas de regalo aplicadas emiten una alerta de compra sin valor de donación: no puede deducirse con fiabilidad el nuevo cobro a partir del total del pedido y la compra del regalo ya se contó. Los nombres de facturación y correos electrónicos no se usan como identidad pública. Los eventos de prueba del panel y las actualizaciones de pedidos no generan alertas de pago.

Estos adaptadores conservan el reenvío, las acciones de bot, Event Flow y el enrutamiento de destinos existentes, con meta.webhookId deduplicación. Exponen nombres públicos, mensajes de texto sin formato, nombres conocidos de artículos en subtitle, y la moneda ISO meta.commerce.currency junto con los valores numéricos de donación cuando corresponda. No añaden contabilidad de reembolsos ni autenticación nueva del receptor; usa la ruta de webhook configurada del proveedor.

meta.monetization.commerce en monetization_update contiene enabled, qr, position, display (first/cycle), seconds y una matriz pública items. Cada artículo tiene name, url, image, amount opcional (null si se desconoce), currency y purpose (shop/gift/support/membership). Son detalles promocionales introducidos por el anfitrión, no pruebas de pago. Añadir o editar artículos no emite eventos de donación o compra. La superposición genérica usa mode=commerce; view=both|showcase|card|alerts separa la promoción de la actividad. Los parámetros opcionales de URL style, scale, cardevery, cardfor y onlytype controlan la presentación. Los modos existentes de proveedores también aceptan controles de vista y programación. Consulta la guía de configuración.

El nodo de Event Flow Cuando digo... el disparador recibe comandos de confianza del micrófono local de SSApp. Su contexto interno de acción usa chatname: "Host", type: "hostvoice", la frase reconocida en chatmessage, y textonly: true. Controles de visualización de productos

Existente monetization_update las instantáneas pueden incluir meta.monetization.commerce.live: null para la programación guardada, o {mode: "show" | "hide", url?: "https://...", until: 0 | epochMilliseconds}. Mostrar busca la URL exacta del producto guardado; si falta el producto, no muestra tarjeta. Un until positivo caduca y vuelve a la programación guardada; cero dura hasta que se cambia o se reinicia SSN. Ocultar suprime las promociones, no las alertas de actividad pagada.

commerce.viewerURL es la URL publicada de la tienda de solo lectura, o una cadena vacía. Cuando existe, los códigos QR promocionales enlazan allí. Nunca contiene la sesión de SSN ni la clave de publicación. Los productos permanecen en commerce.items. Los controles de visualización, las importaciones y la publicación no emiten eventos de donación/compra. Consulta Controles de productos para Event Flow y uso de API remota.

El nodo de Event Flow commerceControl la acción espera la respuesta directa/de Chrome (hasta ocho segundos). En datos normales de eventos conserva el evento y añade meta.commerceControlResult: {success: true, commerce: controlState} o {success: false, error: "..."}. Para un valor existente numérico, matriz u otro tipo no objeto de meta, los metadatos no cambian y el diagnóstico se devuelve como commerceControlResult en el resultado de la acción. Los controles fallidos detienen las acciones posteriores de esa cadena sin suprimir el evento de pago original. Un tiempo de espera agotado no demuestra que el control no se aplicó; revisa el estado antes de reintentar un comando relativo como Siguiente. El éxito confirma el estado local seleccionado/oculto/programado, nunca la visibilidad en OBS ni la sincronización de la página pública.

Flujos con nombre de Stream Deck / API

El disparador de flujo con nombre crea un mensaje interno de Event Flow con type: "api", event: "workflow_trigger", chatname: "Stream Deck / API", vacío chatmessage, y textonly: true. Su meta.workflow el objeto contiene el nombre del disparador y un JSON proporcionado por quien llama data objeto. Lee valores mediante plantillas como {meta.workflow.data.minutes}. Solo se evalúan los flujos guardados y habilitados que coincidan explícitamente con ese disparador. No es un evento entrante de espectador/chat y no se emite como chat; copiar estos campos al chat no activa el disparador con nombre.

Piloto de público de NinjaChatter

El conector experimental de extensión emparejada envía filas solo para visualización con type: socialstreamchat, platform: ninjachatter, y textonly: true. meta.ninjachatter contiene origin: audience, el descriptivo provider, y el público room ID. Estas filas omiten respuestas de plataforma, bots, disparadores de Event Flow y puntos. Que se muestre un proveedor no implica autorización. Las capturas heredadas de NinjaChatter incluyen meta.ninjachatter.room para suprimir duplicados de cada sala.

Cheer usa una ruta independiente autenticada de solicitud y resultado, nunca un comando especial de chat. La configuración fija emite el comando existente de la superposición Actions show_text mensaje durante tres segundos. Recibirlo significa aceptación del transporte, no visualización verificada en OBS. Ningún dato del público puede seleccionar acciones arbitrarias. El piloto está deshabilitado por defecto en NinjaChatter; Electron conserva su relé existente hasta que se valide el nuevo límite de emparejamiento privado.

Tableros de plazas comerciales y ventas recientes

El existente monetization_update evento (type/platform: socialstream) también incluye meta.monetization.boards. Su board contiene title, style (plazas/equipos), columns (1–20), visible, y hasta 120 spots. Cada plaza tiene una cadena id, texto sin formato label, status (disponible/reservada/revelada) y result (texto sin formato, vacío hasta revelarse). Las reservas y revelaciones son estados de visualización introducidos por el anfitrión, no pruebas de compra ni asignaciones aleatorias.

boards.sales contiene hasta 100 registros recientes: id, title, opcional amount (null si se desconoce), currency, quantity, source, y at (milisegundos Unix al registrarse). automatic activa la recopilación, salesVisible controla la visualización y revision aumenta con los cambios. La recopilación automática solo acepta purchase eventos de Shopify, vendedor de eBay, Fourthwall, Ko-fi y Buy Me a Coffee; se excluyen eventos privados/de prueba. No trata los metadatos de subastas, propinas, regalos ni reservas de plazas como compras. Los registros automáticos no sustituyen el precio de un artículo por totales de pedidos, precios de anuncios ni importes de donación. Los registros manuales usan source: "Host confirmed".

El estado persiste en el almacenamiento privado de monetización de esta instalación; las instantáneas públicas excluyen ID de deduplicación de entregas, identidad del comprador y secretos. Las ventas mostradas explícitamente conservan sus ID de evento para eliminarlas. Los reembolsos requieren que el anfitrión las elimine. Los ID de compras duplicadas se recuerdan aparte (hasta 2000), incluso tras borrar el historial visible. El existente getCommerceState la respuesta incluye commerce.boards; commerceControl acepta los comandos de tablero/ventas documentados en la guía del tablero. Las ediciones manuales emiten el estado actualizado, pero nunca crean eventos de compra, totales de donaciones ni recompensas de pago. Las superposiciones se ocultan si no reciben la instantánea del anfitrión durante 35 segundos.

Añadidos al flujo de trabajo de vendedores: commerce.boards.board.id identifica una generación del tablero. Un valor manual saleAdd puede proporcionar boardId y spotId para registrar la venta y reservar esa plaza de forma atómica; se rechazan las ventas vinculadas duplicadas que sigan en el historial reciente. saleRemove con reopenSpot: true libera esa plaza solo si la generación del tablero sigue coincidiendo. Las entradas públicas de ventas omiten estos campos de vinculación del operador. Un campo opcional platform en una venta manual conserva su fuente para el filtrado, mientras que source: "Host confirmed" identifica el método de confirmación. amount es el total de la entrada, incluido su quantity. El campo del adaptador de pedidos pagados de eBay meta.ebayPurchase.quantity se conserva.

salesSettings.auctionSource activa la ayuda de artículos de Whatnot o eBay Live. El campo de la respuesta de control commerce.auction contiene solo source, title, priceText, status y at del último evento capturado auction_update, o null. Caduca a los cinco minutos y se borra al cambiar de fuente, recibir una instantánea inactiva o reiniciar. La ayuda es solo para operadores: no se guarda ni se incluye en emisiones al público; se descarta la identidad del pujador/ganador. Los scripts de fuentes y los datos de eventos de subasta no cambian. Copiar un borrador no confirma el pago ni crea una venta.
