Налаштування захоплення, фільтри та правила корисного навантаження
Важливо: Доступність подій залежить від джерела, дозволів і налаштувань захоплення. Щоб приховати рядки з позначкою події в доку або оверлеї вибраних повідомлень, додайте &hideevents або &hideallevents. Щоб приховати вибрані події, використовуйте &filterevents=subscription_gift,new_follower,gifted. Ці фільтри також можуть приховати платні рядки, що мають event; звичайні рядки донатів без позначки події не зіставляються фільтрами подій. Інші фільтри повідомлень усе одно застосовуються.
Виберіть спосіб захоплення: Для YouTube, Twitch і Kick Режим WebSocket зазвичай надає ширше охоплення подій. Стандартне захоплення DOM читає рядки й картки, фактично відображені на сторінці. YouTube Super Chats, Super Stickers і подарунки Jewel мають шляхи захоплення в обох режимах; інші подарунки, чайові й події членства залежать від джерела. Підтримувані шляхи й потрібні налаштування наведено в таблицях платформ.
Створюєте автоматизації? Перегляньте Посібник із потоків подій щоб дізнатися, як використовувати ці дані подій у власних тригерах, сповіщеннях і процесах. Посібник містить Довідник змінних шаблонів для форматування тексту. Суми подарунків, підрахунок серій і редаговані приклади ігор описані в Створюйте ігри й нагороди.
Структура даних: Рядки чату у стилі донатів мають використовувати hasDonation і необов’язкове donoValue. Не задавайте event: "donation" лише тому, що звичайний рядок чату/чайових має значення; використовуйте конкретні назви подій лише для справжніх дій платформи або типів платних елементів, наприклад superchat, supersticker, gift, або jeweldonation. Використовуйте meta лише для додаткових структурованих даних, які справді потрібні споживачам і ще не охоплені наявними полями.

Огляд полів

data тут означає об’єкт повідомлення, а не додаткову обгортку. Рядки чату й події лише з метаданими мають різні структури: лічильники та знімки стану можуть пропускати chatname/chatmessage. У таблицях платформ повідомлення описує звичайний рядок чату, а не буквальний event: "message".

Поле Структура Використання
data.type рядок Ідентифікатор джерела, який використовують оверлеї, фільтри й Event Flow. Instagram зберігає живий чат як instagramlive а коментарі поза ефіром — як instagram. Дивіться Посібник із типів джерел для варіантів, загальних джерел і вихідної маршрутизації.
data.chatname рядок Source-provided display name used by message processing and non-overlay outputs. A configured user display-name alias may replace this value only in copied dock and overlay transport payloads. The opt-in Show display name (username) setting appends the username when a source supplies both names and they differ, ignoring capitalization, for example 알렌 (allenhklee). These copies retain the source name in meta.sourceDisplayName for moderation matching. Custom aliases take priority; username remains the account login.
data.username рядок Ім’я користувача джерела, якщо доступне. Дані дока або оверлею з псевдонімом можуть додавати це поле, щоб зберегти оригінальне chatname для дій користувача; канонічне повідомлення залишається незмінним.
data.userid рядок Ідентифікатор користувача на конкретній платформі. Дії користувачів надають цьому значенню перевагу перед username і chatname.
data.platformрядок (необов’язково)Деякі інтеграції включають це поряд із type. Багато адаптерів джерел пропускають його; використовуйте type для маршрутизації джерела.
data.idрядок | число (необов’язково)Ідентифікатор повідомлення або події. Його значення залежить від джерела й транспорту; не вважайте, що це завжди власний ID модерації платформи. Використовуйте meta.messageId коли адаптер надає його для синхронізації видалення.
data.donoValueчисло (необов’язково)Наданий джерелом числовий еквівалент у USD, зокрема оцінки. Коректне значення (включно з нулем) має перевагу над конвертацією currency.js. За його відсутності споживачі оцінюють USD за hasDonation і контекстом джерела. Оригінальні суми й одиниці залишаються в hasDonation і наявних метаданих постачальника.
data.chatbadgesмасив | рядок (необов’язково)URL зображень значків або об’єкти значків (type: "img" з src, type: "svg" з html, або type: "text" з text). Пересилання зберігає буквальний підпис текстового значка в необов’язковому rawText і створює екрановане text для старіших оверлеїв. На наступних проходах пересилання генеруйте заново text з rawText; не екрануйте text знову. Поточні засоби відображення показують rawText буквально, якщо є, а інакше зберігайте застарілу обробку закодованого тексту. Це поле подання, а не дозвіл відображати HTML. Старіші джерела можуть надсилати один HTML-рядок замість масиву. Оверлеї значків приймають обидва формати й локально очищують HTML і URL значків, зокрема коли відправник — старіше розширення. Некоректні значки не мають заважати відображенню повідомлення чату або членства.
data.event рядок | логічне значення Ідентифікатор системної активності (наприклад viewer_update, subscription_gift, giftpurchase). Для звичайного чату залишайте це порожнім/false, щоб оверлеї відрізняли системні повідомлення від розмовного тексту.
data.chatmessage рядок Текст повідомлення. Може містити очищений/придатний до відображення HTML лише коли data.textonly має значення false.
data.textonly логічне значення Застосовується лише до data.chatmessage. true означає відображати chatmessage як звичайний текст, зберігаючи буквальні теги й текст, схожий на сутності; не декодуйте, не очищуйте як HTML і не додавайте теги форматування до цього тексту. Застосовуйте оформлення події до відображуваного елемента. false означає chatmessage може містити очищений/придатний до відображення HTML; старіші повідомлення без прапорця зберігають цю поведінку HTML. Інші звичайні поля є простим текстом, окрім медіаполів, як-от chatimg і contentimg. Відображайте текстові поля через textContent, або екрануйте їх один раз під час створення HTML-шаблону; не видаляйте й не декодуйте їхній вміст повторно.
data.contentimg рядок (необов’язково) Зображення вмісту або URL підтримуваного медіа. У розширенні й настільному застосунку окремо вмикана функція allowExternalGifs налаштування заповнює порожнє поле з першого прямого посилання HTTP(S) на GIF у тексті повідомлення або HTML-посиланні. Шлях URL має закінчуватися на .gif (без урахування регістру); параметри запиту й фрагменти зберігаються. Ключ API не потрібен, зберігає chatmessage і наявні вкладення, а також враховує removeContentImage. Необов’язкове hideExternalGifUrl налаштування додає meta.hideExternalGifUrl: true; док і оверлей вибраних повідомлень приховують відповідне посилання GIF лише після завантаження зображення, зберігаючи навколишній текст та оригінальні дані. Зображення, що не завантажилися або перевищили час очікування, згортають контейнер вкладення й залишають посилання видимим. Оверлей лише GIF пробує прямий показ зображення, якщо отримання байтів не вдалося, використовуючи налаштований час показу, коли час анімації недоступний; невдалі або завислі завантаження просувають його чергу. Він не додає event або змініть джерело type. Вміст зовнішніх зображень не фільтрується, і вони можуть не завантажуватися, якщо хостинг блокує вбудовування.
data.membership рядок Читабельний стан членства, наприклад MEMBERSHIP, new_sponsor, gift_recipient. Інтерфейси використовують його для значків, фільтрів і оголошень.
data.subtitle рядок Додатковий опис (тривалість членства, підвищення рівня, хто подарував...). Залишайте його коротким і лише текстовим, щоб оверлеї могли розміщувати його під відображуваним іменем.
data.hasDonation рядок Сума грошового або віртуального подарунка ($5.00, 500 bits, 300 coins). Заповнюйте, навіть коли data.event порожнє, щоб оверлеї донатів могли його визначити.
data.meta число | об’єкт | рядок (застаріле) Використовуйте звичайні цілі числа для окремих лічильників (глядачів, підписників, платних підписників) і об’єкти для багатшого контексту. Деякі старіші події, наприклад Twitch DOM community_highlight, містять рядок. Перевіряйте структуру конкретної події перед читанням властивостей об’єкта; нові структуровані подробиці належать до об’єкта.
data.firsttime логічне значення Задається як true коли ввімкнено визначення нових учасників чату, локальна база даних і це перше збережене повідомлення для цього користувача/джерела. Док використовує це для виділення нових учасників і фільтрів звукового сигналу першого повідомлення; необов’язкове налаштування значка нового учасника додає значок листка на початок chatbadges.
data.lastactivity число Часова позначка Unix у секундах попередньої збереженої активності чату цього користувача, коли ввімкнено визначення нових учасників чату й локальну базу даних. Пропускається для зовсім нових користувачів.

Правила Meta

Транспорт керування оверлеєм відокремлений від захопленого чату/подій. Оновлені приймачі використовують ssnControl обгортку, що містить ідентифікатор доставки id, вибрати target, необов’язковий канал відповіді та ID клієнта знімка. Наявні тіла вибраних повідомлень залишаються незмінними. Публічне керування вибором використовує канал 7; Actions зберігає канал 6. Стан Poll і Map містить поле ведучого epoch, revision і reset позначка; Timer, Ticker і Spotify використовують ssnState з епохою та ревізією. Ці позначки описують стан ведучого, а не відновлену історію голосів/чату. Джерела не мають додавати поля керувальної обгортки до захоплених повідомлень. Підтвердження отримання не доводить завершення дії або видимості в OBS. Дивіться стан міграції щодо підтримуваних функцій, узгодження відповідей і обмежень повторного підключення.

Phrase Guess використовує власний {response: text} запит для відповідей чату server2 та {action: "phraseGuessResponse", value: {type: "bot", chatname: name, chatmessage: text}} для оголошень лише в доку. Ведучий має ввімкнути вхідні повідомлення server3; вимкнення керування ведучого все ще блокує ці запити. Оголошення дока пересилаються як звичайні рядки чату бота з textonly: true, без надсилання в поля чату джерел захоплення. Застарілий режим API зберігає наявний формат команд.

  • viewer_update, follower_update, subscriber_update, і likes_update використовують звичайне ціле число meta значення. likes_update є авторитетним підсумком платформи: споживачі мають установлювати показане значення, а не додавати його. Фоновий скрипт об’єднує кількість глядачів у viewer_updates з об’єктом, ключі якого — data.type.
  • giveaway_state є згенерованим ведучим знімком лише метаданих для керованого відображення. meta.giveaway версія 2 включає giveawayId, постійне roundId/epoch, зі збільшенням generation між новими раундами, revision у межах раунду, status, open, draw, keyword, count, ticketCount, зафіксоване config, до 120 попередніх entrants, і останні 20 winners. Записи надають id, name, platform і tickets; переможці додають drawnAt і надане points. Coin Flip Pot додає outcome; Number Hunt додає number із публічним low, high і останні guesses, ніколи не секрет. Споживачі фільтрують за ID розіграшу й відкидають старі покоління/ревізії. Це зразки відображення, а не повна книга квитків чи інструкція виплат. Ключі гаманців, баланси й резервування не потрапляють у глядацькі знімки. Ведучий публікує в giveaway мітку P2P і ввімкнені потоки WebSocket оверлею; це не означає видимості в OBS. Посібник.
  • meta.giveawayControlResult містить результат дії розіграшу Event Flow (ok, необов’язкове error, giveaway або simulated). meta.giveawayHandled перелічує ID розіграшів, уже оброблених дією входу/покупки потоку, щоб автоматична команда чату не списала кошти повторно. Редактор додає meta.economyTest для імітованих дій розіграшу; це не подія вихідної платформи й не облікові дані авторизації.
  • video_stats використовує структурований meta об’єкт стану зовнішнього кодувальника/сервера, зокрема provider, label, online, bitrateKbps, rttMs, bufferMs, лічильники втрат/відкидання пакетів і необов’язкові подробиці кодека.
  • Події у стилі донатів можуть включати описовий об’єкт, наприклад { amount, currency, supporter } для Kick, { bits } для cheers Twitch. Події членства мають власні метадані, залежні від джерела; вони не є автоматично грошовими донатами.
  • Нормалізовані повідомлення вебхуків Stripe, Ko-fi, Buy Me a Coffee і Fourthwall містять обмежене постачальником meta.webhookId, скопійований зі стабільного ідентифікатора події постачальника, щоб наступні сторінки могли прибирати дублікати повторних спроб і змішаних транспортів.
  • Рейди Twitch передають { fromId, fromLogin, viewers }. Інші джерела відрізняються: Whatnot використовує meta.numRaiders, тоді як SharePlay використовує необов’язкове meta.fromLogin/meta.viewers. Перевірте рядок конкретного джерела перед читанням метаданих рейду.
  • Використання винагород Twitch EventSub надає meta.rewardId, cost, rewardTitle, redemptionId, і застаріле alias поряд із підготовленим повідомленням. Картки винагород DOM та інші джерела можуть надавати менше полів або інші поля.
  • user_banned містить лише метадані для віджетів модерації. Навмисно пропускає chatname і chatmessage; використовуйте meta.username, meta.displayName, meta.avatarUrl, і meta.profileUrl.
  • Транспорти чату, які підтримують синхронізацію видалення через керування джерелом, мають надавати власний ідентифікатор чату платформи як meta.messageId замість покладання на внутрішнє поле дока data-mid значення.
  • Видалення джерел використовують {delete: {type, id}} для відомого ID повідомлення дока або {delete: {type, meta: {messageId}}} для власного ID повідомлення платформи. Відомий ID видаляє лише відповідні повідомлення. Коли відомий лише цільовий користувач, надішліть {delete: {type, userid}} або {delete: {type, chatname}} щоб прибрати повідомлення цього користувача з цієї платформи. Ніколи не підставляйте ідентичність модератора замість цільового користувача. Вхідні видалення не потребують необов’язкового налаштування синхронізації модерації з дока на платформу.
  • Метадані ідентичності джерела SSApp можуть додавати meta.ssnAccountRole, meta.ssnSourceId, і meta.ssnSession коли джерелу призначено роль облікового запису, відмінну від normal.
  • Event Flow може запросити виділення, задавши meta.featured = true у даних чату, що автоматично вибирає повідомлення в доку/оверлеї вибраних повідомлень.
  • AI Event Overlay: дія showAiEventOverlay надсилає копію повідомлення, що її викликало, одержувачу з міткою aievent-CONFIGURATION_ID, додаючи meta.aiEventOverlay: {profile: "CONFIGURATION_ID"}. Наявні поля повідомлення та метадані у вигляді об’єкта зберігаються; скалярні метадані зберігаються в meta.value. Це адресне доставлення, а не нова подія платформи. Початкове повідомлення не змінюється. Див. посібник із налаштування.
  • Необов’язково meta.aiEventOverlay.variation вибирає точну фразу, схвалену в збережених налаштуваннях оверлею. Текст глядача й метадані заповнюють поля шаблону після його генерації.
  • Запити на показ AI Event Overlay потребують профіль і його приватний токен показу. Налаштуваннями та ключами API можна керувати лише через локальне спливне вікно SSN. Відповіді використовують {aiEventResponse: {target, value}} або {aiEventResponse: {target, error}}. Результати генерації містять template, duration, warnings, а також необов’язкові URL медіаданих у image/audio.
  • Винагороди у вигляді ШІ-оверлеїв, оплачені балами, використовують aiEventPresentation (id, profile, expiresAt, result, message) і підтверджують отримання через aiEventDelivered (ідентифікатор доставки). Записи про списання та суми повернень залишаються на хості.
  • Event Flow може запросити закріплення в доку, задавши meta.pinned = true; необов’язкове meta.pinnedTarget обмежує це закріплення доком із відповідним label.
  • Термодрук Event Flow записує свій результат у meta.thermalPrintResult (success і необов’язкове code/error), зі збереженням події чату та інших метаданих. Для подій із числовими або іншими необ’єктними метаданими діагностика залишається в результаті дії, а подія не змінюється.
  • Винагороди-стікери SSN за окремим увімкненням: event: "sticker" надсилається лише до stickers мітку оверлею після списання балів лояльності. Задає platform і type до поля початкового повідомлення type, і зберігає chatname, із порожнім chatmessage, textonly: true, і contentimg що містить відносний шлях до упакованого зображення або схвалений ведучим URL медіа HTTPS. meta.sticker містить id, pack, name, cost, duration (секунди), motion, redemptionId, і expiresAt (мілісекунди Unix). Це винагорода SSN, а не донат платформи чи власна подія балів каналу. Дивіться галереї та посібнику з налаштування.
  • Програвач стікерів повертає керувальний пакет {action: "stickerReceipt", meta: {sticker: {redemptionId, success}}} своєму відправнику після завантаження або збою зображення. Лише підтвердження від підключеного stickers вузлу вирішити очікуване використання винагороди. Невдала або непідтверджена доставка запускає повернення; цей керувальний пакет не є подією чату. Рекомендовано один активний екран стікерів на сесію.
  • Команди сценічного оверлею ШІ використовують { action: "aiOverlay", target, meta } або кероване доком відтворення співведучого використовує { action: "cohostOverlay", target, meta }; зберігайте всі подробиці команд, наприклад command, text, emotion, avatar, і tts всередині meta.
  • Якщо платформа надає кілька лічильників разом, надавайте перевагу структурованому об’єкту з явними ключами (meta.viewer_count, meta.follower_count) замість перевантаження рядків.
  • Торгові оверлеї мають використовувати об’єкти знімків у meta (наприклад auction_update і commerce_update) та уникайте довільних полів верхнього рівня.

Сповіщення про підписників YouTube (new_follower)

Social Stream тепер може визначати нових підписників YouTube за допомогою myRecentSubscribers кінцева точка API. Працює подібно до сповіщень про підписників Streamlabs.

Як це працює:

  • Опитує YouTube API кожні 5 хвилин щодо нових підписників
  • Відстежує побачених підписників у localStorage для визначення нових
  • Надсилає new_follower події з іменем, аватаром та ID каналу підписника
  • Типово залишає сповіщення про підписників вимкненими; після ввімкнення використовується поточний рядок перекладу для alert-just-subscribed
  • Типово групує серії з понад трьох нових підписників, щоб повторні підключення не переповнювали оверлеї або Event Flow
  • Потребує ввімкненого режиму WebSocket у налаштуваннях розширення

Обмеження (це обмеження YouTube API, а не Social Stream):

  • Без гарантованої затримки доставки — SSN опитує кожні п’ять хвилин, але API може повертати затримані або неповні результати. Не покладайтеся на фіксоване чотиригодинне вікно.
  • Лише публічні підписки — Підписники, які зробили список підписок приватним, не запускатимуть сповіщень. На YouTube підписки приватні за замовчуванням.
  • Лише власник каналу — Ви можете отримувати сповіщення про підписників лише для каналів, якими володієте й під обліковим записом яких авторизовані.
  • Використання квоти API — Кожне опитування коштує 1 одиницю API. З інтервалом 5 хвилин це приблизно 288 одиниць на день (із типової добової квоти 10 000).

Включено оновлення подарункової серії DOM і рядки подарунків TikFinity meta.tiktokGiftStreakId, meta.tiktokGiftCount, і meta.tiktokGiftQuietMs щоб оверлеї могли об’єднувати повторні оновлення; застарілі ID серій унікальні для екземпляра сторінки. Метадані подарунка також можуть включати tiktokGiftMessageId (оригінальний ID повідомлення TikTok), tiktokGiftSenderId, groupId, giftId, giftName, streakable, і repeatEnd. Власні ID визначають той самий подарунок у різних вікнах захоплення; ненульовий ID групи разом з ID відправника й подарунка визначає сукупні оновлення серії. Захоплення WebSocket SSApp надає ті самі поля після завершення серії, з count зберігається для сумісності. Перемикач донатів перевіряється при пересиланні кожного подарунка: вимкнення донатів TikTok прибирає hasDonation і donoValue зі збереженням події подарунка та метаданих. Озвучення використовує ці ідентичності для об’єднання оновлень і пригнічення завершених дублікатів протягом максимум десяти хвилин (обмежений кеш) та читає подарунки TikTok як відправника, кількість і назву подарунка. Старіші дані повертаються до наявних ID серій і тексту повідомлення; ідентичність не виводиться лише з тексту подарунка. Озвучення подарунків TikTok використовує вибрану мову озвучення/голосу незалежно від мови інтерфейсу. Дієслова оголошень локалізовані англійською, іспанською, португальською, французькою, німецькою, італійською й нідерландською; інші мови використовують відправника, кількість і назву подарунка без англійського дієслова. Спрощене озвучення зберігає цей нейтральний формат. Назви подарунків залишаються такими, як їх надає платформа; це не перекладає автоматично каталоги подарунків або повідомлення чату й не визначає мову трансляції.

Для цих оновлень серій кількість і підпис донату є сукупними: 1, 2, 3 означає три подарунки, а не шість. Споживачі підсумків мають додавати лише приріст понад найбільшу вже отриману суму для ID цієї серії. Стандартне захоплення підтримує застарілі класи подарунків і поточні рядки зображення/кількості; обидва зберігають event: "gift" і hasDonation. Для невідомих цін зберігаються кількість/назви подарунків для показу та використовується оцінка в USD з розрахунку одна монета за подарунок. Надане джерелом donoValue має пріоритет; метадані відображеного подарунка можуть надавати coinsPerGift або diamondsPerGift перш ніж знадобиться таблиця подарунків або типове значення. Оцінки монет Standard/TikFinity і власні оцінки діамантів SSApp використовують наявні окремі перерахунки; жодна не є гарантованою грошовою виплатою.

Подія Коли спрацьовує Примітки щодо даних

donation Події чайових і внесків у підсилення спільноти Whatnot WebSocket. hasDonation містить відформатовану суму; специфічний контекст WebSocket залишається в meta.

auction_update Коли змінюється стан аукціону на живій нижній панелі (текст переможця/лідера, назва, ставки, ціна, таймер, стан продажу), часто прискорено пакетами життєвого циклу аукціону WebSocket. auction_started, new_bid, auction_ended, product_sold Надходить відповідне живе сповіщення WebSocket. Це окремі події, відокремлені від наявних знімків відображення. platform/type: "whatnot", звичайний текст chatname, userid коли надано, назва товару в subtitle, і звичайний текст у chatmessage з textonly: true. Доступні ідентифікатори й подробиці аукціону містяться в meta: productId, auctionId, orderId, transactionId, livestreamId, bidId, bids, auctionEndTime, і status. Необов’язкове price подається в основних одиницях валюти, з priceText і currency коли надано.

payment_failed Надходить живе сповіщення WebSocket про невдалий платіж. Ті самі доступні поля покупця, товару та ідентифікатора, з meta.paymentStatus: "failed". payment_succeeded Надходить живе сповіщення WebSocket про успішний платіж. meta.paymentStatus: "succeeded", із покупцем, товаром, ID замовлення й іншими дозволеними полями з цього сповіщення. Це залишається окремою платіжною подією; воно не створює ще одну purchase або донат. Відсутні поля залишаються порожніми або пропущеними, навіть якщо попередній продаж їх надавав.

Оновлення відображення аукціону/торгівлі залишаються знімками на основі DOM. Щоб зіставити окрему подію WebSocket в Event Flow, використовуйте Тип події (розширений), виберіть Власна подія, і введіть його точну назву. Підписи можуть використовувати **{username}**\n{subtitle} із вибраною товщиною тексту; умови можуть порівнювати meta.paymentStatus з failed. Об’єкт приклад мітки Whatnot для імпорту доступне. Наявні налаштування захоплення подій трансляції все ще застосовуються.

Додаткові необов’язкові поля: meta.catalogProductId (поле пакета product.productId), meta.parentProductId (product.parentId), meta.transactionType (тип продажу Whatnot, без змін) і meta.placeOrderErrorReason (код помилки замовлення/оплати, наданий Whatnot). Ці посилання на товари описують каталог або батьківське оголошення; вони не замінюють ID замовлення. Кількість у запасі не вважається купленою кількістю.

Для автоматизації успішної оплати задайте Тип події (розширений) тригер на Власна подія: payment_succeeded, і відфільтруйте джерело до Whatnot. Наявні умови й шаблони можуть використовувати поле цієї події userid, chatname, subtitle і meta.orderId безпосередньо. Збережена покупка не потрібна, якщо сповіщення містить необхідні подробиці.

Завершення аукціону або позначення товару проданим не підтверджує успішну оплату: ці сповіщення не надсилаються як оплачені purchase події й не задають суми донатів. Подія успіху надсилається лише для отриманого payment_succeeded сповіщення; захоплення не опитує завершення оплати й не виводить його з продажу. Інші paymentStatus values are forwarded only when explicitly supplied in a captured packet. Missing identifiers are omitted; a product ID alone may cover multiple sales, so use a supplied order/auction ID to correlate notifications. Capture does not remember purchases or match payment updates; any such workflow must be explicitly configured in Event Flow. Repeated commerce notifications with the same native event timestamp/ID are suppressed across overlapping channels and reconnects, within a 2,000-event cache. Packets without a native event identity use a brief duplicate window. Raw order/payment objects are not forwarded.

Його реалізований платіжний контракт надсилає event: "purchase", з type і platform задається як ebay. Потребує оплаченого замовлення, що відповідає вибраному товару. id є стабільним непрозорим ідентифікатором позиції замовлення; chatname має значення «eBay buyer», chatmessage є звичайним текстом (textonly: true), subtitle є назвою товару й необов’язковим contentimg є його зображенням. meta.ebayPurchase містить itemId, itemName, quantity, і публічне url. Без ідентичності покупця, даних доставки, hasDonation або donoValue включається. Це відрізняється від зчитаних оновлень аукціону або запасів, які не доводять оплату.

Реалізація: sources/ebay.js

  • Відкрийте будь-яке з /ebaylive/events/<id>/chat або /ebaylive/events/<id>/stream. Обидва отримують той самий живий потік аукціону.
  • Публічний потік WebSocket надає аукціони, ставки, переможців, продовження часу та зміни запасів; запит GraphQL лише для читання надає подробиці оголошення. Захоплення DOM залишається запасним варіантом, коли мережеві дані недоступні.
  • Захоплювати події трансляції керує знімками метаданих (auction_update, commerce_update); лічильники глядачів і далі враховують перемикачі глядачів/ажіотажу.
Подія Коли спрацьовує Примітки щодо даних
viewer_update Коли змінюється кількість глядачів активної події (лічильник заголовка або запасний індикатор живої події). meta є цілою кількістю глядачів.
follower_update Коли кінцева точка статистики продавця повертає кількість його підписників. meta є цілою кількістю підписників. Джерело опитує кінцеву точку продавця кожні 60 секунд; вона все ще може повертати кешоване значення до 5 хвилин.

Мережеве захоплення задає meta.sourceMode до network і надає title, price, bidder, winner, bids, timer та endingAt. meta.ebay містить eventId, listingId, запис оголошення GraphQL (listing), поточне публічне сокетне оголошення (eventListing) та останнє оновлення аукціону (update). Вони зберігають категорію, зображення, валюти, кількості, подробиці брейку коробок, результати аукціону й часові поля, не втрачаючи подробиць платформи. Початкова історія/історія повторного підключення включається до поточного знімка замість надсилання старих перемог. Видалення всіх показаних оголошень створює status: "idle" з cardCount: 0 щоб очистити аукціон. Запасний варіант DOM зберігає поля картки програвача або попереднього перегляду події.
commerce_update Коли змінюються розділи знімка каталогу/живих подій. Знімок лише метаданих у meta. Мережевий режим включає eventId, navigation.viewerCount і playerCards для поточних представлених оголошень, кожне з тією самою докладною ebay об’єкт як знімок аукціону. Порожній список карток очищує видалені оголошення. Запасний варіант DOM також може включати liveEvents, livePreview, currentEvent і upcomingEvents.
reaction Коли eBay Live відображає анімацію сердечка/реакції. Надсилається безпосередньо до окремої цілі реакцій. meta.reactionType є heart; eBay не надає окремого імені користувача для цих DOM-анімацій.

Події метаданих eBay навмисно пропускають chatname/chatmessage; наступні оверлеї мають відображати з data.event + data.meta лише.

Joystick

Реалізації: sources/joystick.js, sources/inject/joystick-ws.js, і sources/websocket/joystick.js

  • Звичайне джерело вебсайту Joystick 2.0 працює на авторизованій /u/<channel>/chat сторінка. Читає поле сторінки ChatChannel, WhisperChatChannel, EventLogChannel, і SystemEventChannel Кадри Action Cable із запасним зчитуванням відображених рядків для Electron і випадків повторного підключення.
  • Повідомлення чату вебсайту використовують ті самі основні поля, що й YouTube, Twitch і Kick: власний id, chatname, chatmessage, chatimg, chatbadges, nameColor, membership, mod, private, username/userid, і timestamp коли Joystick їх надає. Коли сокет не передає колір імені, відображений рядок надає те саме nameColor поле, яке використовують доки з увімкненими кольорами.
  • Редагування повідомлень на сайті замінюють відповідний рядок дока; видалення, приглушення й блокування прибирають відповідні рядки за власним ID або іменем користувача.
  • Окреме джерело WebSocket використовує облікові дані бота Joystick (client_id + client_secret); джерело вебсайту використовує авторизовану сесію сторінки.
  • Авторизується на https://joystick.tv/api/oauth/authorize, потім обмінює/оновлює токени на https://api.joystick.tv/api/oauth/token.
  • Підключається до wss://api.joystick.tv/cable і підписується на GatewayChannel.
  • Необов’язковий обмін токенами OAuth використовується для допоміжних кінцевих точок, як-от https://api.joystick.tv/api/users/stream-settings.
  • Окреме джерело з обліковими даними бота не надсилає viewer_update. Авторизоване джерело вебсайту надсилає кількість глядачів, коли сокет сторінки її надає, як описано нижче.

XP Sync

Реалізація: sources/xpsync.js

Тримайте віртуалізований чат прокрученим до найновіших повідомлень. Наявна історія, повторно відображені рядки й системні повідомлення без автора виключаються. Індекси відображення залишаються внутрішніми й не надсилаються як власні ID повідомлень. Події підписок, донатів, кількості глядачів або модерації не виводяться.

Нагору

Оверлеї монетизації

Чайові NinjaBacker використовують platform: "ninjabacker", type: "ninjabacker", chatname, звичайний текст chatmessage, textonly: true, поле з префіксом джерела id, відформатоване hasDonation, і числове donoValue. Це звичайні рядки донатів без event перевизначення. meta.ninjabacker містить ISO currency і в основних одиницях amount. Анонімні чайові використовують ім’я Anonymous. Джерело використовує або живий SSE (без повторного відтворення), або окремо вмиканий приймач підписаних вебхуків на SSN API (до семи днів доставки з черги). Надійні доставки використовують стабільний ninjabacker:delivery:DELIVERY_ID id. Жоден режим не отримує скасувань через повернення/спори. Облікові дані приймача й секрети підпису ніколи не потрапляють у дані подій. Значення callbackId, контрольовані викликачем, не є ідентичністю платежу й не пересилаються. Тестові чайові панелі виключаються з рядків донатів. Вони надсилають event: "monetization_test" з meta.ninjabackerTest що містить id і at (мілісекунди Unix), лише для окремого сповіщення попереднього перегляду.

event: "monetization_update" є знімком лише метаданих із type/platform: "socialstream". meta.monetization.wishlist містить enabled, qr, position, rank, total, публічний url і поточний item (name, amount, currency, image, публічний url) або null. meta.monetization.ninja містить enabled, qr, position, username і публічний url для чайових. Приватні Tip IDs ніколи не включаються. meta.monetization.ebay містить enabled, qr, position, display (cycle/cheapest/first), seconds, окремо вмикані налаштування оголошень і публічні items. Кожен елемент має id, name, amount, currency, image, url, auction, startingBid, endsAt, available, bought і updatedAt. Час указано в мілісекундах Unix. Облікові дані продавця й ідентичність покупця не включаються.

Підтверджена ведучим покупка зі списку бажань також включає meta.wishlistPurchase з id, name, необов’язковим supporter і at (мілісекунди Unix). Це підтвердження ведучого, а не сповіщення оплати Amazon, і воно не рахується грошовим донатом. Оверлеї мають усувати дублікати за id та ігнорувати старі сповіщення покупок.

Оплачені замовлення Shopify

Необов’язковий приймач підписаних повідомлень Shopify надсилає platform/type: "shopify" і event: "purchase" лише для orders/paid з financial_status: "paid", додатну загальну суму, test: false, відсутність скасування та поточна часова позначка оновлення підписаного тіла. Тестові, неоплачені, застарілі, скасовані повідомлення й повідомлення повернень не створюють дій покупки. Намір подарунка не виводиться.

chatname має значення Anonymous; поля клієнта, приватні примітки й URL замовлень виключаються. chatmessage є звичайним текстом із textonly: true; subtitle містить до трьох публічних назв товарів. meta.commerce містить orderTotal і currency у валюті магазину, а також quantity коли відома повна коректна кількість. Одержувач і фізичне/цифрове призначення залишаються незаданими. Без hasDonation або donoValue задано. id є стабільним непрозорим хешем, обмеженим магазином/замовленням, із префіксом Shopify; це не необроблений ідентифікатор замовлення.

Покупки використовують наявні шляхи активності, категорію Purchase multi-alerts і Event Flow. Просування товарів використовує наявний meta.monetization.commerce каталог. Імпорт товару або встановлення його рекламного підпису Gift не створює подію покупки чи подарунка. Налаштування Shopify та обмеження доставки.

Подарунки й торгівля

Використовуйте event: "gift" для подарунка, giftcontribution для платної підтримки подарунка, giftfunded для завершення фінансування й purchase для продажу товару. Ці назви незалежні від постачальника й від того, фізичний товар чи цифровий. Залиште застарілий giftpurchase подія подарованих членств; Throne раніше неправильно використовував цю назву, а тепер надсилає gift. Наявні джерела подій членства залишаються незмінними. Власні фільтри назв подій Throne мають перейти на gift; фільтри донатів змінювати не потрібно.

hasDonation залишається ознакою сумісності для платної підтримки, з donoValue що містить надане або оцінене значення в USD. Подарунки й внески зберігають ці поля. Завершення фінансування пропускає обидва, щоб не враховувати внески двічі. Звичайні продажі товарів типово їх пропускають, зберігаючи контракт eBay. Не виводьте намір подарунка з магазину, URL списку бажань або фізичного товару: покупка для покупця чи іншого одержувача залишається продажем, якщо джерело явно не визначає подарунок автору.

Необов’язкове спільне meta.commerce поля: recipient (creator, buyer, other), itemType (physical, digital, service), quantity (додатна кількість товарів), currency (валюта ISO), goalAmount (ціль фінансування в основних одиницях валюти, ніколи не новий дохід) і orderTotal (відома загальна сума оплаченого замовлення в основних одиницях валюти; торгівля, а не дохід від донатів). Пропускайте невідомі подробиці. Зберігайте назви товарів у subtitle, зображення в contentimg, і текст підтримки в chatmessage. Наявні метадані постачальників залишаються доступними. Throne надає одержувача й валюту, а після завершення — goalAmount; eBay надає кількість. Жоден не вгадує тип товару й не розкриває приватних відомостей одержувача.

Стрічка активності показує ці події навіть без тексту підтримки. Multi-alerts використовує оформлення донатів для подарунків і внесків, включно з окремим сповіщенням Gift Fully Funded без грошового значення. Покупки мають окрему категорію Purchase, увімкнену за замовчуванням, з purchasestyle, purchasesound, purchaseaccent, і disablepurchases параметри URL. Сповіщення про покупки не змінюють суми донатів.

Event Flow надає ці назви подій у тригерах Event Type і Other Event. Тригери Donation і далі перевіряють hasDonation; тригери Gift Sub зберігають семантику членства. Compare Property приймає вкладені шляхи, наприклад meta.commerce.recipient. Шаблони дій приймають {meta.commerce.quantity} і {meta.commerce.currency}, поряд із наявним {donation}, {subtitle}, і {meta}. Вкладені шляхи чутливі до регістру, відсутні значення відображаються порожніми, а обхід прототипів заборонений.

Вебхуки торгівлі авторів і рекламні оверлеї

Публічні платежі Donation Ko-fi зберігають hasDonation і отримують USD donoValue. Платежі підписок використовують new_subscriber або resub, із рівнем у membership. Shop Order і Commission використовують purchase без значень донатів. Приватні події Ko-fi залишаються виключеними. JSON у кодуванні форми декодується один раз; імена й повідомлення є звичайним текстом.

Buy Me a Coffee donation.created зберігає грошову підтримку; extra_purchase.created і commission_order.created стають purchase. wishlist_payment.created стає giftcontribution використовуючи лише суму цього платежу; meta.commerce.completed записує прапорець завершення постачальника без надсилання ще одного грошового рядка. membership.started стає new_subscriber із рівнем у membership, більше не використовуючи помилково hasDonation для назви рівня. Сума початку підписки сама по собі не вважається оплаченим списанням. Тестові, повернені, невдалі та непідтримувані події оновлення/життєвого циклу не створюють платних сповіщень. Приховані примітки прихильників пропускаються.

Fourthwall підтримує ORDER_PLACED (purchase), GIFT_PURCHASE (gift, одержувач other), DONATION (звичайний рядок донату) і SUBSCRIPTION_PURCHASED (new_subscriber). Наявні суми замовлень зберігають hasDonation для зворотної сумісності, позначене meta.commerce.legacyDonationValue: true; це явний виняток із нових типових правил продажу товарів. Замовлення із застосованими подарунковими картками створюють сповіщення про покупку без значення донату: нове списання неможливо надійно визначити із загальної суми замовлення, а придбання подарунка вже враховане. Платіжні імена й електронні адреси не використовуються для публічної ідентичності. Тестові події панелі та оновлення замовлень не створюють платних сповіщень.

Ці адаптери зберігають наявне пересилання, дії ботів, Event Flow і маршрутизацію цілей, з meta.webhookId усунення дублікатів. Вони надають публічні імена, звичайні текстові повідомлення, відомі назви товарів у subtitle, і ISO meta.commerce.currency поряд із числовими значеннями донатів, де доречно. Вони не додають обліку повернень або нової автентифікації приймача; використовуйте наявний налаштований маршрут вебхука постачальника.

meta.monetization.commerce у monetization_update містить enabled, qr, position, display (first/cycle), seconds і публічний масив items. Кожен елемент має name, url, image, необов’язкове amount (null, якщо невідомо), currency та purpose (shop/gift/support/membership). Це введені ведучим рекламні подробиці, а не доказ оплати. Додавання або редагування елементів не створює події донату чи покупки. Загальний оверлей використовує mode=commerce; view=both|showcase|card|alerts відокремлює просування від активності. Необов’язкові параметри URL style, scale, cardevery, cardfor і onlytype керують поданням. Наявні режими постачальників також приймають керування view і розкладом. Дивіться посібник із налаштування.

Події подарунків Throne

Окремо вмикана інтеграція Monetization пересилає підписані події Throne з platform і type задається як throne. Усі три використовують стабільний ідентифікатор доставки id, звичайний текст chatname, chatmessage з textonly: true, назва товару в subtitle, і необов’язкову мініатюру HTTPS у contentimg.

подіяЗначенняСума донату / ранг
giftПридбаний подарунокhasDonation і USD donoValue; ранг подарунка +1
giftcontributionВнесок на подарунокЛише сума внеску; без підвищення рангу
giftfundedПодарунок, на який завершено спільний збірНі hasDonation або donoValue, уникаючи повторного врахування попередніх внесків; ранг подарунка +1

meta.throne містить itemName, creator (публічне ім’я користувача), completed, currency і в основних одиницях amount. Для giftfunded, сума описує ціль, а не новий дохід. Анонімні дарувальники залишаються Anonymous; завершені спільнотні подарунки використовують Community. Приватні платіжні поля й поля доставки ніколи не пересилаються.

monetization_update знімки додатково містять meta.monetization.throne: enabled, username, url, qr, position, rank, і gifts. Ці знімки не містять URL вебхука або облікових даних прослуховування.

Голосові команди ведучого (попередня настільна версія)

У Event Flow Коли я кажу… тригер отримує довірені локальні команди мікрофона від SSApp. Його внутрішній контекст дії використовує chatname: "Host", type: "hostvoice", розпізнана фраза в chatmessage, і textonly: true. Це не вхідна подія платформи й не новий транспорт чату. Надсилання цих полів через чат не може активувати голосовий тригер.

Потребує оновленої настільної збірки, явного запуску мікрофона й увімкнення дій після тестового режиму. Дивіться налаштування попередньої версії та стан перевірки.

Керування відображенням товарів

Наявне monetization_update знімки можуть включати meta.monetization.commerce.live: null для збереженого розкладу або {mode: "show" | "hide", url?: "https://...", until: 0 | epochMilliseconds}. Show зіставляє точний збережений URL товару; якщо товар відсутній, картка не показується. Додатне until після завершення строку повертає збережений розклад; нуль діє до зміни або перезапуску SSN. Hide приховує рекламні покази, але не сповіщення про платну активність.

commerce.viewerURL є опублікованим URL магазину лише для читання або порожнім рядком. Якщо є, рекламні QR-коди ведуть туди. Він ніколи не містить сесії SSN або ключа публікації. Товари залишаються в commerce.items. Керування відображенням, імпорт або публікація не створюють події донату/покупки. Дивіться Керування товарами для Event Flow і віддаленого API.

У Event Flow commerceControl дія чекає прямої відповіді/відповіді Chrome (до восьми секунд). Для звичайних даних події вона зберігає подію й додає meta.commerceControlResult: {success: true, commerce: controlState} або {success: false, error: "..."}. Для наявного числового, масивного або іншого необ’єктного meta, метадані не змінюються, а діагностика повертається як commerceControlResult у результаті дії натомість. Невдалі команди керування зупиняють наступні дії в цьому ланцюжку, не пригнічуючи початкову платіжну подію. Тайм-аут не доводить, що команду не застосовано; перевірте стан перед повтором відносної команди, наприклад Next. Успіх підтверджує локальний стан вибору/приховування/розкладу, але ніколи не видимість в OBS або синхронізацію публічної сторінки.

Іменовані процеси Stream Deck / API

Цей тригер іменованого процесу створює внутрішнє повідомлення Event Flow із type: "api", event: "workflow_trigger", chatname: "Stream Deck / API", порожнє chatmessage, і textonly: true. Його meta.workflow об’єкт містить назву тригера й надані викликачем JSON-дані data об’єкт. Читайте значення через шаблони, наприклад {meta.workflow.data.minutes}. Оцінюються лише збережені ввімкнені потоки, які явно відповідають цьому тригеру. Це не вхідна подія глядача/чату й вона не транслюється як чат; копіювання цих полів у чат не активує іменований тригер.

Пілот аудиторії NinjaChatter

Експериментальний спарений конектор розширення надсилає рядки лише для відображення з type: socialstreamchat, platform: ninjachatter, і textonly: true. meta.ninjachatter містить origin: audience, описове provider, і публічне room ID. Ці рядки обходять відповіді платформ, ботів, тригери Event Flow і бали. Відображений постачальник не є авторизацією. Застарілі захоплення джерела NinjaChatter включають meta.ninjachatter.room для усунення дублікатів у межах кімнати.

Cheer використовує окремий автентифікований шлях заявки й результату, ніколи не спеціальну команду чату. Фіксований пресет надсилає наявну подію оверлею Actions show_text повідомлення на три секунди. Його отримання означає прийняття транспортом, а не перевірений показ в OBS. Жодні дані аудиторії не можуть вибирати довільні дії. Пілот типово вимкнений у NinjaChatter; Electron зберігає наявне пересилання, доки нова межа приватного спарювання не буде перевірена.

Торгові дошки місць і останні продажі

Наявний monetization_update подія (type/platform: socialstream) також включає meta.monetization.boards. Його board містить title, style (spots/teams), columns (1–20), visible, і до 120 spots. Кожне місце має рядкове поле id, звичайний текст label, status (available/claimed/revealed) і result (звичайний текст, порожній до розкриття). Зайняття та розкриття — введений ведучим стан відображення, а не доказ покупки чи випадковий розподіл.

boards.sales містить до 100 останніх записів: id, title, необов’язкове amount (null, якщо невідомо), currency, quantity, source, і at (час запису в мілісекундах Unix). automatic вмикає збирання, salesVisible керує відображенням і revision збільшується при змінах. Автоматичне збирання приймає лише purchase події Shopify, продавця eBay, Fourthwall, Ko-fi та Buy Me a Coffee; приватні/тестові події виключаються. Метадані аукціону, чайові, подарунки або зайняття місць не вважаються покупками. Автоматичні записи не підставляють загальну суму замовлення, ціну оголошення або суму донату замість ціни товару. Ручні записи використовують source: "Host confirmed".

Стан зберігається в приватному сховищі монетизації цієї інсталяції; публічні знімки виключають ID усунення дублікатів доставки, ідентичність покупця та секрети. Явно показані продажі зберігають ID подій для видалення. Повернення потребують видалення ведучим. Дубльовані ID покупок запам’ятовуються окремо (до 2 000), зокрема після очищення видимої історії. Наявний getCommerceState відповідь включає commerce.boards; commerceControl приймає команди дошки/продажів, задокументовані в посібнику дошок. Ручні зміни транслюють оновлений стан, але ніколи не створюють подій покупок, сум донатів або платних винагород. Оверлеї приховуються, якщо знімок ведучого відсутній 35 секунд.

Доповнення процесу продавця: commerce.boards.board.id визначає покоління дошки. Ручний saleAdd може надавати boardId і spotId щоб атомарно записати продаж і зайняти це місце; дубльовані пов’язані продажі, що ще є в недавній історії, відхиляються. saleRemove з reopenSpot: true звільняє це місце лише якщо покоління дошки все ще збігається. Публічні записи продажів пропускають ці операторські поля зв’язку. Необов’язковий platform для ручного продажу зберігає джерело для фільтрації, тоді як source: "Host confirmed" визначає спосіб підтвердження. amount є підсумком запису, включно з його quantity. Поле адаптера оплачених замовлень eBay meta.ebayPurchase.quantity зберігається.

salesSettings.auctionSource вмикає помічник товарів Whatnot або eBay Live. Поле відповіді керування commerce.auction містить лише source, title, priceText, status і at з останнього захопленого auction_update, або null. Він спливає через п’ять хвилин і очищується при зміні джерела, неактивному знімку або перезапуску. Помічник призначений лише для оператора: він не зберігається та не входить до глядацьких трансляцій; особу учасника торгів/переможця відкидають. Скрипти джерел і дані подій аукціону не змінюються. Копіювання чернетки не підтверджує оплату й не створює продажу.

Event Flow audio controls

The Actions overlay accepts actionType: "play_audio" з audioUrl, volume (0–1), and optional audioPlayback: "queue" або "interrupt". Omitting the playback option keeps overlapping playback. Local media continues to use sourceType: "local", localAssetId, і localAssetName. Queue mode holds up to 30 waiting clips with a two-minute limit per clip; interrupt mode replaces that queue's current clip and clears its waiting items.

actionType: "stop_audio" stops Flow Actions audio clips and clears the sound queue. These are overlay control messages, not source chat events or proof that OBS output was heard. Event Flow resolves a configured random sound set to one audio URL before sending the action. See Event Flow setup.
