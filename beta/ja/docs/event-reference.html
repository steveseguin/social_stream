重要： イベントの可用性はソース、権限、取り込み設定によって異なります。ドックや注目表示オーバーレイでイベント付き行を隠すには、次を追加します： &hideevents または &hideallevents。特定のイベントを隠すには次を使います： &filterevents=subscription_gift,new_follower,gifted。これらのフィルターは、次の値を持つ有料行も隠す場合があります： event。イベントマーカーのない通常の寄付行はイベントフィルターに一致しません。他のメッセージフィルターは引き続き適用されます。
取り込み方法を選びます： YouTube、Twitch、Kickでは、 WebSocketモード は通常、より幅広いイベントに対応します。標準DOM取り込みは、ページに実際に表示された行とカードを読み取ります。YouTubeのSuper Chat、Super Sticker、Jewelギフトには両モードで取り込み経路があります。他のギフト、投げ銭、メンバーシップイベントはソースによって異なります。対応経路と必要な設定は各プラットフォームの表を確認してください。
自動化を作りますか？ こちらをご覧ください： Event Flowガイド を参照すると、カスタムトリガー、アラート、ワークフローでこれらのイベントペイロードを使用する方法を確認できます。ガイドには次が含まれます： テンプレート変数リファレンス で文字装飾を確認できます。ギフト額、連続ギフトの計算、編集可能なゲーム例は ゲームと報酬を作る.
ペイロードの形式： 寄付形式のチャット行では次を使ってください： hasDonation 、任意の donoValue。次の値は設定しないでください： event: "donation" を、通常のチャット・投げ銭行に金額があるという理由だけで設定しないでください。固有のイベント名は、実際のプラットフォーム操作や有料アイテム種類にだけ使います。例： superchat, supersticker, gift、または jeweldonation。使う項目： meta は、受信側が実際に必要とし、既存フィールドで表せない追加の構造化データにだけ使ってください。

フィールドの概要

data はここではメッセージオブジェクトを意味し、追加するラッパーではありません。チャット行とメタデータのみのイベントは形式が異なります。カウンターや状態スナップショットでは、次を省略する場合があります： chatname/chatmessage。プラットフォームの表では、 メッセージ は通常のチャット行を表し、文字どおりの次のイベントではありません： event: "message".

フィールド 形式 用途
data.type 文字列 オーバーレイ、フィルター、Event Flowが使うソース識別子。Instagramのライブチャットは次のままにします： instagramlive 、ライブ以外のコメントは次として扱います： instagram。参照先： ソース種類ガイド に派生形、汎用ソース、送信先経路を記載しています。
data.chatname 文字列 メッセージ処理やオーバーレイ以外の出力が使う、ソース提供の表示名。設定したユーザー表示名の別名は、コピーされたドック・オーバーレイ通信ペイロード内だけでこの値を置き換えられます。
data.username 文字列 取得可能な場合のソース上のユーザー名。別名を適用したドック・オーバーレイペイロードでは、元の次の値を保持するため、このフィールドを追加する場合があります： chatname をユーザー操作に使います。標準メッセージ自体は変えません。
data.userid 文字列 プラットフォーム固有のユーザー識別子。ユーザー操作では、次よりこの値を優先します： username および chatname.
data.platform文字列（任意）一部の連携では、次と併せて含めます： type。多くのソースアダプターは省略するため、次を使ってください： type をソースの経路指定に使います。
data.id文字列 | 数値（任意）メッセージまたはイベントの識別子。意味はソースと通信経路によるため、常にプラットフォーム固有のモデレーションIDだと考えないでください。使う値： meta.messageId アダプターが削除同期用に公開している場合。
data.donoValue数値（任意）ソースが提供する数値の米ドル相当額。推定値を含みます。有効な値は0も含めてcurrency.jsの換算より優先します。なければ受信側でhasDonationとソースの文脈から米ドル額を見積もります。元の金額と単位はhasDonationおよび既存のプロバイダーメタデータに保持します。
data.chatbadges配列 | 文字列（任意）バッジ画像URLまたはバッジオブジェクト（type: "img" 付随する値： src, type: "svg" 付随する値： html、または type: "text" 付随する値： text）。転送では、テキストバッジのラベル文字列を任意の次の欄に保持します： rawText から、エスケープ済みの次の値を生成します： text を古いオーバーレイ向けに使います。その後の転送時には、次を再生成してください： text 取得元： rawText。次をエスケープしないでください： text を再度処理しないでください。現在のレンダラーの表示対象： rawText がある場合は文字どおりに扱い、それ以外では従来のエンコード済みテキスト処理を維持します。これは表現形式のフィールドであり、HTML描画の許可ではありません。古いソースは配列の代わりに単一HTML文字列を送る場合があります。バッジ表示オーバーレイは両形式を受け付け、古い拡張機能からの送信でもバッジのHTML・URLをローカルでサニタイズします。不正なバッジがあっても、チャットやメンバーシップメッセージの表示を妨げてはいけません。
data.event 文字列 | 真偽値 システム活動の識別子（例： viewer_update, subscription_gift, giftpurchase）。通常のチャットでは空またはfalseにし、オーバーレイがシステム通知と会話文を区別できるようにします。
data.chatmessage 文字列 メッセージ本文。サニタイズ済みで描画可能なHTMLを含められるのは、次の場合だけです： data.textonly はfalseです。
data.textonly 真偽値 適用対象は次だけです： data.chatmessage. true の意味は、次を描画することです： chatmessage をプレーンテキストとして扱い、タグや実体参照のような文字列をそのまま保持します。本文をデコードしたり、HTMLサニタイズしたり、書式タグを追加したりしないでください。イベントのスタイルは表示要素に適用します。 false の意味： chatmessage にはサニタイズ済みで描画可能なHTMLを含められます。フラグのない古いメッセージも、そのHTML動作を保ちます。他の通常フィールドはプレーンテキストですが、次のようなメディアフィールドは例外です： chatimg および contentimg。プレーンテキストのフィールドは次で表示します： textContent、またはHTMLテンプレートを組み立てる際に1回だけエスケープします。内容を削除したり、繰り返しデコードしたりしないでください。
data.contentimg 文字列（任意） コンテンツ画像または対応メディアのURL。拡張機能とデスクトップアプリでは、任意で有効にする次の設定： allowExternalGifs 設定は、メッセージ本文またはHTMLリンク内の最初の直接HTTP(S) GIFリンクを、空のフィールドに設定します。URLのパスは次で終わる必要があります： .gif （大文字・小文字を区別しない）。クエリパラメーターとフラグメントは保持されます。APIキーは不要で、次を保持します： chatmessage と既存の添付を保持し、次に従います： removeContentImage。任意の hideExternalGifUrl 設定で次が追加されます： meta.hideExternalGifUrl: true。ドックと注目表示オーバーレイは、画像を読み込んでから一致するGIFリンクだけを隠し、前後のテキストと元のペイロードは保持します。画像の読み込み失敗やタイムアウト時は添付領域を閉じ、リンクを残します。GIF専用オーバーレイは、画像データの取得に失敗すると直接画像表示を試みます。アニメーション時間がわからない場合は設定された表示時間を使い、読み込みが失敗・停止したらキューを進めます。次の値は追加しません： event またはソースの次の値を変更します： type。外部画像の内容はフィルタリングしません。ホストが埋め込みを禁止していると読み込めない場合があります。
data.membership 文字列 読みやすいメンバーシップ状態。例： MEMBERSHIP, new_sponsor, gift_recipient。各画面はバッジ、フィルター、お知らせに使います。
data.subtitle 文字列 補足説明（メンバー継続期間、ティアのアップグレード、ギフトの贈り主など）。オーバーレイで表示名の下に入れられるよう、短いプレーンテキストにしてください。
data.hasDonation 文字列 金銭または仮想ギフトの金額（$5.00, 500 bits, 300 coins）。次の場合でも設定します： data.event は空欄にし、寄付オーバーレイで検出できるようにします。
data.meta 数値 | オブジェクト | 文字列（旧形式） 単一のカウンター（視聴者、フォロワー、登録者）には単純な整数を、詳細な文脈にはオブジェクトを使ってください。Twitch DOMの次のイベントなど、一部の古いイベントは community_highlightは文字列を持ちます。オブジェクトのプロパティを読む前に、イベント固有の形式を確認してください。新しい構造化情報はオブジェクトに格納します。
data.firsttime 真偽値 設定する値： true 初回チャットの検出とローカルデータベースが有効で、そのユーザー／ソースについて保存される最初のチャットメッセージである場合。ドックはこれを初回チャットの強調表示と初回の通知音フィルターに使用します。任意の初回バッジ設定を有効にすると、葉のバッジが次の先頭に追加されます： chatbadges.
data.lastactivity 数値 初回チャット検出とローカルデータベースが有効な場合の、そのユーザーについて前回保存したチャット活動のUnixタイムスタンプ（秒）。完全な新規ユーザーでは省略します。

オーバーレイ操作の通信は、取り込んだチャット・イベントとは別です。更新済みの受信側は次を使います： ssnControl のエンベロープには配信識別子が含まれます： id、注目表示 target、任意の返信チャンネルとスナップショットクライアントIDを使います。既存の注目表示本文は維持します。公開の注目表示操作はチャンネル7、Actionsは引き続きチャンネル6を使います。PollとMapの状態にはホストの次の値を含めます： epoch, revision および reset のマーカーを使います。Timer、Ticker、Spotifyが使う値： ssnState エポックとリビジョンが含まれます。これらのマーカーはホストの状態を表し、復元された投票／チャット履歴を表すものではありません。ソースは、キャプチャしたメッセージに制御エンベロープのフィールドを追加しないでください。受領の確認は、アクションの完了やOBSでの表示を保証しません。参照： 移行状況 に対応機能、返信の調整、再接続の制限を記載しています。

Phrase Guessが使うネイティブの値： {response: text} server2のチャット返信用リクエストと {action: "phraseGuessResponse", value: {type: "bot", chatname: name, chatmessage: text}} をドック専用のお知らせに使います。ホストはserver3の受信メッセージを有効にする必要があります。ホスト操作を無効にすると、これらの要求も引き続きブロックされます。ドックのお知らせは、次の値を持つ通常のボットチャット行として転送されます： textonly: trueへ送り、取り込みソースのチャット入力欄へは送りません。従来のAPIモードでは既存のコマンド形式を保持します。

Metaの規約

ダッシュボードや自動化の整合性を保つため、次を拡張するときはこれらの規約に従ってください： data.meta:

  • viewer_update, follower_update, subscriber_update、および likes_update 単純な整数を使用します： meta の値。 likes_update はプラットフォームの正式な合計です。受信側は加算せず、その値を表示値として設定してください。バックグラウンドスクリプトは視聴者数を次へ集計します： viewer_updates 次をキーとするオブジェクトを使用します： data.type.
  • giveaway_state は管理対象の表示向けにホストが生成する、メタデータのみのスナップショットです。 meta.giveaway バージョン2には次が含まれます： giveawayId、永続的な roundId/epoch、増加する generation を新しいラウンド間で保持し、 revision 同じラウンド内で、 status, open, draw, keyword, count, ticketCount、固定された config、最大120件のプレビュー entrants、最新20件の winners。各項目が公開する値： id, name, platform および tickets。当選者には次を追加します： drawnAt 、付与された points。Coin Flip Potは次を追加します： outcome。Number Huntは次を追加します： number 公開される値： low, high 、最近の guessesを含めますが、シークレットは含めません。受信側はプレゼント企画IDで絞り、古い世代・リビジョンを破棄します。これらは表示用サンプルであり、完全なチケット台帳や支払い指示ではありません。ウォレットキー、残高、予約は視聴者向けスナップショットに含めません。ホストは次へ公開します： giveaway のP2Pラベルと、有効なオーバーレイWebSocketフィードに送ります。OBSに表示されていることを意味しません。 ガイド.
  • meta.giveawayControlResult にEvent Flowのプレゼント企画アクションの結果を格納します（ok、任意の error, giveaway または simulated). meta.giveawayHandled に、参加・購入のフローアクションですでに処理したプレゼント企画IDを列挙し、自動チャットコマンドによる再課金を防ぎます。エディターが追加する値： meta.economyTest はプレゼント企画アクションのシミュレーション用であり、ソースプラットフォームのイベントや認証情報ではありません。
  • video_stats 構造化された次の値を使用します： meta オブジェクトは外部エンコーダー・サーバーの稼働状態用で、次を含めます： provider, label, online, bitrateKbps, rttMs, bufferMs、パケット損失・ドロップのカウンター、任意のコーデック詳細。
  • 寄付形式のイベントには説明用オブジェクトを含める場合があります。例： { amount, currency, supporter } をKickに使い、 { bits } をTwitchのCheerに使います。メンバーシップイベントはソース固有のメタデータを持ち、自動的に金銭的な寄付になるわけではありません。
  • 正規化したStripe、Ko-fi、Buy Me a Coffee、FourthwallのWebhookメッセージには、プロバイダー単位の次の値が含まれます： meta.webhookIdには、プロバイダーの安定したイベント識別子をコピーします。これにより、受信側ページで再試行や複数の通信経路による重複を抑止できます。
  • Twitchのレイドが渡す値： { fromId, fromLogin, viewers }。他のソースでは異なります。Whatnotが使う値： meta.numRaiders。一方、SharePlayでは任意の次の値を使います： meta.fromLogin/meta.viewers。レイドのメタデータを読む前に、ソース固有の行を確認してください。
  • Twitch EventSubの報酬交換が提供する値： meta.rewardId, cost, rewardTitle, redemptionId、従来の alias を準備済みメッセージとともに渡します。DOMの報酬カードや他のソースでは、フィールドが少ない、または異なる場合があります。
  • user_banned はモデレーションウィジェット向けのメタデータのみです。意図的に省略する値： chatname および chatmessage。使う項目： meta.username, meta.displayName, meta.avatarUrl、および meta.profileUrl.
  • ソース操作による削除同期に対応するチャット通信では、プラットフォーム固有のチャット識別子を次として提供してください： meta.messageId を使い、ドック内部の次の値には依存しないでください： data-mid の値。
  • ソースの削除が使う値： {delete: {type, id}} を既知のドックメッセージIDに使うか、 {delete: {type, meta: {messageId}}} をプラットフォーム固有のメッセージIDに使います。既知のIDなら一致するメッセージだけを削除します。対象ユーザーだけがわかる場合は、次を送信します： {delete: {type, userid}} または {delete: {type, chatname}} を使用して、そのプラットフォームでの対象ユーザーのメッセージを削除します。対象ユーザーの代わりにモデレーターの識別情報を使用しないでください。受信した削除に、任意のドックからプラットフォームへのモデレーション同期設定は必要ありません。
  • SSAppのソース識別メタデータが追加する場合がある値： meta.ssnAccountRole, meta.ssnSourceId、および meta.ssnSession ソースに通常以外のアカウントの役割が割り当てられている場合。
  • Event Flowでは、次を設定して強調表示を依頼できます： meta.featured = true をチャットペイロードに設定すると、ドック・注目表示オーバーレイで自動的にメッセージを注目表示します。
  • AI Event Overlay： アクション showAiEventOverlay は、トリガーとなったメッセージのコピーを、ラベル aievent-CONFIGURATION_IDに送信し、 meta.aiEventOverlay: {profile: "CONFIGURATION_ID"}を追加します。既存のメッセージフィールドとオブジェクト形式のメタデータは保持されます。スカラー値のメタデータは meta.valueとして保持されます。これは宛先を指定した配信であり、新しいプラットフォームイベントではありません。元のメッセージは変更されません。詳細： 設定ガイド.
  • 任意 meta.aiEventOverlay.variation は、保存されたオーバーレイ設定で承認済みの語句を完全一致で選択します。視聴者のテキストとメタデータは、生成後にテンプレートの各フィールドへ挿入されます。
  • AI Event Overlay の表示リクエストには、プロファイルとその専用の非公開表示トークンが必要です。設定と API キーは、ローカルの SSN ポップアップでのみ管理します。応答形式は {aiEventResponse: {target, value}} または {aiEventResponse: {target, error}}. 生成結果に含まれるフィールドは template, duration, warnings, 任意のメディアデータ URL の格納先は image/audio.
  • ポイントで支払うAIオーバーレイ報酬は aiEventPresentation (id, profile, expiresAt, result, message) を使用し、aiEventDelivered（配信ID）で受信を確認します。ポイントの引き落とし記録と返還額はホスト側に保持されます。
  • Event Flowでは、次を設定してドックのピン留めを依頼できます： meta.pinned = true。任意の meta.pinnedTarget はピン留め対象を、次が一致するドックに限定します： label.
  • Event Flowの感熱印刷結果は次に記録します： meta.thermalPrintResult (success 、任意の code/error）に格納し、チャットイベントと他のメタデータを保持します。メタデータが数値などのオブジェクト以外の場合、診断情報はアクション結果に残し、イベントは変更しません。
  • 任意で有効化するSSNステッカー報酬： event: "sticker" の送信先は次だけです： stickers のオーバーレイラベルへ、ロイヤルティポイントの引き落とし後に送ります。設定する値： platform および type を元のメッセージの次の値に設定します： type、次を保持します： chatnameで、次は空です： chatmessage, textonly: true、および contentimg には、同梱画像の相対パス、または配信者が承認したHTTPSメディアURLを格納します。 meta.sticker に含まれる値： id, pack, name, cost, duration （秒）、 motion, redemptionId、および expiresAt （Unix時刻、ミリ秒）。これはSSNの報酬であり、プラットフォームの寄付やネイティブのチャンネルポイントイベントではありません。参照先： ギャラリーと設定ガイド.
  • ステッカープレイヤーは、次の制御パケットを返します： {action: "stickerReceipt", meta: {sticker: {redemptionId, success}}} を、画像の読み込みが完了または失敗したときに送信元へ返します。接続済みの次の対象からの受領通知のみが使用されます： stickers のピアが、待機中の報酬交換を確定します。配信失敗や未確認の場合は返金します。この制御パケットはチャットイベントではありません。セッションごとに有効なステッカー表示を1つだけにすることをおすすめします。
  • AIステージオーバーレイのコマンドが使う形式： { action: "aiOverlay", target, meta } またはドックが操作する共同司会再生では、次を使います： { action: "cohostOverlay", target, meta }。次のようなコマンド詳細はすべて保持します： command, text, emotion, avatar、および tts 格納先： meta.
  • プラットフォームが複数のカウンターをまとめて提供する場合は、明確なキーを持つ構造化オブジェクトを優先してください（meta.viewer_count, meta.follower_count）を使い、文字列に複数の役割を持たせないでください。
  • コマースオーバーレイは、次の中のスナップショットオブジェクトを使ってください： meta （例： auction_update および commerce_update）を使い、場当たり的な最上位フィールドは避けてください。

YouTube登録者通知（new_follower)

Social Streamでは、次を使って新しいYouTube登録者を検出できます： myRecentSubscribers のAPIエンドポイント。Streamlabsの登録通知に似た仕組みです。

動作の仕組み：

  • YouTube APIで最近の登録者を5分ごとに取得します
  • 確認済みの登録者をlocalStorageで追跡し、新しい登録者を検出します
  • 送信する値： new_follower イベントに、登録者の名前、アバター、チャンネルIDを含めます
  • 登録通知メッセージは既定で無効です。有効にすると、次の現在の翻訳文字列を使います： alert-just-subscribed
  • 既定では新規登録者が3人を超えるまとまった更新を集約し、再接続時にオーバーレイやEvent Flowへ大量に流れないようにします
  • 拡張機能設定でWebSocketモードの有効化が必要です

制限事項（Social StreamではなくYouTube APIの制約です）：

  • 配信までの時間は保証されません – SSNは5分ごとにポーリングしますが、APIの結果は遅延したり不完全だったりする場合があります。固定の4時間枠を前提にしないでください。
  • 公開の登録のみ – 登録チャンネル一覧を非公開にしている登録者は、アラートの対象になりません。YouTubeでは登録情報は既定で非公開です。
  • チャンネル所有者のみ – 登録者アラートを受信できるのは、自分が所有し、そのアカウントで認証したチャンネルのみです。
  • API利用枠の使用量 – ポーリング1回につきAPIを1単位消費します。5分間隔では、1日あたり約288単位を使用します（標準の1日あたりの割り当ては10,000単位）。

For explicitly streakable gifts with a repeatEnd flag, TikFinity sends only the completed streak and its final quantity; intermediate count updates are not forwarded. Non-streak gifts and older payloads without that flag continue through immediately. Native DOM gift streak updates and TikFinity gift rows include meta.tiktokGiftStreakId, meta.tiktokGiftCount、および meta.tiktokGiftQuietMs これにより、オーバーレイで繰り返しの更新をまとめられます。従来の連続ギフトIDはページインスタンスごとに固有です。ギフトのメタデータには次が含まれる場合もあります： tiktokGiftMessageId （元のTikTokメッセージID）、 tiktokGiftSenderId, groupId, giftId, giftName, streakable、および repeatEnd。ネイティブIDは異なる取り込みウィンドウ間の同じギフトを識別します。0以外のグループIDを送信者ID・ギフトIDと組み合わせることで、連続ギフトの累計更新を識別します。SSAppのWebSocket取り込みでも、連続ギフト確定後に同じフィールドを提供します。その値は count は互換性のために保持されます。各ギフトの転送時に寄付の切り替え設定が確認されます。TikTokの寄付を無効にすると、次が削除されます： hasDonation および donoValue ギフトイベントとメタデータを保持します。TTSはこれらの識別情報を使用して更新をまとめ、完了済みの重複を最大10分間抑制します（上限付きキャッシュ）。TikTokのギフトは送信者、数量、ギフト名の順に読み上げます。古いペイロードでは既存の連続ギフトIDとメッセージ本文を使用し、ギフトのテキストだけから識別情報を推測することはありません。TikTokギフトの読み上げには、UI言語とは別に、選択したTTS／音声の言語を使用します。告知の動詞は英語、スペイン語、ポルトガル語、フランス語、ドイツ語、イタリア語、オランダ語に対応しています。その他の言語では、英語の動詞を加えず、送信者、数量、ギフト名を使用します。簡略TTSでも、この中立的な形式を維持します。ギフト名はプラットフォームから提供されたままです。ギフト一覧やチャットメッセージを自動翻訳したり、配信の言語を推測したりする機能ではありません。

連続ギフトの更新では、個数と寄付ラベルは累計です。1、2、3はギフト3個であり、6個ではありません。合計を計算する側は、その連続IDですでに確認した最大量からの増加分だけを加えてください。標準取り込みは旧ギフトクラスと現在の画像・個数行に対応し、どちらも次を保持します： event: "gift" および hasDonation。価格不明の場合はギフト数・名前を表示用に保持し、1ギフトあたり1コインの米ドル換算を使います。ソースが提供する donoValue が優先されます。表示されたギフトのメタデータから次が提供される場合があります： coinsPerGift または diamondsPerGift を優先し、必要な場合だけギフト表や既定値を使います。標準・TikFinityのコイン推定とSSAppネイティブのダイヤ推定は、それぞれ従来の別々の換算を使います。どちらも現金の受取額を保証しません。

支払い成功の自動化には、次を設定します： イベント種類（詳細）（Event Type (Advanced)） トリガーの設定先： 独自イベント: payment_succeededを選び、ソースをWhatnotに絞ります。既存の条件やテンプレートでは、そのイベントの次の値を使えます： userid, chatname, subtitle および meta.orderId を直接使います。通知に必要な詳細が含まれていれば、以前の購入を記憶している必要はありません。

オークションの終了や商品の売却済み表示は、支払い成功を確認するものではありません。これらの通知は、支払い済みの次のイベントとして送信しません： purchase イベントとして扱い、寄付額は設定しません。成功イベントは、次を受信した場合だけ送信します： payment_succeeded 通知を受信した場合です。取り込み処理は支払い完了を定期照会せず、販売から推測もしません。他の paymentStatus 値は、キャプチャされたパケットで明示的に提供された場合にのみ転送されます。存在しない識別子は省略されます。商品IDだけでは複数の販売を指す可能性があるため、通知の関連付けには提供された注文／オークションIDを使用してください。キャプチャは購入を記憶せず、支払い更新との照合も行いません。そのようなワークフローはEvent Flowで明示的に設定する必要があります。既存の2つのキャプチャブリッジから短時間に届く重複パケットは抑制されます。元の注文／支払いオブジェクトは転送されません。

Joystick

  • 別のボット認証ソースは次を送信しません： viewer_update。ログイン済みのウェブサイトソースは、以下の説明どおり、ページのソケットから視聴者数を受け取れれば送信します。

ギフトとコマース

使う項目： event: "gift" をギフトに使い、 giftcontribution をギフトへの有料支援に使い、 giftfunded を資金達成に使い、 purchase を商品販売に使います。これらの名前はプロバイダーや、現物・デジタルといった商品種類によらず共通です。従来の次の名前は用途を限定してください： giftpurchase イベントはメンバーシップギフト用です。Throneは以前この名前を誤用していましたが、現在は次を送信します： gift。既存のメンバーシップ生成元は変わりません。Throneの独自イベント名フィルターは、次へ切り替えてください： gift。寄付フィルターの変更は不要です。

Buy Me a Coffee donation.created 金銭的なサポートの情報を保持します。 extra_purchase.created および commission_order.created は次になります： purchase. wishlist_payment.created は次になります： giftcontribution その支払い金額のみを使用します。 meta.commerce.completed 新たな金額付きの行を出力せず、プロバイダーの完了フラグを記録します。 membership.started は次になります： new_subscriber ティアの格納先： membershipとなり、次の値を誤用しなくなりました： hasDonation をティア名に使います。サブスクリプション開始時の金額は、独立した支払い済み請求として扱いません。テスト、返金済み、失敗、未対応の更新・ライフサイクルイベントでは有料アラートを生成しません。非公開の支援者メモは省略します。

FourthwallはORDER_PLACED（purchase）、GIFT_PURCHASE（gift、受取人が他者）、DONATION（通常の寄付行）、SUBSCRIPTION_PURCHASED（new_subscriber）。既存の注文合計では次を保持します： hasDonation を後方互換性のために使い、次の印を付けます： meta.commerce.legacyDonationValue: true。これは新しい商品販売の既定ルールに対する明示的な例外です。ギフトカード適用の注文は、寄付額を含まない購入アラートを送信します。注文合計から新たな請求額を確実に推測できず、ギフト購入はすでに計上済みのためです。請求先の名前やメールアドレスを公開の識別情報に使いません。ダッシュボードのテストイベントや注文更新で有料アラートは生成しません。

これらのアダプターは、既存の転送、ボット操作、Event Flow、宛先経路を保持し、次を使います： meta.webhookId による重複除外を使います。公開名、プレーンテキストのメッセージ、判明している商品名を次で提供します： subtitle、ISOの meta.commerce.currency を、該当する場合は数値の寄付額と併せて含めます。返金の会計処理や新しい受信認証は追加しません。プロバイダーの既存の設定済みWebhook経路を使ってください。

meta.monetization.commerce 格納先： monetization_update にはenabled、qr、position、display（first/cycle）、seconds、公開items配列を格納します。各項目はname、url、image、任意のamount（不明ならnull）、currency、purpose（shop/gift/support/membership）を持ちます。これらは配信者が入力した紹介情報であり、支払い証拠ではありません。追加・編集で寄付・購入イベントは発生しません。汎用オーバーレイが使う値： mode=commerce; view=both|showcase|card|alerts はプロモーションとアクティビティを分離します。任意のURLパラメーターstyle、scale、cardevery、cardfor、onlytypeで表示を制御します。既存のプロバイダーモードでも、viewとスケジュールの制御を使用できます。参照： 設定ガイド.

配信者の音声コマンド（デスクトップのプレビュー版）

Event Flowの この言葉を話したとき… トリガーは、SSAppから信頼されたローカルマイクのコマンドを受け取ります。その内部アクションコンテキストでは次を使用します： chatname: "Host", type: "hostvoice"、認識したフレーズの格納先： chatmessage、および textonly: true。これはプラットフォームからの受信イベントでも、新しいチャットの通信方式でもありません。チャット経由でこれらのフィールドを送っても、音声トリガーは起動しません。

商品表示の操作

既存の monetization_update スナップショットには次が含まれる場合があります： meta.monetization.commerce.live：保存済みスケジュールならnull、または {mode: "show" | "hide", url?: "https://...", until: 0 | epochMilliseconds}。Showは保存済み商品URLと完全一致で照合し、商品がなければカードを表示しません。untilが正の値なら期限後に保存済みスケジュールへ戻り、0なら変更またはSSNの再起動まで続きます。Hideは商品紹介を隠すだけで、有料アクティビティのアラートは抑止しません。

commerce.viewerURL は公開された読み取り専用ショップURL、または空文字列です。ある場合、紹介用QRコードはそこへリンクします。SSNのセッションや公開キーは含みません。商品は引き続き次に保持します： commerce.items。表示操作、インポート、公開によって寄付・購入イベントは発生しません。参照先： 商品操作 をEvent FlowとリモートAPIで使います。

Event Flowの commerceControl アクションは、直接またはChromeからの応答を最大8秒待ちます。通常のイベントペイロードではイベントを保持し、次を追加します： meta.commerceControlResult: {success: true, commerce: controlState} または {success: false, error: "..."}。既存の値が数値、配列、その他のオブジェクト以外の形式の場合： metaの場合はメタデータを変更せず、診断情報を次として返します： commerceControlResult を代わりにアクション結果へ格納します。操作が失敗すると、元の支払いイベントは抑止せず、その連鎖の後続アクションを止めます。タイムアウトは操作が適用されなかった証明ではありません。Nextなどの相対操作を再試行する前に状態を確認してください。成功はローカルの選択・非表示・スケジュール状態を確認するもので、OBSでの表示や公開ページとの同期は確認しません。

名前付きのStream Deck・APIワークフロー

対象の 名前付きワークフロートリガー は、次を含む内部Event Flowメッセージを作成します： type: "api", event: "workflow_trigger", chatname: "Stream Deck / API"、空の chatmessage、および textonly: true。その meta.workflow オブジェクトにはトリガー名と、呼び出し側が指定するJSONの次の値を含めます： data オブジェクトです。次のようなテンプレートで値を読み取ります： {meta.workflow.data.minutes}。そのトリガーに明示的に一致する、保存済みで有効なフローだけを評価します。これは受信する視聴者・チャットイベントではなく、チャットとして配信しません。これらのフィールドをチャットにコピーしても、名前付きトリガーは起動しません。

NinjaChatter視聴者機能の試験導入

実験的なペアリング済み拡張機能コネクターは、表示専用の行を次の値付きで送信します： type: socialstreamchat, platform: ninjachatter、および textonly: true. meta.ninjachatter が持つ値： origin: audience、説明用の provider、公開の room IDを使います。これらの行はプラットフォームへの返信、ボット、Event Flowトリガー、ポイント処理を通りません。プロバイダーが表示されていても、認証済みという意味ではありません。従来のNinjaChatterソース取り込みに含まれる値： meta.ninjachatter.room をルームごとの重複抑止に使います。

Cheerは独立した認証付きの要求・結果経路を使い、特別なチャットコマンドは使いません。固定プリセットが送信する既存のActionsオーバーレイイベント： show_text メッセージを3秒間表示します。受信は通信として受け付けたことを示し、OBSでの表示確認ではありません。視聴者のペイロードから任意のアクションを選ぶことはできません。NinjaChatterでは試験機能は既定で無効です。Electronは、新しい非公開ペアリングの境界を検証できるまで既存の転送を維持します。

コマースの枠ボードと最近の売上

既存の monetization_update イベント（type/platform: socialstream）には次も含まれます： meta.monetization.boards。その board に含まれる値： title, style （spots/teams）、 columns (1–20), visible、最大120件の spots。各枠には文字列の次の値があります： id、プレーンテキストの label, status （available/claimed/revealed）と result （プレーンテキスト。公開するまで空欄）。確保や公開は配信者が入力する表示状態であり、購入の証明やランダムな割り当てではありません。

boards.sales に最近の記録を最大100件格納します： id, title、任意の amount （不明な場合はnull）、 currency, quantity, source、および at （記録時点のUnix時刻、ミリ秒）。 automatic で収集を有効にし、 salesVisible で表示と次を制御します： revision は変更時に増加します。自動収集で受け付けるのは次だけです： purchase イベントをShopify、eBay出品者、Fourthwall、Ko-fi、Buy Me a Coffeeから受信します。非公開・テストイベントは除外します。オークションのメタデータ、投げ銭、ギフト、枠の確保を購入として扱いません。自動記録は注文合計、出品価格、寄付額を商品価格に代用しません。手動記録が使う値： source: "Host confirmed".

状態はこのインストール環境の非公開収益化ストレージに保持します。公開スナップショットには配信重複除外ID、購入者識別情報、シークレットを含めません。明示的に表示する売上は、削除用のイベントIDを保持します。返金分は配信者による削除が必要です。重複購入IDは別に最大2,000件記憶し、表示履歴の消去後も残します。既存の getCommerceState 応答には次が含まれます： commerce.boards; commerceControl は、次のガイドにあるボード・売上コマンドを受け付けます： ボードガイド。手動編集は更新した状態を配信しますが、購入イベント、寄付合計、有料報酬は作成しません。ホストのスナップショットが35秒間届かないと、オーバーレイは非表示になります。

出品者向け手順の追加： commerce.boards.board.id でボードの世代を識別します。手動の saleAdd が提供する場合のある値： boardId および spotId を使用して、販売の記録と枠の確保を一括で行います。最近の履歴に残っている、関連付け済みの重複した販売は拒否されます。 saleRemove 付随する値： reopenSpot: true ボードの世代がまだ一致している場合に限り、その枠を解放します。公開される販売情報には、これらの操作用の関連付けフィールドは含まれません。任意の platform を手動売上に設定すると、フィルタリング用のソースを保持します。一方、 source: "Host confirmed" で確認方法を識別します。 amount は項目の合計で、次を含みます： quantity。eBayの支払い済み注文アダプターの meta.ebayPurchase.quantity は保持されます。

salesSettings.auctionSource でWhatnotまたはeBay Liveの商品ヘルパーを有効にします。制御応答の commerce.auction には、最後に取り込んだ次のイベントのsource、title、priceText、status、atだけを格納します： auction_update、またはnullです。5分で期限切れになり、ソース変更、アイドル状態のスナップショット、再起動時に消去します。ヘルパーは操作担当者専用で、永続保存も視聴者への配信への追加も行いません。入札者・落札者の識別情報は破棄します。ソーススクリプトとオークションイベントのペイロードは変わりません。下書きをコピーしても、支払いの確認や売上の作成は行いません。
