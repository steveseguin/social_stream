Настройки захвата, фильтры и соглашения о полезной нагрузке
Важно: Доступность событий зависит от источника, разрешений и настроек захвата. Чтобы скрыть строки с маркером события в док-панели или оверлее выделенных сообщений, добавьте &hideevents или &hideallevents. Чтобы скрыть выбранные события, используйте &filterevents=subscription_gift,new_follower,gifted. Эти фильтры также могут скрывать платные строки, содержащие event; обычные строки пожертвований без маркера события не совпадают с фильтрами событий. Остальные фильтры сообщений продолжают действовать.
Выберите способ захвата: Для YouTube, Twitch и Kick Режим WebSocket обычно обеспечивает более широкий охват событий. Стандартный захват DOM читает строки и карточки, которые действительно отображены на странице. YouTube Super Chat, Super Sticker и подарки Jewel захватываются в обоих режимах; другие подарки, чаевые и подписки зависят от источника. Поддерживаемые пути и необходимые настройки приведены в таблицах платформ.
Создаёте автоматизацию? Посмотрите Руководство по Event Flow чтобы узнать, как использовать эти данные событий в собственных триггерах, уведомлениях и процессах. Руководство включает Справочник переменных шаблонов для форматирования текста. Суммы подарков, подсчёт серий и редактируемые игры описаны в Создавайте игры и награды.
Структура данных: Строки чата с пожертвованиями должны использовать hasDonation и необязательный donoValue. Не задавайте event: "donation" лишь потому, что обычная строка чата или чаевых содержит сумму; используйте конкретные имена событий только для настоящих действий платформы или типов платных элементов, например superchat, supersticker, gift, или jeweldonation. Используйте meta только для дополнительных структурированных данных, которые действительно нужны получателям и ещё не представлены существующими полями.

Обзор полей

data здесь означает объект сообщения, а не дополнительную оболочку, которую нужно добавить. Строки чата и события только с метаданными имеют разные структуры: счётчики и снимки состояния могут не содержать chatname/chatmessage. В таблицах платформ сообщение описывает обычную строку чата, а не буквальное event: "message".

Поле Структура Использование
data.type строка Идентификатор источника, используемый оверлеями, фильтрами и Event Flow. Instagram сохраняет чат трансляции как instagramlive а комментарии вне эфира — как instagram. См. Руководство по типам источников для вариантов, общих источников и исходящей маршрутизации.
data.chatname строка Отображаемое имя, переданное источником и используемое обработкой сообщений и выводами вне оверлеев. Настроенный псевдоним отображаемого имени может заменять его только в копиях данных для передачи док-панелям и оверлеям.
data.username строка Имя пользователя источника, если доступно. Данные док-панели или оверлея с псевдонимом могут добавлять это поле для сохранения исходного chatname для действий с пользователем; каноническое сообщение не меняется.
data.userid строка Идентификатор пользователя на платформе. Действия с пользователем предпочитают это значение вместо username и chatname.
data.platformстрока (необязательно)Некоторые интеграции включают это вместе с type. Многие адаптеры источников его не передают; используйте type для маршрутизации источников.
data.idстрока | число (необязательно)Идентификатор сообщения или события. Его смысл зависит от источника и способа передачи; не считайте, что это всегда собственный идентификатор модерации платформы. Используйте meta.messageId когда адаптер предоставляет его для синхронизации удаления.
data.donoValueчисло (необязательно)Числовой эквивалент в долларах США, переданный источником, включая оценки. Допустимое значение, в том числе ноль, имеет приоритет перед пересчётом currency.js. Без него получатели оценивают сумму в долларах по hasDonation и контексту источника. Исходные суммы и единицы остаются в hasDonation и существующих метаданных провайдера.
data.chatbadgesмассив | строка (необязательно)URL изображений значков или объекты значков (type: "img" с src, type: "svg" с html, или type: "text" с text). Ретранслятор сохраняет буквальную подпись текстового значка в необязательном rawText и создаёт экранированный text для старых оверлеев. При последующих этапах пересылки пересоздавайте text из rawText; не экранируйте text снова. Текущие средства отображения показывают rawText буквально, если присутствует, и сохраняйте прежнюю обработку закодированного текста в остальных случаях. Это поле представления, а не разрешение показывать HTML. Старые источники могут передавать одну HTML-строку вместо массива. Оверлеи значков принимают оба формата и локально очищают HTML и URL значков, в том числе от старого расширения. Недопустимые значки не должны мешать отображению сообщения чата или подписки.
data.event строка | логическое значение Идентификатор системной активности (например viewer_update, subscription_gift, giftpurchase). Для обычного чата оставляйте пустым или false, чтобы оверлеи отличали системные уведомления от разговорного текста.
data.chatmessage строка Тело сообщения. Оно может содержать очищенный и пригодный для отображения HTML только при data.textonly равно false.
data.textonly логическое значение Применяется только к data.chatmessage. true означает отображать chatmessage как обычный текст, сохраняя буквальные теги и текст, похожий на HTML-сущности; не декодируйте, не очищайте как HTML и не добавляйте теги форматирования в это тело. Применяйте оформление события к отображаемому элементу. false означает chatmessage может содержать очищенный и пригодный для отображения HTML; старые сообщения без этого признака сохраняют такое HTML-поведение. Остальные обычные поля — простой текст, за исключением медиа-полей, например chatimg и contentimg. Показывайте обычные поля с помощью textContent, либо экранируйте один раз при создании HTML-шаблона; не удаляйте и не декодируйте повторно их содержимое.
data.contentimg строка (необязательно) URL изображения контента или поддерживаемого медиафайла. В расширении и настольном приложении включаемая по желанию функция allowExternalGifs настройка заполняет пустое поле из первой прямой HTTP(S)-ссылки на GIF в тексте сообщения или HTML-ссылке. Путь URL должен оканчиваться на .gif (без учёта регистра); параметры запроса и фрагменты сохраняются. API-ключ не нужен; сохраняется chatmessage и существующие вложения, а также учитывает removeContentImage. Необязательный hideExternalGifUrl настройка добавляет meta.hideExternalGifUrl: true; док-панель и оверлей выделенных сообщений скрывают соответствующую GIF-ссылку только после загрузки изображения, сохраняя окружающий текст и исходные данные. При ошибке или тайм-ауте контейнер вложения сворачивается, а ссылка остаётся видимой. Оверлей только для GIF пробует прямой показ изображения, если загрузка байтов не удалась, и использует заданное время показа, когда длительность анимации недоступна; при ошибке или зависании загрузки очередь продолжается. Это не добавляет event или измените источник type. Внешние изображения не проходят фильтрацию содержимого и могут не загрузиться, если хост запрещает встраивание.
data.membership строка Читаемое состояние подписки, например MEMBERSHIP, new_sponsor, gift_recipient. Поверхности используют его для значков, фильтров и объявлений.
data.subtitle строка Дополнительное описание (срок подписки, повышение уровня, кем подарено…). Делайте его коротким и текстовым, чтобы оверлеи могли разместить его под отображаемым именем.
data.hasDonation строка Денежная сумма или количество виртуального подарка ($5.00, 500 bits, 300 coins). Заполняйте даже если data.event пустой, чтобы оверлеи пожертвований могли его распознать.
data.meta число | объект | строка (устаревший вариант) Для одиночных счётчиков зрителей, фолловеров и подписчиков используйте целые числа, а для более подробного контекста — объекты. Некоторые старые события, например Twitch DOM community_highlight, содержат строку. Перед чтением свойств объекта проверяйте структуру конкретного события; новые структурированные сведения должны находиться в объекте.
data.firsttime логическое значение Установить в true когда включены определение новых участников и локальная база данных и это первое сохранённое сообщение этого пользователя и источника. Док-панель использует признак для выделения новых участников и фильтров первого звукового сигнала; необязательная настройка значка нового участника добавляет листок в начало chatbadges.
data.lastactivity число Метка времени Unix в секундах для предыдущей сохранённой активности чата этого пользователя, когда включены определение новых участников и локальная база данных. Для совершенно новых пользователей не передаётся.

Правила метаданных

Передача управления оверлеями отделена от захваченного чата и событий. Обновлённые получатели используют ssnControl оболочку с идентификатором доставки id, функцию target, необязательный канал ответа и идентификатор клиента снимка. Существующие тела данных функций сохраняются. Публичное управление функциями использует канал 7; Actions сохраняет канал 6. Состояние Poll и Map включает значение ведущего epoch, revision и reset маркер; Timer, Ticker и Spotify используют ssnState с эпохой и ревизией. Эти маркеры описывают состояние ведущего, а не восстановленную историю голосов или чата. Источники не должны добавлять поля управляющей оболочки в захваченные сообщения. Подтверждение получения не доказывает завершение действия или видимость в OBS. См. состояние миграции для поддерживаемых функций, согласования ответов и ограничений переподключения.

Phrase Guess использует собственный {response: text} запрос для ответов чата server2 и {action: "phraseGuessResponse", value: {type: "bot", chatname: name, chatmessage: text}} для объявлений только в док-панели. Ведущий должен включить входящие сообщения server3; отключение управления ведущим по-прежнему блокирует эти запросы. Объявления док-панели пересылаются как обычные строки чата бота с textonly: true, не отправляя их в поля чата источников захвата. Устаревший режим API сохраняет существующий формат команд.

Чтобы панели и автоматизация оставались согласованными, следуйте этим правилам при расширении data.meta:

  • viewer_update, follower_update, subscriber_update, и likes_update используют обычное целое число meta значение. likes_update — достоверный итог платформы: получатели должны устанавливать показанное значение, а не прибавлять его. Фоновый скрипт объединяет количество зрителей в viewer_updates с объектом, ключи которого определяются по data.type.
  • giveaway_state — созданный ведущим снимок только с метаданными для управляемых представлений. meta.giveaway версия 2 включает giveawayId, постоянный roundId/epoch, увеличивая generation между новыми раундами, revision в пределах раунда, status, open, draw, keyword, count, ticketCount, замороженный config, до 120 предварительных entrants, и последние 20 winners. Записи предоставляют id, name, platform и tickets; победители добавляют drawnAt и начисленные points. Coin Flip Pot добавляет outcome; Number Hunt добавляет number с публичным low, high и недавний guesses, но никогда не секрет. Получатели фильтруют по идентификатору розыгрыша и отбрасывают старые поколения и ревизии. Это образцы для отображения, а не полный реестр билетов или инструкция на выплату. Ключи кошельков, балансы и бронирования не попадают в снимки для зрителей. Ведущий публикует в giveaway метку P2P и включённые потоки WebSocket оверлеев; это не означает видимость в OBS. Руководство.
  • meta.giveawayControlResult содержит результат действия розыгрыша Event Flow (ok, необязательный error, giveaway или simulated). meta.giveawayHandled перечисляет идентификаторы розыгрышей, уже обработанные действием участия или покупки, чтобы автоматическая команда чата не списала оплату повторно. Редактор добавляет meta.economyTest для имитированных действий розыгрыша; это не событие исходной платформы и не ключ авторизации.
  • video_stats использует структурированный meta объект для состояния внешнего кодировщика или сервера, включая provider, label, online, bitrateKbps, rttMs, bufferMs, счётчики потерь и отброшенных пакетов и необязательные сведения о кодеке.
  • События в стиле пожертвования могут включать объект с описанием, например { amount, currency, supporter } для Kick, { bits } для Cheers Twitch. У событий подписок свои метаданные, зависящие от источника; они не становятся денежными пожертвованиями автоматически.
  • Нормализованные сообщения вебхуков Stripe, Ko-fi, Buy Me a Coffee и Fourthwall включают идентификатор в пространстве провайдера meta.webhookId, скопированный из стабильного идентификатора события провайдера, чтобы принимающие страницы могли подавлять повторы при повторной доставке и смешанных способах передачи.
  • Рейды Twitch передают { fromId, fromLogin, viewers }. Другие источники отличаются: Whatnot использует meta.numRaiders, тогда как SharePlay использует необязательный meta.fromLogin/meta.viewers. Перед чтением метаданных рейда проверьте строку конкретного источника.
  • Активации наград Twitch EventSub предоставляют meta.rewardId, cost, rewardTitle, redemptionId, и устаревшее alias вместе с подготовленным сообщением. Карточки наград DOM и другие источники могут передавать меньше полей или другой их набор.
  • user_banned содержит только метаданные для виджетов модерации. Намеренно исключает chatname и chatmessage; используйте meta.username, meta.displayName, meta.avatarUrl, и meta.profileUrl.
  • Способы передачи чата, поддерживающие синхронизацию удаления через управление источником, должны предоставлять собственный идентификатор чата платформы в meta.messageId вместо опоры на внутренний идентификатор док-панели data-mid значение.
  • Удаления из источника используют {delete: {type, id}} для известного идентификатора сообщения док-панели либо {delete: {type, meta: {messageId}}} для собственного идентификатора сообщения платформы. Известный идентификатор удаляет только совпадающие сообщения. Если известен только целевой пользователь, отправьте {delete: {type, userid}} или {delete: {type, chatname}} чтобы удалить сообщения этого пользователя с этой платформы. Никогда не подставляйте личность модератора вместо целевого пользователя. Входящие удаления не требуют необязательной настройки синхронизации модерации из док-панели на платформу.
  • Метаданные идентификации источника SSApp могут добавлять meta.ssnAccountRole, meta.ssnSourceId, и meta.ssnSession когда источнику назначена нестандартная роль учётной записи.
  • Event Flow может запросить выделение, задав meta.featured = true в данных чата, что автоматически выделяет сообщение в док-панели и оверлее выделенных сообщений.
  • AI Event Overlay: действие showAiEventOverlay отправляет копию вызвавшего его сообщения получателю с меткой aievent-CONFIGURATION_ID, добавляя meta.aiEventOverlay: {profile: "CONFIGURATION_ID"}. Существующие поля сообщения и метаданные в виде объекта сохраняются; скалярные метаданные сохраняются в meta.value. Это адресная доставка, а не новое событие платформы. Исходное сообщение не изменяется. См. руководство по настройке.
  • Необязательно meta.aiEventOverlay.variation выбирает точную фразу, одобренную в сохранённых настройках оверлея. Текст зрителя и метаданные заполняют поля шаблона после его генерации.
  • Запросы на отображение AI Event Overlay требуют профиль и его приватный токен отображения. Настройки и ключи API управляются только через локальное всплывающее окно SSN. Ответы используют {aiEventResponse: {target, value}} или {aiEventResponse: {target, error}}. Результаты генерации содержат template, duration, warnings, а также необязательные URL данных мультимедиа в image/audio.
  • Награды в виде ИИ-оверлеев, оплаченные баллами, используют aiEventPresentation (id, profile, expiresAt, result, message) и подтверждают получение через aiEventDelivered (идентификатор доставки). Записи о списаниях и суммы возврата остаются на стороне хоста.
  • Event Flow может запросить закрепление в док-панели, задав meta.pinned = true; необязательный meta.pinnedTarget ограничивает закрепление док-панелью с соответствующим label.
  • Термопечать Event Flow записывает результат в meta.thermalPrintResult (success и необязательный code/error), сохраняя событие чата и остальные метаданные. Для событий с числовыми или другими необъектными метаданными диагностика остаётся в результате действия, а само событие не меняется.
  • Включаемые по желанию награды-стикеры SSN: event: "sticker" отправляется только в stickers метку оверлея после списания баллов лояльности. Устанавливает platform и type в поле исходного сообщения type, и сохраняет chatname, с пустым chatmessage, textonly: true, и contentimg содержащий относительный путь к изображению из пакета или одобренный ведущим HTTPS-адрес медиафайла. meta.sticker содержит id, pack, name, cost, duration (секунды), motion, redemptionId, и expiresAt (миллисекунды Unix). Это награда SSN, а не пожертвование платформы или её собственное событие баллов канала. См. галерея и руководство по настройке.
  • Проигрыватель стикеров возвращает пакет управления {action: "stickerReceipt", meta: {sticker: {redemptionId, success}}} своему отправителю при загрузке изображения или ошибке. Только подтверждения от подключённого stickers участнику соединения завершить ожидающую активацию награды. Неудачная или неподтверждённая доставка запускает возврат; этот пакет управления не является событием чата. Рекомендуется один активный экран стикеров на сеанс.
  • Команды сценического оверлея ИИ используют { action: "aiOverlay", target, meta } либо воспроизведение соведущего под управлением док-панели использует { action: "cohostOverlay", target, meta }; сохраняйте все сведения команды, например command, text, emotion, avatar, и tts внутри meta.
  • Если платформа одновременно предоставляет несколько счётчиков, предпочтителен структурированный объект с явными ключами (meta.viewer_count, meta.follower_count) вместо перегрузки строк разными значениями.
  • Торговые оверлеи должны использовать объекты снимков в meta (например auction_update и commerce_update) и избегайте произвольных полей верхнего уровня.

YouTube — стандартный захват DOM

Реализация: sources/youtube.js

  • Держите вкладку чата трансляции открытой. Захват читает карточки подписок и подарков, отображаемые в этом сеансе; зрителю не обязательно быть владельцем канала или модератором. Доступ учётной записи и выбранный вид чата могут влиять на видимые строки.
  • При открытии оверлея количества зрителей и активности чата с отображением зрителей их количество запрашивается автоматически. Настройки Показывать количество зрителей и Отслеживать активных участников чата также включают сбор данных.

YouTube — захват WebSocket / Data API

Реализация: sources/websocket/youtube.html, общие вспомогательные модули в shared/

  • По умолчанию используются разрешения OAuth youtube.readonly и youtube.channel-memberships.creator. Необязательное право записи добавляет youtube.force-ssl для отправки чата, модерации, блокировок и изменения сведений о трансляции; Google может показывать это как широкое разрешение управления YouTube, поскольку отдельного разрешения записи только для чата YouTube не предоставляет.
  • Статистика канала учитывает отдельные переключатели настроек (showsubscount, showviewercount).
  • API не может передавать изображения собственных значков; резервные значки используют указанные ниже эмодзи.
  • Когда API явно сообщает authorDetails.isChatModerator: true, данные чата, Super Chat, Super Sticker, YouTube Gift и подарочных подписок включают mod: true. Статус модератора не определяется предположительно и не кэшируется между событиями.
  • Уведомления о новых подписчиках используют myRecentSubscribers API (опрос каждые 5 минут). Примечание: результаты могут задерживаться или быть неполными; определить можно только публично видимые подписки.
  • Data API не предоставляет баннеры перенаправления YouTube, поэтому redirect остаётся доступным только из стандартного захвата DOM.

Уведомления о подписчиках YouTube (new_follower)

Social Stream теперь может определять новых подписчиков YouTube с помощью myRecentSubscribers адрес API. Это работает аналогично уведомлениям о подписчиках Streamlabs.

Как это работает:

  • Опрашивает API YouTube каждые 5 минут для получения новых подписчиков
  • Отслеживает увиденных подписчиков в localStorage для определения новых
  • Отправляет new_follower события с именем подписчика, аватаром и идентификатором канала
  • По умолчанию сообщения уведомлений о подписчиках отключены; при включении используется текущая строка перевода для alert-just-subscribed
  • По умолчанию объединяет серии из более чем трёх новых подписчиков, чтобы переподключения не переполняли оверлеи или Event Flow
  • Требуется включить режим WebSocket в настройках расширения

Ограничения (это ограничения API YouTube, а не Social Stream):

  • Нет гарантированного срока доставки — SSN опрашивает каждые пять минут, но API может возвращать задержанные или неполные результаты. Не рассчитывайте на фиксированное четырёхчасовое окно.
  • Только публичные подписки — Подписчики с приватным списком подписок не вызывают уведомлений. На YouTube подписки по умолчанию приватны.
  • Только владелец канала — Уведомления о подписчиках доступны только для каналов, которыми вы владеете и под которыми прошли аутентификацию.
  • Использование квоты API — Каждый опрос стоит 1 единицу API. При интервале 5 минут это примерно 288 единиц в день из стандартной суточной квоты 10 000.

Упрощённое озвучивание сохраняет этот нейтральный формат. В этих обновлениях серии количество и подпись пожертвования накопительные: 1, 2, 3 означают три подарка, а не шесть. Стандартный захват поддерживает устаревшие классы подарков и текущие строки с изображением и количеством; оба сохраняют event: "gift" и hasDonation. Переданный источником donoValue имеет приоритет; метаданные отрисованного подарка могут предоставлять coinsPerGift или diamondsPerGift до необходимости обращаться к таблице подарков или значению по умолчанию. Существующие настройки захвата событий трансляции продолжают действовать.

Эти ссылки на товары описывают каталог или родительское объявление; они не заменяют идентификатор заказа. Остаток товара не считается приобретённым количеством.

Для автоматизации успешных платежей задайте Тип события (расширенный) триггер в Собственное событие: payment_succeeded, а источник отфильтруйте до Whatnot. Существующие условия и шаблоны могут использовать поля этого события userid, chatname, subtitle и meta.orderId напрямую. Ранее сохранённая покупка не нужна, если уведомление содержит необходимые сведения.

Завершение аукциона или пометка товара как проданного не подтверждает успешную оплату: эти уведомления не отправляются как оплаченные purchase события и не задают суммы пожертвований. Другие paymentStatus values are forwarded only when explicitly supplied in a captured packet. Missing identifiers are omitted; a product ID alone may cover multiple sales, so use a supplied order/auction ID to correlate notifications. Capture does not remember purchases or match payment updates; any such workflow must be explicitly configured in Event Flow. Repeated commerce notifications with the same native event timestamp/ID are suppressed across overlapping channels and reconnects, within a 2,000-event cache. Packets without a native event identity use a brief duplicate window. Raw order/payment objects are not forwarded.

Joystick

Реализации: sources/joystick.js, sources/inject/joystick-ws.js, и sources/websocket/joystick.js

  • Обычный источник сайта Joystick 2.0 работает с выполненным входом на /u/<channel>/chat странице. Читает поле страницы ChatChannel, WhisperChatChannel, EventLogChannel, и SystemEventChannel Кадры Action Cable с резервным чтением отрисованных строк для Electron и переподключений.
  • Сообщения чата сайта используют те же основные поля, что YouTube, Twitch и Kick: собственный id, chatname, chatmessage, chatimg, chatbadges, nameColor, membership, mod, private, username/userid, и timestamp когда Joystick их предоставляет. Если сокет не передаёт цвет имени пользователя, отрисованная строка предоставляет тот же nameColor поле, используемое док-панелями с поддержкой цветов.
  • Изменения сообщений на сайте заменяют соответствующую строку док-панели; удаления, заглушения и блокировки убирают соответствующие строки по собственному идентификатору или имени пользователя.
  • Отдельный источник WebSocket использует учётные данные бота Joystick (client_id + client_secret); источник сайта использует сеанс страницы с выполненным входом.
  • Авторизуется на https://joystick.tv/api/oauth/authorize, затем обменивает или обновляет токены по адресу https://api.joystick.tv/api/oauth/token.
  • Подключается к wss://api.joystick.tv/cable и подписывается на GatewayChannel.
  • Необязательный обмен токенов OAuth используется для вспомогательных адресов, например https://api.joystick.tv/api/users/stream-settings.
  • Отдельный источник с учётными данными бота не отправляет viewer_update. Источник сайта с выполненным входом отправляет количество зрителей, когда сокет страницы передаёт его, как описано ниже.

Реализация: sources/xpsync.js

Instagram — захват эфира через REST и входящие новости

Реализация: sources/instagram.js и sources/instagramlive.js (одинаковые копии)

  • На страницах эфира (/<user>/live/?broadcast_id=...), чат трансляции поступает из собственного веб-API Instagram, который опрашивается с того же источника с cookie сеанса: GET /api/v1/live/{broadcast_id}/get_comment/?last_comment_ts={ts} примерно каждые 2 секунды, и POST /api/v1/live/{broadcast_id}/heartbeat_and_get_viewer_count/ примерно каждые 5 секунд при включённом количестве зрителей. После трёх последовательных ошибок или при отсутствии broadcast_id можно определить), источник переключается на разбор отрисованного DOM чата.
  • Личная лента активности учётной записи опрашивается через POST /api/v1/news/inbox/ примерно каждые 45 секунд на любой странице Instagram. Первый опрос только заполняет набор устранения дубликатов, поэтому история никогда не воспроизводится повторно; записи устраняются как дубликаты по tuuid.
  • Обязательные заголовки API (все статические или вычисляемые): X-IG-App-ID: 936619743392459, X-CSRFToken (из cookie), X-ASBD-ID: 359341, X-Requested-With: XMLHttpRequest, Content-Type: application/x-www-form-urlencoded.
  • Все события ленты активности используют type: "instagram"; чат трансляции остаётся type: "instagramlive". События лайков идут обычным путём через фоновый процесс: он отправляет одну копию в отдельный оверлей реакций, затем включает их в основной поток чата и событий только при capturelikeevent включено, как у TikTok и MeetMe. hideevents и собственный фильтр событий блокируют их везде. Поскольку события входящих принадлежат учётной записи с выполненным входом, они подавляются при просмотре чужого эфира (оба /<user>/live/ страницах и эфирах в просмотрщике историй; принадлежность определяется для каждого профиля и повторно проверяется после ошибок поиска) и отправляются в вашем эфире и на всех страницах вне эфира. Одновременно входящие опрашивает одна активная вкладка Instagram, и только при выполненном входе.

Facebook Live

Реализация: sources/facebook.js (сбор из DOM) и необязательный мост Graph API в sources/websocket/facebook.html

  • Захват DOM читает отрисованные комментарии Facebook; мост Graph API управляемой страницы читает комментарии видео. Оба используют type: "facebook", стандартные поля чата и отсутствие event для обычных комментариев. Мост API также включает необязательный platform: "facebook".
  • Мост API использует userid для идентификатора автора, если доступен, timestamp для допустимого времени создания в миллисекундах Unix и contentimg для изображения-вложения HTTP(S), переданного API. У комментариев только с изображением может быть пустое chatmessage. textonly применяется только к телу сообщения: исходный текст при true, экранированный HTML при false.
  • Контекст комментария API использует meta.messageId (собственный идентификатор комментария), meta.permalink, meta.videoId, и meta.pageId. В более ранних сборках API использовался meta.commentId, дублируемые поля автора и времени в meta, а также передавали туда необработанные вложения. Новые сборки вместо этого используют стандартные поля автора, времени и медиа; синхронизация удаления от этого не появляется.
  • Количество зрителей обновляется только при включении. Мост API читает одновременные live_views; суммарные просмотры видео не подставляются, а для недоступного количества не выдумывается ноль. Захват через API не выводит Stars, подписки, выделения или ответы из обычного текста комментария.
  • Stars захватываются из отрисованного DOM чата трансляции, когда Facebook показывает видимый N sent маркер; они заполняют hasDonation и donoValue по курсу 100 Stars = 1 доллар США без задания data.event.
  • Для проверки добавьте ssnreplay=1 к URL Facebook Live для обработки строк чата, уже видимых после обновления.

  • Оставьте data.meta предсказуемым: предпочитайте плоские ключи, не перегружайте строки смешанными данными и всегда указывайте единицы (currency, bits, duration).

Оверлеи монетизации

Чаевые NinjaBacker используют platform: "ninjabacker", type: "ninjabacker", chatname, обычный текст chatmessage, textonly: true, с префиксом источника id, отформатированный hasDonation, и числовой donoValue. Это обычные строки пожертвований без event переопределение. meta.ninjabacker содержит ISO currency и в основных единицах валюты amount. Для анонимных чаевых используется имя Anonymous. Источник использует либо SSE в реальном времени без повтора, либо отдельно включаемый приёмник подписанных вебхуков в API SSN с очередью доставки до семи дней. Надёжная доставка использует стабильный ninjabacker:delivery:DELIVERY_ID id. Ни один режим не получает обратные операции возвратов или споров. Учётные данные приёмника и секреты подписи никогда не попадают в данные событий. Управляемые вызывающей стороной callbackId не являются идентификаторами оплаты и не передаются. Тестовые чаевые из панели исключаются из строк пожертвований. Они отправляют event: "monetization_test" с meta.ninjabackerTest содержащий id и at (миллисекунды Unix), только для отдельного уведомления предпросмотра.

event: "monetization_update" — снимок только с метаданными из type/platform: "socialstream". meta.monetization.wishlist содержит enabled, qr, position, rank, total, публичный url и текущий item (name, amount, currency, image, публичный url) либо null. meta.monetization.ninja содержит enabled, qr, position, username и публичный URL чаевых. Приватные Tip ID никогда не включаются. meta.monetization.ebay содержит enabled, qr, position, display (cycle/cheapest/first), seconds, отдельно включаемые настройки объявлений и публичные товары. У каждого товара есть id, name, amount, currency, image, url, auction, startingBid, endsAt, available, bought и updatedAt. Время указано в миллисекундах Unix. Учётные данные продавца и личность покупателя не включаются.

Подтверждённая ведущим покупка из списка желаний также включает meta.wishlistPurchase с id, name, необязательным supporter и at (миллисекунды Unix). Это подтверждение ведущего, а не уведомление об оплате Amazon; оно не считается денежным пожертвованием. Оверлеи должны устранять дубликаты по id и игнорировать старые уведомления о покупках.

Оплаченные заказы Shopify

Необязательный приёмник подписанных событий Shopify отправляет platform/type: "shopify" и event: "purchase" только для orders/paid с financial_status: "paid", положительную общую сумму, test: false, отсутствие отмены и актуальная метка времени обновления из подписанного тела. Тестовые, неоплаченные, устаревшие, отменённые уведомления и возвраты не создают действия покупки. Намерение сделать подарок не выводится автоматически.

chatname равно Anonymous; поля покупателя, приватные заметки и URL заказов исключаются. chatmessage является обычным текстом с textonly: true; subtitle хранит до трёх публичных названий товаров. meta.commerce содержит orderTotal и currency в валюте магазина, а также quantity когда известно полное допустимое количество. Получатель и физическое или цифровое назначение остаются незаданными. Без hasDonation или donoValue задано. id — стабильный непрозрачный хеш в пределах магазина и заказа с префиксом Shopify; это не исходный идентификатор заказа.

Покупки используют существующие пути активности, категорию Purchase в Multi-Alerts и Event Flow. Продвижение товаров использует существующий meta.monetization.commerce каталог. Импорт товара или установка его рекламной метки Gift не создают событие покупки или подарка. Настройка Shopify и ограничения доставки.

Подарки и торговля

Используйте event: "gift" для подарка, giftcontribution для оплаченной поддержки сбора на подарок, giftfunded для завершения сбора, и purchase для продажи товара. Эти имена не зависят от провайдера и от того, физический товар или цифровой. Устаревшее имя оставляйте giftpurchase событие для подаренных подписок; Throne раньше использовал это имя неправильно, а теперь отправляет gift. Существующие источники событий подписок не меняются. Собственные фильтры имён событий Throne следует переключить на gift; фильтры пожертвований менять не нужно.

hasDonation остаётся признаком платной поддержки для совместимости, с donoValue с переданным или оценённым значением в долларах США. Подарки и взносы сохраняют эти поля. Завершение сбора не включает оба поля, чтобы не учитывать взносы дважды. Обычные продажи товаров по умолчанию их не включают, сохраняя контракт eBay. Не определяйте намерение подарить по магазину, ссылке списка желаний или физическому товару: покупка для покупателя или другого получателя остаётся продажей, если источник явно не указывает подарок автору.

Необязательный общий meta.commerce поля: recipient (creator, buyer, other), itemType (physical, digital, service), quantity (положительное количество товаров), currency (валюта ISO), goalAmount (целевая сумма сбора в основных единицах валюты, никогда не новый доход) и orderTotal (известная общая сумма оплаченного заказа в основных единицах валюты; торговля, а не доход от пожертвований). Неизвестные сведения не передавайте. Названия товаров храните в subtitle, изображения в contentimg, а текст поддержки — в chatmessage. Существующие метаданные провайдеров остаются доступны. Throne передаёт получателя и валюту, а при завершении — goalAmount; eBay передаёт количество. Ни один из них не предполагает тип товара и не раскрывает приватные сведения о получателе.

Лента активности показывает эти события даже без текста поддержки. Multi-Alerts использует оформление пожертвований для подарков и взносов, включая отдельное уведомление Gift Fully Funded без денежной суммы. Для покупок есть отдельная категория Purchase, включённая по умолчанию, с purchasestyle, purchasesound, purchaseaccent, и disablepurchases параметры URL. Уведомления о покупках не меняют суммы пожертвований.

Event Flow предлагает эти имена событий в триггерах Event Type и Other Event. Триггеры пожертвований по-прежнему проверяют hasDonation; триггеры Gift Sub сохраняют смысл подписки. Compare Property принимает вложенные пути, например meta.commerce.recipient. Шаблоны действий принимают {meta.commerce.quantity} и {meta.commerce.currency}, вместе с существующим {donation}, {subtitle}, и {meta}. Вложенные пути учитывают регистр; отсутствующие значения отображаются пустыми, обход прототипов запрещён.

Вебхуки торговли автора и рекламные оверлеи

Публичные платежи Donation Ko-fi сохраняют hasDonation и получают значение в долларах США donoValue. Оплата подписок использует new_subscriber или resub, с уровнем в membership. Заказы магазина и индивидуальные заказы используют purchase без сумм пожертвований. Приватные события Ko-fi остаются исключёнными. JSON, закодированный как форма, декодируется один раз; имена и сообщения являются обычным текстом.

Buy Me a Coffee donation.created сохраняет денежную поддержку; extra_purchase.created и commission_order.created становятся purchase. wishlist_payment.created становится giftcontribution используя только сумму этого платежа; meta.commerce.completed записывает признак завершения провайдера, не создавая ещё одну денежную строку. membership.started становится new_subscriber с уровнем в membership, больше не используя неверно hasDonation для названия уровня. Сумма начала подписки сама по себе не считается оплаченным списанием. Тестовые, возвращённые, неудачные и неподдерживаемые события обновления или жизненного цикла не создают платных уведомлений. Скрытые заметки сторонников исключаются.

Fourthwall поддерживает ORDER_PLACED (purchase), GIFT_PURCHASE (gift, получатель other), DONATION (обычная строка пожертвования) и SUBSCRIPTION_PURCHASED (new_subscriber). Существующие суммы заказов сохраняют hasDonation для обратной совместимости с пометкой meta.commerce.legacyDonationValue: true; это явное исключение из новых правил по умолчанию для продаж товаров. Заказы с использованными подарочными картами создают уведомление о покупке без суммы пожертвования: новую списанную сумму нельзя надёжно вывести из общей суммы заказа, а покупка подарка уже учтена. Платёжные имена и адреса электронной почты не используются для публичного представления. Тесты из панели управления и обновления заказов не создают платные уведомления.

Эти адаптеры сохраняют существующие пересылку, действия ботов, Event Flow и маршрутизацию направлений с meta.webhookId устранением дубликатов. Они предоставляют публичные имена, сообщения обычным текстом, известные названия товаров в subtitle, и ISO meta.commerce.currency вместе с числовыми суммами пожертвований, где применимо. Они не добавляют учёт возвратов или новую аутентификацию приёмника; используйте существующий настроенный путь вебхука провайдера.

meta.monetization.commerce в monetization_update содержит enabled, qr, position, display (first/cycle), seconds и массив публичных items. У каждого товара есть name, url, image, необязательный amount (null, если неизвестен), currency и purpose (shop/gift/support/membership). Это рекламные сведения, введённые ведущим, а не доказательство оплаты. Добавление и изменение товаров не создаёт событие пожертвования или покупки. Общий оверлей использует mode=commerce; view=both|showcase|card|alerts отделяет продвижение от активности. Необязательные параметры URL style, scale, cardevery, cardfor и onlytype управляют отображением. Существующие режимы провайдеров также принимают параметры вида и расписания. Управление отображением товаров

Существующий monetization_update снимки могут включать meta.monetization.commerce.live: null для сохранённого расписания или {mode: "show" | "hide", url?: "https://...", until: 0 | epochMilliseconds}. Show сопоставляет точный сохранённый URL товара; если товара нет, карточка не показывается. Положительное until по истечении возвращает сохранённое расписание; нулевое действует до изменения или перезапуска SSN. Hide скрывает рекламу товаров, но не уведомления о платной активности.

commerce.viewerURL — опубликованный URL магазина только для чтения или пустая строка. При наличии рекламные QR-коды ведут туда. Он никогда не содержит сеанс SSN или ключ публикации. Товары остаются в commerce.items. Элементы отображения, импорт и публикация не создают события пожертвования или покупки. См. Управление товарами для Event Flow и удалённого API.

Event Flow commerceControl ожидает прямой ответ или ответ Chrome до восьми секунд. Для обычных данных событий оно сохраняет событие и добавляет meta.commerceControlResult: {success: true, commerce: controlState} или {success: false, error: "..."}. Для существующего числового, массива или другого необъектного meta, метаданные не меняются, а диагностика возвращается как commerceControlResult в результате действия вместо этого. Неудачные команды управления останавливают дальнейшие действия цепочки, не подавляя исходное платёжное событие. Тайм-аут не доказывает, что команда не применена; проверьте состояние перед повтором относительной команды, например Next. Успех подтверждает только локальное состояние выбора, скрытия или расписания, но никогда не видимость в OBS или синхронизацию публичной страницы.

Торговые доски мест и последние продажи

Существующий monetization_update событие (type/platform: socialstream) также включает meta.monetization.boards. Его board содержит title, style (spots/teams), columns (1–20), visible, и до 120 spots. У каждого места есть строковый id, обычный текст label, status (available/claimed/revealed) и result (обычный текст, пустой до раскрытия). Занятие и раскрытие мест — введённое ведущим состояние отображения, а не доказательство покупки или случайное распределение.

boards.sales хранит до 100 последних записей: id, title, необязательный amount (null, если неизвестно), currency, quantity, source, и at (время записи в миллисекундах Unix). automatic включает сбор, salesVisible управляет отображением и revision увеличивается при изменениях. Автоматический сбор принимает только purchase события Shopify, eBay seller, Fourthwall, Ko-fi и Buy Me a Coffee; приватные и тестовые события исключаются. Метаданные аукциона, чаевые, подарки и занятие мест не считаются покупками. Автоматические записи не подставляют общие суммы заказов, цены объявлений или суммы пожертвований вместо цены товара. Ручные записи используют source: "Host confirmed".

Состояние сохраняется в приватном хранилище монетизации этой установки; публичные снимки исключают идентификаторы устранения повторных доставок, личность покупателя и секреты. Явно показанные продажи сохраняют идентификаторы событий для удаления. Возвраты ведущий должен удалять вручную. Повторные идентификаторы покупок запоминаются отдельно (до 2000), в том числе после очистки видимой истории. Существующий getCommerceState ответ включает commerce.boards; commerceControl принимает команды доски и продаж, описанные в руководстве по доскам. Ручные изменения передают обновлённое состояние, но никогда не создают события покупок, суммы пожертвований или платные награды. Оверлеи скрываются, если снимок ведущего не поступал 35 секунд.

Дополнения для работы продавца: commerce.boards.board.id обозначает поколение доски. Ручной saleAdd может предоставлять boardId и spotId чтобы атомарно записать продажу и занять место; повторные связанные продажи, ещё присутствующие в недавней истории, отклоняются. saleRemove с reopenSpot: true освобождает это место только если поколение доски всё ещё совпадает. Публичные записи продаж не содержат этих полей связи для оператора. Необязательный platform для ручной продажи сохраняет источник для фильтрации, тогда как source: "Host confirmed" обозначает способ подтверждения. amount — итог записи, включая её quantity. Поле адаптера оплаченных заказов eBay meta.ebayPurchase.quantity сохраняется.

salesSettings.auctionSource включает помощник по товару Whatnot или eBay Live. Поле ответа управления commerce.auction содержит только source, title, priceText, status и at из последнего захваченного auction_update, либо null. Срок действия — пять минут; значение очищается при смене источника, снимке простоя или перезапуске. Помощник предназначен только оператору: он не сохраняется и не попадает в передачи зрителям; данные участника ставки или победителя отбрасываются. Скрипты источников и данные событий аукциона не меняются. Копирование черновика не подтверждает оплату и не создаёт продажу.

Event Flow audio controls

The Actions overlay accepts actionType: "play_audio" с audioUrl, volume (0–1), and optional audioPlayback: "queue" или "interrupt". Omitting the playback option keeps overlapping playback. Local media continues to use sourceType: "local", localAssetId, и localAssetName. Queue mode holds up to 30 waiting clips with a two-minute limit per clip; interrupt mode replaces that queue's current clip and clears its waiting items.

actionType: "stop_audio" stops Flow Actions audio clips and clears the sound queue. These are overlay control messages, not source chat events or proof that OBS output was heard. Event Flow resolves a configured random sound set to one audio URL before sending the action. See Event Flow setup.
